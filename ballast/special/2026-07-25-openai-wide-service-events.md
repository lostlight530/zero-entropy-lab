类型: 特殊专题
主题: 两次跨产品广泛事件与一项后续 ChatGPT 事件的事实边界

## 触发事件

2026-07-25 的公开状态记录当前列出三项事件, 其中两起跨产品事件均列出 API、ChatGPT 与 Codex 多个受影响组件, 更晚的一项仅列出 ChatGPT conversations

本专题于 2026-07-26 补录, 独立保存现实事件证据, 不占用 2026-07-25 每日专题, 不把公开事件报道当作受控实验结果

## 事实边界

能够确认的是 OpenAI 官方登记了两起已恢复的跨产品事件, 后续 ChatGPT conversations 事件在 2026-07-28 复核时已从 Investigating 经过 Identified 和 Monitoring 进入 Resolved, 并列出 1 个受影响组件

不能确认的是所有 OpenAI 产品、所有组件、所有区域和所有用户在同一时刻完全不可用

OpenAI 状态页说明可用性按层级、模型和错误类型聚合, 单个客户的实际可用性可能因订阅层级、模型和 API 功能而不同

因此本专题使用广泛服务事件或广泛共同退化, 不使用全部服务对全部用户完全失效作为已验证事实

## 与每日研究的关系

[2026-07-25 每日专题](../records/2026-07-25.md) 使用两次共同故障和分阶段恢复作为受控场景, 比较盲重试、聚合状态放行与上下文门控恢复

现实事件只触发研究问题, 不证明实验中的故障时序、客户端行为或恢复机制真实发生在 OpenAI 内部

每日实验结果也不能反向解释本事件根因

## 可迁移问题

- 多个 Agent 共享一个依赖时, 各自重试是否放大失败负载
- 聚合恢复状态是否足以证明每个执行上下文完成
- 事件复发时, 已验证任务能否避免重新调用依赖
- 检查点是否能区分等待恢复与错误完成
- 状态页恢复与任务级后置条件冲突时应采用哪一个完成判断

这些问题必须进入受控实验后才能形成观察, 本专题本身不计作独立实验

## 已验证事实

- 7 月 25 日的官方历史页当前列出三项事件
- 前两个事件页均列出 API 12 个组件、ChatGPT 15 个组件和 Codex 4 个组件
- 前两个事件最终均被官方标记为恢复
- 后续事件已从 Investigating 经过 Identified 和 Monitoring 进入 Resolved
- 官方明确说明聚合可用性与单个客户可用性可能不同

## 基于证据的推断

三个产品面同时出现多个受影响组件, 说明依赖该供应商的多条 Agent 路径可能在相近窗口暴露相关失败

聚合恢复状态适合作为恢复探测的输入, 但仅凭该状态不能证明某个具体任务已经有效完成

以上只是从公开范围声明导出的研究假设, 不是对内部架构或根因的事实陈述

## 未验证事项

- 三项事件的内部根因与相互关系
- 页面展示时间的时区
- 每个组件的逐分钟错误率与恢复顺序
- 所有地区、订阅层级、模型和用户的实际影响
- 客户端是否发生重试风暴或重复副作用
- 用户所称全部人员失败的完整样本与分母

## 后续研究入口

在独立时间窗口改变执行者数量、错误类型和恢复顺序, 比较固定重试、退避加抖动、共享重试预算与分区熔断

如果任务级调用和独立结果验证在聚合状态恢复前稳定通过, 应推翻必须等待聚合恢复才能继续的解释
