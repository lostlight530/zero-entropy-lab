## 重复信号

### 1. 技术可执行不等于当前有权执行

本周最稳定的重复信号是 `技术上仍可执行` 与 `当前任务仍有权执行` 的分离.

- 08-07 旧任务仍能调用生产入口
- 08-08 旧幂等身份仍能命中完成记录
- 08-09 旧任务仍能发起迟到重放
- 08-10 旧观察仍能在本地满足目标谓词
- 08-11 旧 generation 仍能到达尚未见新 generation 的 sink
- 08-12 服务和 transport 都仍允许请求
- 08-13 credential 自身仍然有效

这些局部合同都可能正确, 但任何一个都不能单独续期任务级副作用权限.

### 2. 当前性至少具有五个独立维度

本周证据可以稳定拆成五个需要分别维护的维度:

- `world state`: 当前事实源、revision、generation 与目标后置条件
- `intent`: 当前规范化意图是否仍与恢复身份相同
- `ownership`: 当前 holder 或尝试 generation 是否仍授权此执行者
- `time`: 任务业务有效期是否已经跨越
- `task authorization`: 当前任务是否 RUNNING, capability 或 credential 是否仍适用于这次任务

credential 是任务授权的一个输入, 不是任务授权的全部. 同样, 当前 world state 已满足目标也不能自动授权旧执行者继续写入.

### 3. 最终状态正确不能清除历史副作用

08-10 和 08-11 都证明只看最终状态存在历史不可辨识性.

- 08-10 相同最终 revision/value 可能来自完成判定前漂移或返回后的合法变化
- 08-11 三条路径最终都得到 value 30, 但两条弱路径已经执行过一次旧 holder 副作用

因此对时间竞态和不可逆副作用, 验证需要事件顺序、身份集合、计数或等价线性化边界.

## 恢复与重放

- 08-07 让旧任务和已完成当前任务真实重新经过生产入口, 区分 stale reject 与真实零写入完成
- 08-08 让同身份不同意图进入原生产入口, 证明错误跳过也可以是零写入
- 08-09 让迟到任务重新进入三条生产路径, 区分覆盖、冲突停止和 already_satisfied
- 08-10 重放的是验证边界, 并额外用事件顺序限制完成证据时点, 不把只读复核误称为业务副作用幂等
- 08-11 当前 holder 的已完成意图重新经过同一提交入口后零新增写入
- 08-12 已完成 intent 重新经过同一 retry 入口后零新增写入
- 08-13 已完成 intent 重新经过同一 authorization/submit 入口后零新增写入

零写入只有在身份、意图、当前状态和任务授权都仍匹配时才是有效幂等证据. 08-08 已经给出零写入但新目标未完成的反例.

## 假成功检查

- 08-07 两次 `applied` 都正常结束, 但旧值覆盖当前结果并复制副作用
- 08-08 `already_complete` 与零写入同时成立, 但新意图没有执行
- 08-09 迟到 `applied` 覆盖较新状态, 而单纯 generation conflict 又可能把已满足目标误判为失败
- 08-10 单次后置条件读取返回满足, 但判定前 revision 已经变化
- 08-11 最终值为 30 且 sink 最终已见 generation 2, 仍可能掩盖过期 generation 1 写入
- 08-12 HTTP/服务恢复、deadline 与 at-most-once 都通过, 但任务已经过期
- 08-13 token introspection 返回 ACTIVE 且请求只执行一次, 但任务已经 CANCELLED

因此本周既攻击“成功信号过强”, 也攻击“冲突信号被误当最终失败”. 完成判定必须回到当前任务语义而不是局部协议状态.

## 审计缺口

- 尚未用一个真实端到端服务同时组合 world state、intent、owner generation、valid_until、task status 与 credential state
- 尚未测量任务取消或改向到已经在飞行中的外部 tool call 真正失效所需的传播延迟
- 尚未在不可逆副作用上验证历史 stale write 的检测与补偿
- 尚未验证 approval 或 confirmation 是否需要与 action identity、intent、revision 和 expiry 绑定
- 尚未验证 sandbox 或 network allowlist 内部的动作在任务已经取消时是否仍会被错误接受
- 真实 multi-agent handoff 与 sink 之间的 generation 推进是否可以共享原子或线性化边界仍未知
- 08-09 的验证独立性低于 08-10 至 13, 当日只有逻辑分支独立而没有独立进程成功结果
- 本轮无法取得当前 PR head 的真实完整工作树, 因此不能实际执行 `ballast/tools/check.py`

## 下一阶段控制项

1. 构造统一夹具, 同时携带 `state revision + intent digest + owner generation + valid_until + task status + credential state`
2. 每次只撤销或推进一个维度, 让旧执行者重新经过真正副作用入口, 检查哪一层能够独立阻断
3. 把 approval 建模为绑定 action identity 与 expiry 的 capability, 比较永久批准、短期批准和提交时复核
4. 把 sandbox/egress containment 与任务语义授权分开实验, 防止把“无法出边界”误当成“边界内动作一定正确”
5. 对不可逆副作用记录唯一身份和事件顺序, 检查最终状态恢复正确后能否仍发现历史污染
6. 使用真实支持条件写入、租约或动态授权的服务做至少一个端到端复验
7. 后续如果统一夹具在三个实质不同故障位置、两个时间窗口均稳定复现并通过强反例, 再评估是否形成新的发现, 不提前升级

## 事实分层

### 已验证事实

- 08-07 至 08-13 七个日报都包含正常基线、故障注入或状态变化、强反例以及明确的验证边界
- 08-07、08-08、08-11、08-12、08-13 对有效完成路径提供真实生产或等价提交入口重放且零新增写入
- 08-10 的同日补充验证使用独立 Python 进程与 awk, 成功区分判定前漂移和判定后合法变化
- 08-11 的强反例中最终 value 相同, 但 stale side effect 计数不同
- 08-12 的弱路径即使服务恢复、transport deadline 未到且副作用只执行一次, 仍执行了已过期任务
- 08-13 的 introspection-only 路径即使 credential 为 ACTIVE, 仍执行了已取消任务
- 当前 METHOD 尚未把 08-07 至 08-13 的执行权限新鲜度统一为一个稳定方法段
- 当前 CASES 尚停在 B-20, 没有保存 08-07 至 08-13 七个新的可复用失败机制

### 基于证据的推断

- 安全恢复的最小控制面已经超出单一 generation 或 idempotency key, 更适合表示为 world state、intent、ownership、time 和 task authorization 的联合当前性检查
- 当前授权不是任务开始时一次计算后永久有效的布尔值, 对长时 Agent 更接近需要在副作用入口重新证明的时变合同
- sandbox、网络边界和 credential 最小权限主要限制动作能力与影响范围, 仍需要任务状态和意图层判断这次允许范围内的动作是否应该发生
- 独立验证需要尽量保留事件顺序和副作用身份, 因为合法后续动作可能把错误最终状态覆盖回正确值

### 未验证事项

- 五维联合控制面在真实分布式服务中的最小充分字段和原子性要求
- 任务状态服务、credential 服务与副作用 sink 之间的不同一致性级别会产生多大新的 TOCTOU 窗口
- 高并发 multi-agent fleet 中 ownership、intent 与 approval 的组合传播成本
- 人工确认、自动 safety decision 和 containment 在真实厂商 Agent 中如何与任务取消或改向联动
- 当前 PR head 完整工作树上的仓库级 `ballast/tools/check.py` 结果
