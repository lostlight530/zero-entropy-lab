## 外部来源复核

- [Google AIP-158 Pagination](https://google.aip.dev/158) 状态为 Approved, 页令牌用于继续分页且后续请求除页大小外应保持参数一致, 但规范没有承诺所有实现都绑定稳定集合快照
- [PostgreSQL 18 Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) 说明 Read Committed 下连续查询可以看到不同快照, Repeatable Read 才提供同一事务内稳定视图, 支持区分页位置与集合视图身份
- [Amazon SQS SendMessageBatch](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_SendMessageBatch.html) 明确说明批量调用即使返回 HTTP 200 也可能同时包含成功与失败单项
- [Microsoft Graph JSON batching](https://learn.microsoft.com/en-us/graph/json-batching) 明确说明批量响应 200 不代表内部各请求成功, 单项响应各自携带状态
- [MITRE CWE-367](https://cwe.mitre.org/data/definitions/367.html) 说明检查与使用之间资源状态变化会使检查结果失效
- [SLSA v1.2 Verifying artifacts](https://slsa.dev/spec/v1.2/verifying-artifacts) 要求 statement subject 与实际产物摘要匹配, 支持把验证结论绑定实际被消费的字节身份
- [RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html) 规定 202 只表示接受而非处理完成, `If-Match` 可用于防止 lost update, 前置条件失败时不得执行原方法, 并保留能够确认状态变更请求已经成功时的特殊处理语义
- [Azure Asynchronous Request-Reply](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply) 把 202, 状态资源和最终结果资源分开, 完成后再定位结果
- [Google Cloud Storage Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions) 用 generation-match 防止迟到或重复请求作用于错误对象代际
- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) 说明 stale `resourceVersion` 更新返回 409 Conflict, 需要客户端重新处理而不是按旧基准覆盖
- [Amazon EC2 API idempotency](https://docs.aws.amazon.com/ec2/latest/devguide/ec2-api-idempotency.html) 规定相同 client token 与相同参数可安全重试, 同 token 不同参数返回 `IdempotentParameterMismatch`
- [Google AIP-155 Request identification](https://google.aip.dev/155) 把 request ID 定义为特定请求的去重和安全重试身份
- [Stripe Idempotent requests](https://docs.stripe.com/api/idempotent_requests) 保存首次 key 结果并比较后续参数, 参数不一致时拒绝复用

这些来源来自标准组织, 公共规范和多个独立云服务实现, 能支持本周实验选择的工程合同, 但不能替代受控实验本身, 也不能证明不同服务共享相同原子性, TTL, 快照或副作用可见边界

## 递进关系

### 08-03 至 08-06: 完成证据身份化

四天依次攻击集合数量, 批量传输状态, 文件路径和异步状态资源

共同结果不是要求更多成功标记, 而是要求完成证据绑定真正被消费或产生的对象身份

- 集合任务需要绑定集合视图和成员身份
- 批量任务需要绑定单项意图和单项副作用
- 发布任务需要绑定实际字节摘要
- 异步任务需要绑定操作, 意图和最终产物

这四天主要回答 `验证的对象到底是谁`

### 08-07: 从验证正确进入生产重放正确

08-06 的完成后重放只重复验证器, 不能证明真实副作用入口幂等

08-07 明确让旧任务和已完成任务重新经过生产入口, 直接测量写入计数和最终值, 因此它不是重复 08-06, 而是证据层级提升

本日建立的边界是 `旧基准是否仍有提交权限`

### 08-08: 零副作用不是完成证明

08-07 已能拒绝旧代际并让已完成同输入重放零写入

08-08 进一步构造同一 token 但意图已经变化的恢复调用, 弱路径同样零写入且返回 already_complete, 却没有实现新目标

因此幂等记录必须回答 `同一意图是否完成`, 不能只回答 `同一身份是否出现过`

### 08-09: 冲突也不是失败证明

08-09 在 08-07 的代际围栏上加入反向强反例

当前 generation 已变化时旧任务确实失去直接写权限, 但如果当前权威状态已经满足原目标, 统一返回 conflict 会丢失真实完成信息

因此版本围栏负责写权限, 当前后置条件负责完成判断, 两者不能互相替代

## 周度候选解释

本周形成一个值得继续复验的三层恢复判定模型

1. 写权限层: 当前代际, ETag, generation 或等价版本是否仍允许旧意图提交
2. 意图身份层: 幂等身份是否仍绑定同一规范化任务意图
3. 目标后置条件层: 当前权威世界是否已经满足任务目标

三层分别受到 08-07, 08-08 和 08-09 的直接攻击, 但本周没有单一端到端实验同时组合三层并注入多次并发状态变化

因此该三层模型只作为周度候选解释保存, 不升级为新发现, 不写入 NOTES.md

## 强反例收束

本周最重要的七类假成功或误判分别是

- 结果数量正确但集合身份重复和遗漏
- 批量 HTTP 200 且条目齐全但单项副作用缺失
- 验证与发布命令都成功但最终字节不是被验证字节
- 状态 Succeeded 但最终产物不存在
- 生产入口 applied 但旧值覆盖新状态并复制副作用
- already_complete 且零写入但新意图根本没有执行
- generation conflict 但当前状态其实已经满足目标

它们共同证明表面成功与表面失败都不能直接替代当前任务级后置条件

- 七份日报都包含固定研究链, 故障注入, 强反例和事实分层

- 08-09 验证没有达到进程级独立, 该限制被保留

### 基于证据的推断

- 完成证据需要绑定集合, 单项, 字节, 操作, 意图和当前状态中的适用身份, 不能只绑定传输或脚本成功状态
- 安全恢复至少需要分别处理旧写权限, 当前意图身份和当前目标后置条件, 但三层组合模型仍需端到端攻击
- 操作数量和局部耗时只有在结果质量与验证强度满足后才有比较意义

### 未验证事项

- 三层恢复判定模型在单一端到端系统中的组合正确性
- 真实远端服务的原子性, 最终一致性, TTL, 缓存和不可逆副作用边界
- 跨实现验证器是否会发现当前共享 JSON, SHA-256 或字段合同中的共同失效
- 完整工作树上的仓库级检查结果
