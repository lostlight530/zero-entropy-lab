## 重复信号

### 1. Current execution permission

08-18 证明新 holder 获得新 epoch 只回答谁现在有权尝试执行

08-21 的 task expiry 控制条件继续限制恢复窗口, 说明 effect evidence 即使完整也不能自动续期当前任务权限

因此第一问保持为 `现在是否仍允许执行`

### 2. Historical effect evidence

08-19 至 08-22 连续把 negative evidence 从 query availability 收紧到 read freshness、retention 与 resource lifecycle

- query error 不能降级为 miss
- successful miss 需要覆盖 prior commit 的 freshness
- fresh miss 还需要 retention coverage
- current live absence 不能替代 historical occurrence absence
- marker 或 tombstone 只有绑定 exact effect identity 才可能成为有效线索

因此第二问保持为 `此前未知尝试到底发生了什么`

### 3. Current completion evidence

08-23 证明 exact receipt hit 只保证 historical occurrence, effect 后续被 compensation 或其他合法 reversal 时不自动等于 current completed

08-24 继续证明即使恢复器确实重新读取 postcondition, successful read 也可能来自滞后副本, stale positive 会让 authoritative value 已经不满足任务时仍保存 completion

08-10 的既有 postcondition race 实验已经证明完成声明应绑定 verified revision 与判定时点, 08-24 从读取一致性方向独立攻击同一稳定边界

因此第三问从 `当前目标现在是否仍成立` 收紧为 `是否有足够新鲜且绑定正确目标的 current completion evidence`

### 4. 相关状态围栏

08-20 与 08-24 都出现 whole-store global revision 的同类代价: 它可以提供保守 freshness, 但无关状态推进会造成 over-fencing

08-24 的 target-state fence 在目标真正变化时等待, 只发生无关 global revision 变化时不等待

这支持使用 relevant state projection 缩小围栏范围, 前提是 projection 保守覆盖任务完成语义的全部依赖字段

### 5. 七日模型

本周期恢复判定可以收束为

`recovery decision = current execution permission + valid historical effect evidence + fresh current completion evidence`

其中 valid historical effect evidence 已有独立 NOTES 发现

fresh current completion evidence 不是另起一条重复发现, 而是对既有“生产路径成功证据不能替代当前后置条件”发现的跨时增强

## 恢复与重放

- 08-18 普通并发下 lease 可以限制同时执行者, 但 unknown-outcome takeover 若不查旧 effect 仍会重复副作用
- 08-19 query outage 时 strong path 保持 unknown 并停止, 查询恢复后从真实 receipt hit 或 authoritative miss 继续
- 08-20 strong path 等 freshness 覆盖 receipt commit 或直接读取 current authoritative receipt
- 08-21 receipt 过期后只有覆盖合法恢复窗口的 receipt 或 exact effect fallback 才能支持继续
- 08-22 current resource 已删除时 exact history 或 independent receipt 可以证明历史 occurrence, history pruning 后 miss 回到 unknown

- 08-24 stale positive 被 freshness fence 拒绝后读取 authoritative `clean`, 再确认 current permission 并恢复 `marked`

## 审计缺口

- 七日实验仍以受控标准库状态机为主, 没有真实支付、Saga engine、对象存储、多区域数据库或 Kubernetes API 端到端故障注入

- 尚未验证 current postcondition read 与 completion commit 之间再次变化的 TOCTOU 窗口
- 尚未验证多目标或多资源 postcondition 的 partial state、跨资源 revision 与 projection completeness
- 尚未把 target reincarnation 与 compensation reversal、stale read 三类故障组合到同一夹具

## 事实分层

### 已验证事实

- 08-18 至 08-24 七个日期都有主题唯一的每日研究记录
- 08-19 至 08-22 四个不同 failure position 已经支撑现有 negative prior-effect evidence 发现
- 08-23 exact receipt 在 effect 真实发生后存在, 但 effect 被合法反转后 receipt-only 仍会把 current `clean` 状态错误 completed
- 08-24 exact receipt 同样真实存在, eventual postcondition read 返回旧 `marked` 时得到 effect 1、completed 1、authoritative value `clean`
- 08-24 global-revision-fence、target-state-fence 与 linearizable-postcondition 都识别当前 `clean` 并在重新确认 current permission 后恢复 `marked`
- 08-24 unrelated global lag 中 global fence 发生额外等待, target-state fence 不等待
- 08-24 completed replay 四条路径均保持 effect 1, 因而不能替代 stale-positive crash-window
- 本周期包含一个外部特殊专题, 但专题没有计入独立实验数量

### 基于证据的推断

- unknown-outcome recovery 至少需要分别建立 current permission、valid historical effect evidence 与 fresh current completion evidence
- 对 persistent-state completion contract, truthful historical receipt 只证明 occurrence, 不能证明当前 postcondition 仍成立
- current postcondition query success 也不是充分证据, freshness 或等价 version boundary 必须覆盖会改变完成语义的相关状态
- whole-store revision 可以作为保守围栏, relevant-state projection 在依赖集合完整时可以减少无关 over-fencing
- current completion freshness 属于既有当前后置条件发现的稳定化, 不需要新增语义重复的 NOTES 发现

### 未验证事项

- 尚未证明三合同模型可以直接外推到任意不可逆副作用、消息投递或第三方 API
- 尚未证明一次 strong read 足以覆盖 read 后到 completion commit 之间的变化
- 尚未证明 target-state projection 在复杂真实任务中能够完整表达全部 completion dependencies
- 尚未验证真实多区域复制、cache invalidation、quorum failure 与跨服务 transaction 下的组合行为
- 尚未证明任何单一 Agent 平台已经完整实现本审计的 recovery contract
