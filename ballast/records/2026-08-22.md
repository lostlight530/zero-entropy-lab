# Ballast 日记录 2026-08-22

类型: 每日专题
主题: 当前资源删除后的历史副作用证据与删除标记误判

## 研究问题

当 unknown outcome 的远端副作用已经发生, completion 尚未持久化, 随后目标资源又被外部删除时, 当前权威读取返回 absent 是否足以证明此前没有副作用

本轮改变故障位置: 不测试 receipt query error, stale replica 或 receipt retention, 而测试 effect resource 自身的生命周期变化, 即 `effect committed -> completion missing -> resource deleted -> replay`

重点检验三个边界: 当前 live state 是否能代表历史 effect, delete marker 是否能作为完成证据, 以及绑定完整 effect identity 的版本历史在被清理后是否仍有证明能力

## 来源依据

查询日期为 2026-08-22

- [Amazon S3 deleting object versions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html) 说明 versioning-enabled bucket 的普通 DELETE 会让 delete marker 成为 current version, 随后的普通 GET 会表现为 404, 但此前对象版本仍可能作为 noncurrent version 保留. 适用边界是 S3 Versioning, 不直接证明任意 effect sink 的历史语义
- [Google Cloud Storage Object Versioning](https://docs.cloud.google.com/storage/docs/object-versioning?hl=en) 说明删除 live object 后可以保留 noncurrent object version, 同名版本由 generation 区分, 且 noncurrent version 只有在显式包含历史版本的请求中才出现. 适用边界是 Cloud Storage Object Versioning, 不等价于任意审计或 receipt 系统

两个独立官方来源共同支持一个设计前提: 当前资源不存在与历史资源从未存在不是同一事实, 当前读取和历史版本查询可以给出不同证据

把这个对象生命周期边界用于 Agent unknown-outcome 恢复属于本轮待证伪假设

## 可证伪假设

- H1: 当前权威 live read 返回 absent 时, 可以直接执行新的非幂等 effect, 因为 absent 足以证明上一次没有成功
- H2: 只要存在同名目标的 delete marker, 就可以把任务恢复为 completed, 无需核对历史 effect identity
- H3: 如果历史版本仍可查询并绑定完整 task, normalized action 与 target incarnation identity, deleted-after-effect replay 可以恢复 completion 而不产生第二次 effect
- H4: 如果历史版本证据已经永久清理, version-history miss 不能再证明此前没有 effect, 需要独立且仍有效的 authoritative receipt 或等价证据
- H5: completed replay 不能替代 resource-deleted crash-window, 因为 completion short circuit 会掩盖历史 effect 是否已经发生

H1 的反证条件是首次 effect 已发生且资源随后删除, replay live absent 后产生第二次 effect

H2 的反证条件是只有同名但不同 task, action 或 target incarnation 的删除历史时, marker 路径错误 completed 且当前必要 effect 数为 0

H3 的反证条件是 exact historical identity 仍存在时, version-identity 路径仍产生第二次 effect

H4 的反证条件是历史版本清理后, version-identity miss 仍能可靠区分 never-executed 与 executed-then-pruned 两种历史

H5 的反证条件是 completed replay 能暴露 deleted-after-effect 的重复副作用窗口

## 控制条件

- 当前 task, normalized action 与 target incarnation 保持固定, 除 unrelated-deleted-history 强反例外不改变
- current permission 在每次 B 侧真实 effect commit 前重新检查并记录 `permission_valid`
- completion 与 effect 分开保存, unknown 场景固定在 effect 与 receipt 已保存后, completion 保存前中断
- 外部删除只改变 effect resource 的 live state, 不改变 task current intent, ownership, valid_until, credential 或 approval binding
- `live-only` 只读取当前 live state, absent 后执行新 effect
- `delete-marker` 在 live absent 后读取同名 delete marker, marker hit 即恢复 completion
- `version-identity` 在 live absent 后查询历史版本, 只接受完整 effect identity hit
- `receipt-identity` 在 live absent 后查询独立 authoritative receipt, 只接受完整 effect identity hit
- unrelated-deleted-history 注入同名删除历史但 identity 不同, 用于攻击 marker 过宽
- history-pruned-after-effect 在真实 effect 与删除后再清理历史版本, 但保留独立 receipt
- 夹具只使用 Python 标准库与系统 awk, 不访问真实 S3, Cloud Storage 或外部 effect sink

## 实验设计

1. 四条路径执行 normal-no-prior, 没有 live resource, delete marker,历史版本或 receipt, 检查是否各执行一次必要 effect
2. 四条路径执行 deleted-after-effect, A 先通过 permission check, 提交 effect 与 receipt, 在 completion 前中断, 随后外部删除 live resource, B 重新进入同一 production entry
3. 四条路径执行 unrelated-deleted-history, 只存在同名但 identity 不同的历史版本与 delete marker, 检查 marker 是否 false hit
4. 四条路径执行 history-pruned-after-effect, A 已产生 effect 与 receipt 并中断, live resource 被删除后历史版本再被清理, 检查 version-history miss 是否退化成重复 effect
5. 四条路径执行 completed-replay, A 已保存 completion 后再次进入同一 production entry, 检查是否都保持单次 effect
6. producer 输出 scenario, path, effect_count, completed, result, ops 与 event_order, 完整运行三次并比较 stdout TSV SHA-256
7. 独立 Python verifier 不导入 producer, 从 event_order 重建真实 effect commit 数, 检查每个 B effect 前存在 current permission evidence, 并复核决定性反例
8. awk 第二验证实现独立复核 live-only 重复 effect, marker false hit, version identity 成功与历史清理后的失效, receipt fallback 单次 effect
9. producer 与 verifier 执行 `py_compile`

## 强反例

- unrelated-deleted-history 证明 delete marker 只说明同名对象存在删除历史, 不能单独证明当前 task, action 与 target incarnation 的 effect 已完成, 否则会形成 effect 0 与 completed 1 的假完成
- history-pruned-after-effect 证明 exact version history 只有在其保留边界覆盖恢复窗口时才能提供 prior-effect evidence, 历史被永久清理后 miss 会重新把 executed-then-pruned 与 never-executed 混在一起
- receipt-identity 在 history-pruned-after-effect 中仍保持单次 effect, 证明独立证据可以跨越 effect resource 自身的删除与历史清理, 但前提是 receipt provenance, identity, freshness 与 retention 条件本身成立
- normal-no-prior 证明 version-identity 与 receipt-identity 在没有历史证据时不会错误阻止必要 effect
- completed-replay 四条路径都只保持 1 次 effect, 因为 completion 在历史证据查询之前短路, 所以不能替代 resource-deleted crash-window

## 暂时结论

状态保持观察

本轮支持把 authoritative prior-effect evidence 再增加一个对象生命周期边界: 当前资源 absence 只是 current state, 不能单独回答历史 effect 是否曾发生

版本历史可以在 live resource 已删除后继续提供历史 effect evidence, 但必须绑定完整 effect identity, 仅有同名 delete marker 会产生 false hit

如果版本历史本身又被清理, version-history miss 不再能区分 never-executed 与 executed-then-pruned, 此时仍需要保留期更长的独立 authoritative receipt 或其他可核验历史证据

这与 8 月 21 日的 receipt retention 不同: 昨天攻击 receipt 自身的过期, 今天攻击 effect resource 与其版本历史的删除生命周期

## 复验条件

- 使用真实版本化对象存储验证 live 404, delete marker, noncurrent version 与 version identity 的实际 API 语义
- 加入版本历史生命周期规则, 验证 pruning 时点与任务合法恢复窗口是否错位
- 加入同名 key 但不同 generation, action 与 target incarnation 的真实对象历史, 检验 identity 绑定完整性
- 加入跨区域复制与历史列表一致性, 区分 history query error, stale history 与 authoritative miss
- 验证独立 receipt 与 effect resource 生命周期不同步时的 retention, provenance 与恢复行为

## 体系增量

- 为 unknown-outcome prior-effect evidence 增加 `current state != historical occurrence` 检查
- effect resource 当前 absence 不能单独作为 authoritative no-effect 证明
- delete marker 或 tombstone 只能作为历史存在提示, 若不绑定完整 effect identity 不得直接恢复 completion
- 版本历史作为 effect evidence 时需要显式记录 identity, freshness 与 retention 边界
- 历史版本被清理后应回到未知状态, 不得把 history miss 自动降级为 never-executed

## 事实分层

### 已验证事实

- 受控夹具中, effect 已发生且资源随后删除时 live-only 重放产生第二次 effect
- 同名但无关删除历史中, delete-marker 路径产生 effect 0 与 completed 1 的假完成
- exact version identity 仍保留时, version-identity 在资源已删除后保持单次 effect 并恢复 completion
- exact version history 被清理后, version-identity 产生第二次 effect
- 独立 exact receipt 仍保留时, receipt-identity 在版本历史被清理后保持单次 effect
- completed replay 四条路径都保持单次 effect, 不能暴露上述删除窗口

### 基于证据的推断

- current remote absence 与 prior effect absence 应被视为两个不同命题
- tombstone 只有在能够证明完整 effect identity 时才可能成为完成证据, 仅同名删除历史不够
- version history 可以作为 remote effect evidence, 但安全性受其 identity, freshness 与 retention 合同共同约束
- 当 effect resource 与其历史版本都可能被删除时, prior-effect evidence 需要独立于当前资源生命周期或明确覆盖合法恢复窗口

### 未验证事项

- 未把真实 S3 或 Cloud Storage 作为实验目标
- 未验证真实对象版本列表的线性一致性, 多区域复制或生命周期删除时延
- 未验证永久删除 version 与 receipt retention 同时发生的真实竞态
- 未验证不可查询外部副作用, 多实体副作用或删除后又同名重建的端到端恢复
- 未测量真实版本历史查询或 receipt 查询的网络成本
