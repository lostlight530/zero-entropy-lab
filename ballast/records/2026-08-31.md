## 研究问题

当 selector-bound persistent-state task 要求所有当前匹配 `worker` 的成员都为 `marked` 时, 如果 selector 成员发生 delete+join 但最终成员数量保持不变, 仅用 member count 作为 membership witness 是否会把旧成员集合误当成 current set

进一步构造同名 delete+recreate, 让成员数量和 logical name set 都保持不变, 检查 name-set witness 是否仍可能漏掉新的 target incarnation

关键窗口分别为 `LIST {A,B} -> delete B + add C(clean) -> count compare -> completion` 与 `LIST {A,B(uid-B1)} -> recreate B(uid-B2, clean) -> name-set compare -> completion`

## 来源依据

查询日期为 2026-08-31

- [Kubernetes Object Names and IDs](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/) 说明对象删除后可以重建同名对象, UID 用于区分相似实体的不同历史 occurrence. 适用边界是 Kubernetes object identity, 不直接证明 Ballast 夹具中的 selector membership contract
- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) 说明 collection list 带有 `resourceVersion`, list + watch 用该版本连续观察后续 create、delete、update. 适用边界是 Kubernetes collection change tracking, 不直接等价于本轮 UID-set witness
- [etcd API](https://etcd.io/docs/v3.7/learning/api/) 说明 transaction 的 comparison 只检查明确指定的 key/value/version/revision, 多个 comparison 原子应用. 适用边界是 etcd key-value transaction, 不自动证明业务 compare set 已覆盖真实 membership identity
- [PostgreSQL Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html) 将 phantom read 定义为重复 predicate 查询时匹配行集合因并发提交而变化, 并说明不同隔离级别对该异常提供不同约束. 适用边界是数据库 predicate consistency, 不直接等价于任意 Agent selector store

这些独立官方资料共同支持有限设计前提: 动态集合的完成证明需要能够区分成员集合的历史 identity, 原子比较只能保护实际进入 compare predicate 的字段

外部资料不证明本轮 false completion、effect_count 或恢复结果

## 可证伪假设

- H1: selector 成员总数在 completion 前保持不变时, count witness 足以证明 membership 未发生语义变化
- H2: count 与 logical name set 都保持不变时, name-set witness 足以证明 current selector membership 等价于旧集合
- H3: 对 selector-bound task, membership identity witness 需要绑定 current member UID set, 并结合逐成员 freshness 后再受保护提交 completion
- H4: whole-store global revision 可以发现成员替换, 但 selector 外无关 metadata 变化会造成额外 conflict
- H5: 替换后的新成员已经满足 `marked` 时, identity-aware path 应重新证明集合而不产生无效 effect
- H6: completed replay 不能替代 delete+join before completion 的 production-entry 窗口

H1 的反证条件是 count compare 成功且最终 count 仍为 2, 但 clean C 已替换 B, 路径仍 completed

H2 的反证条件是 recreate 后 names 仍为 A/B, name-set compare 成功, 但 B2 为新的 clean incarnation 且 current contract 不成立

H3 的反证条件是 UID set 发生替换后 strong path 仍直接接受旧 completion evidence, 或 conflict 后没有重新读取 current set 与重新确认 current permission

## 控制条件

- historical prior-effect evidence 固定为 hit, 本轮只研究 current completion membership evidence
- current execution permission 的 intent、holder、valid_until、task status、credential capability 与 approval binding 固定有效
- task semantics 固定为所有 current `worker` members 的 value 都必须为 `marked`
- 初始成员为 A=`uid-A1` 与 B=`uid-B1`, value 均为 marked, local revision 均为 1
- 初始 selector epoch 为 5, global revision 为 10
- `count-witness` 只比较 current membership count 是否仍为 2
- `name-set-witness` 比较 logical member name set 是否仍为 A/B
- `uid-set-witness` 比较 member UID set 与每个 observed UID 的 local revision
- `global-revision` 比较 whole-store global revision
- membership replace 会推进 selector epoch 与 global revision, 新 incarnation 的 local revision 允许重新从 1 开始
- selector 外 metadata 变化只推进 global revision
- conflict 后 strong path 重新读取 current set, 只对 current clean member 执行必要 effect, effect 前重新确认 current permission
- completed replay 从已持久化 completion 重新进入同一 production entry
- 夹具只使用 Python 标准库与系统 awk

## 强反例

第一强反例攻击 cardinality witness

B1 被 C1 clean 替换后, selector member count 仍为 2, count compare 完全成功, 但 task contract 已失效

第二强反例攻击 logical name-set witness

B1 被同名 B2 clean 替换后, member count 与 name set 都完全相同, name-set compare 仍成功, 但新 incarnation 未满足任务

反方向强反例是 replace-name-marked

membership identity 确实变化, strong path 必须重新证明 current set, 但因为新成员已经满足 predicate, 不应为了 identity conflict 机械产生 effect

outside-metadata-change 则限制 whole-store fallback: 它能发现 membership change, 但也会对 selector 外无关变化产生额外 reconciliation

## 路径比较

- count-witness 操作最少, 但同量 delete+join 时直接遗漏 membership identity 变化
- name-set-witness 能发现 B->C 的 logical membership 变化, 但同名 recreate 时仍把新 incarnation 当成旧成员
- uid-set-witness 在本轮受控条件下同时区分 member replacement 与 same-name reincarnation, 并避免 selector 外 global change 的额外 conflict
- global-revision 保守发现两种 replacement, 但 over-fencing 无关 metadata
- strong path 的额外读与 compare 只有在不降低结果质量时才视为合理成本, 本轮不以最少 ops 作为首要优化目标

## 暂时结论

本轮支持将 dynamic selector membership witness 进一步解释为 identity-bearing evidence

成员数量相同只能证明 cardinality, logical name set 相同也不能跨 delete/recreate 证明同一历史 membership

对任务语义要求 current members 的 selector-bound completion, membership proof 至少需要能够区分当前成员 incarnation, 并与逐成员 freshness 和 protected completion boundary 共同成立

这没有改变现行 METHOD 的稳定规则, 因为 METHOD 已明确要求 dynamic selector 的新增、删除或替换会使旧 membership proof 失效

### 基于证据的推断

- dynamic membership witness 需要区分 identity, cardinality equality 不足
- logical name-set equality 不能跨 delete/recreate 自动证明 membership 等价
- task-semantic member identity 与 per-member freshness 应在 protected completion boundary 共同成立
- whole-store revision 可作为保守 fallback, 但 relevant identity witness 能减少无关 over-fencing

### 未验证事项

- 尚未验证真实 Kubernetes、etcd 或 PostgreSQL 中的同量 replacement
- 尚未证明 UID-set witness 在高 churn、分页、stale index 或跨服务场景中足够
- 尚未验证 membership 与 completion 无共享事务时的 reconciliation
- verifier 仍共享事件字段语义与运行环境
