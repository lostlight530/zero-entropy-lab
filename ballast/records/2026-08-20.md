# Ballast 日记录 2026-08-20

类型: 每日专题
主题: 滞后副本 receipt miss 的一致性边界与恢复重放

## 研究问题

当 unknown outcome 的 receipt 查询请求本身成功, 但读取的是可能滞后的副本时, `receipt miss` 是否足以证明此前没有副作用

本轮承接 2026-08-19 的 `hit / miss / error` 三态, 但改变故障位置: 查询不报错, 而是让 receipt 已经提交到权威状态, 读取副本仍停留在更旧 revision

重点检验三件事: eventual miss 能否直接触发 effect, 旧 pre-attempt watermark 能否证明 miss 足够新鲜, 以及等待全局副本追平是否会对无关 revision 产生过度等待

## 来源依据

查询日期为 2026-08-20

- [etcd API guarantees](https://etcd.io/docs/v3.7/learning/api_guarantees/) 说明 etcd KV 默认提供线性化读取, 而 serializable member-local read 可以绕过实时 consensus 并返回相对 quorum 的 stale data. 适用边界是 etcd 的 KV 一致性合同, 不直接证明任意 receipt store 的实现
- [Amazon DynamoDB read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html) 说明 eventually consistent read 可能暂时不反映已经成功完成的近期写入, strongly consistent read 则反映此前成功写入的最新数据. 适用边界是 DynamoDB table 与受支持索引的读取合同, 不等价于所有跨区域或缓存读取
- [Amazon DynamoDB DAX consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DAX.consistency.html) 进一步说明缓存或节点复制可以暂时返回不同值, strongly consistent read 需要绕过 DAX cache 交给 DynamoDB. 适用边界是 DAX 与 DynamoDB 的组合模型, 本轮不把 DAX 行为外推为通用缓存协议

这些来源共同支持一个设计前提: 成功返回的“未找到”只有在读取一致性足够覆盖目标写入时, 才能作为当前不存在的证据

把该前提具体映射到 unknown-outcome receipt 的 freshness 合同属于本轮待证伪假设

## 可证伪假设

- H1: receipt 查询只要成功返回 miss, 即使来自 eventual replica, 也可以直接执行新的非幂等 effect
- H2: 只要副本 revision 不低于任务在首次 effect 之前记录的 pre-attempt revision, replica miss 就足够新鲜
- H3: 要避免 stale miss, 必须使用能够覆盖当前权威提交的读取语义, 或在不能证明 freshness 时安全停止
- H4: 要求副本追平整个全局 revision 虽然安全, 但可能因与 receipt 无关的更新造成过度等待

H1 的反证条件是 receipt 已在 revision 11 提交, 副本仍为 revision 10, replay 把 replica miss 当 authoritative miss 并产生第二次 effect

H2 的反证条件是 pre-attempt revision 恰为 10, 副本已经满足 `replica_rev >= 10`, 但 receipt 在后续 revision 11 才提交, 因而旧 watermark 仍允许 stale miss

H3 的反证条件是 linearizable current read 在 receipt 已提交场景仍产生第二次 effect, 或在真实无 receipt 场景错误永久零写入

H4 的反证条件是只有无关对象把 primary revision 推进到 11 时, global freshness 路径并未产生额外停止

## 控制条件

- relevant world state, current intent, ownership, task status, valid_until, credential, approval, action identity 与 target incarnation 全程不变
- 每次真实 effect 尝试前重新执行 current permission check
- receipt 与 effect 在同一受控提交动作形成, 不重复 2026-08-17 的双写顺序故障
- pre-attempt revision 固定为 10, 表示首次 effect 之前可知的最后权威 revision
- `eventual-miss` 从本地副本读取 receipt, miss 直接进入 effect
- `preattempt-watermark` 先要求 `replica_rev >= preattempt_rev`, 再把 replica miss 当可执行依据
- `global-freshness` 要求副本追平当前 primary global revision, 否则停止, 追平后重新进入 production entry
- `linearizable-current` 直接读取当前权威状态, 在模型中能够观察所有已经成功提交到 primary 的 receipt
- `lag-after-effect` 初始已有 effect 1 与 receipt revision 11, completion 缺失, replica revision 仍为 10
- `unrelated-lag` 没有历史 effect 与 receipt, 只有无关对象把 primary revision 推进到 11, replica 仍为 10
- completed replay 先完成 effect, receipt 与 completion 后再进入同一 production entry
- 夹具只使用 Python 标准库与系统 awk, 不访问真实 etcd, DynamoDB 或缓存服务

## 实验设计

1. 四条路径执行 normal-no-prior, primary 与 replica 都处于 revision 10 且没有 receipt
2. 四条路径执行 lag-after-effect, A 已在 revision 11 提交 effect 与 receipt, completion 保存前中断, B 在 replica revision 10 时恢复
3. 对会安全停止的路径, 系统让 replica 追平当前 primary revision 后, C 重新进入同一 production entry
4. 四条路径执行 unrelated-lag, 只有无关对象产生 revision 11, 用于检查 global freshness 的 over-fencing
5. 四条路径执行 completed-replay, 验证已完成重放是否能暴露 stale miss 窗口
6. producer 输出 scenario, path, effect_count, receipt_rev, primary_rev, replica_rev, completed, first_result, second_result, ops 与 event_order
7. producer 完整运行三次并比较 stdout TSV SHA-256, timing 独立写 stderr
8. 独立 Python verifier 不导入 producer, 从 event_order 中重建 effect 数, permission-before-effect, replica revision 与读取结果关系
9. awk 第二验证器独立复核 lag-after-effect 的重复 effect, linearizable receipt hit 与 unrelated-lag 的 over-fencing 反例
10. producer 与 verifier 执行 Python 语法编译检查

## 强反例

- unrelated-lag 中没有历史 effect, global-freshness 仅因无关对象把 primary revision 推进到 11 就先停止一次, 说明要求副本追平整个 global revision 是安全但保守的 over-fencing
- normal-no-prior 中四条路径最终都只产生 1 次 effect, 单看正常 miss 无法识别 eventual read 的假阴性风险
- completed replay 四条路径也都只保留 1 次 effect, 因为 completion 在 receipt 查询之前就短路返回, 不能替代 effect 已发生但 completion 缺失的 stale-replica 窗口
- pre-attempt watermark 确实能证明副本没有倒退到任务开始前更旧的状态, 但不能证明它已经覆盖 attempt 自己后续可能创建的 receipt
- lag-after-effect 的弱路径与强路径最终都 completed=1, 只有 effect 计数, receipt revision 与 event order 能区分重复历史

这些操作数只是受控状态机计数, 不能推断真实 consensus read, replica catch-up 或跨区域读取的成本

## 暂时结论

状态保持观察

本轮支持把 2026-08-19 的三态继续细化: `authoritative miss` 不只需要“查询没有报错”, 还需要读取 freshness 足以覆盖此前可能成功提交的 receipt

对 unknown outcome 的非幂等副作用, eventual replica 返回的 miss 不能自动当成不存在证据

仅绑定首次 attempt 之前的 watermark 也不够, 因为未知 effect 与 receipt 可能发生在该 watermark 之后

线性化当前读在本轮模型中直接关闭 stale miss 窗口; 如果系统只能使用滞后副本, 则需要能够证明该读已经覆盖相关 receipt 提交的更强 freshness 证据, 证明不了时应安全停止

要求追平整个 global revision 是一种保守替代, 但 unrelated-lag 表明它可能因无关状态变化造成不必要等待, 因此不能把“更强”误写成“更精确”

## 事实分层

### 已验证事实

- 受控 lag-after-effect 中, receipt 已在 primary revision 11 存在而 replica 仍为 revision 10 时, eventual-miss 与 preattempt-watermark 都产生第二次 effect
- preattempt-watermark 在 `replica_rev=10` 已满足 `preattempt_rev=10` 后仍读取不到 revision 11 receipt
- global-freshness 等副本追平 revision 11 后命中旧 receipt, effect 总数保持 1
- linearizable-current 在同一场景直接命中 revision 11 receipt, effect 总数保持 1
- unrelated-lag 中 global-freshness 因无关 revision 先停止一次, linearizable-current 不需要该等待, 两者最终都只执行一次必要 effect
- completed replay 四条路径均保持 effect 数 1
- 三次 producer 轨迹 SHA-256 一致, Python verifier 3/3 PASS, awk PASS, producer 与 verifier 均通过 `py_compile`

### 基于证据的推断

- unknown outcome 中的 receipt miss 必须带有足够的读取 freshness 语义, 才能升级为“此前 effect 未发生”的证据
- pre-attempt watermark 只能约束副本不早于 attempt 开始, 不能覆盖 attempt 自己后续可能成功的 effect receipt
- 读取当前共识状态是一种直接满足 freshness 的方式, 但真实系统还需按自身 consistency contract 判断, 不能把本轮 `linearizable-current` 名称当成跨系统 API 要求
- global freshness 可以作为保守围栏, 但如果全局 revision 包含大量无关更新, 它可能牺牲可用性而不增加相关 receipt 语义精度

### 未验证事项

- 未验证真实 etcd serializable 或 linearizable read 的端到端 effect recovery
- 未验证真实 DynamoDB eventually consistent 或 strongly consistent read 的副作用恢复流程
- 未验证跨区域复制, DAX, GSI, quorum 故障, read timestamp 欺骗, per-key revision 与 retention expiry
- 未证明任意 linearizable receipt store 都能同时解决 effect/receipt 原子性, target incarnation 或 permission freshness 问题
- 未测量真实 consensus read 与 replica catch-up 的延迟, 吞吐或成本
