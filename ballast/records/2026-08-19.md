# Ballast 日记录 2026-08-19

类型: 每日专题
主题: authoritative receipt 查询故障中的缺失判定与安全停止

## 研究问题

当任务处于 unknown outcome, authoritative effect receipt 查询本身暂时不可用时, 恢复路径能否把查询错误或过期负缓存当成 receipt 缺失并直接重试非幂等副作用

本轮承接 2026-08-18 的 takeover 后 prior-effect 查询, 但改变故障位置, 不再攻击 claim 本身, 而是攻击查询证据链不可用时的缺失判定

重点区分三种状态: `receipt hit`, `receipt miss`, `receipt query error`

## 来源依据

查询日期为 2026-08-19

- [RFC 9110: HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html) 将 404 Not Found 与 503 Service Unavailable 定义为不同语义类别. 404 表示当前未找到目标表示或不愿披露存在性, 503 表示服务暂时无法处理请求. 适用边界是 HTTP 响应语义, 不直接证明任意 receipt store 的业务存在性
- [Amazon S3 error best practices](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/ErrorBestPractices.html) 明确指出 InternalError 下请求可能已经处理也可能没有处理, 后续读取可能看到旧值或新值, 并建议按具体错误类型处理. 适用边界是 Amazon S3 请求与错误模型, 不等价于通用 effect receipt 协议
- [Google Cloud Storage Retry strategy](https://cloud.google.com/storage/docs/retry-strategy) 区分 transient response 与操作 idempotency, 并警告无条件重试非幂等操作可能产生意外副作用. 适用边界是 Cloud Storage 客户端与请求模型, 不证明本轮受控状态机的三态实现就是通用恢复方案

三个来源共同支持一个设计前提: 查询失败与权威确认的“不存在”不是同一个证据状态, 是否重试还必须考虑操作的幂等性

把该前提具体映射为 unknown-outcome receipt 查询的 `hit / miss / error` 三态恢复合同属于本轮待证伪假设

## 可证伪假设

- H1: authoritative receipt 查询错误可以等价处理为 receipt miss, 直接执行副作用仍不会重复
- H2: 查询失败时使用最近一次负缓存可以安全代替权威 receipt miss
- H3: 对非幂等 unknown outcome, 只有权威 miss 才允许进入新 effect, 查询 error 应安全停止并等待可核验查询恢复

H1 的反证条件是旧 effect 已提交且 receipt 真实存在, 查询故障被折叠为 miss 后产生第二次 effect

H2 的反证条件是负缓存形成于旧 effect 之前, effect 提交后缓存未更新, 查询故障回退该缓存后产生第二次 effect

H3 的反证条件是三态路径在查询恢复并得到真实 miss 后仍错误零写入, 或在查询 error 阶段仍产生新的 effect

## 控制条件

- relevant world state, intent, ownership, task status, valid_until, credential, approval, action identity 与 target incarnation 全程保持不变
- 每次真实 effect 尝试前都重新执行 current permission check
- receipt 与 effect 在同一受控提交动作中形成, 本轮不重复 2026-08-17 的 receipt/effect 双写顺序实验
- `error-as-miss` 把 receipt query error 折叠为 miss
- `negative-cache-fallback` 在 query error 时使用最近一次 cached miss, 该缓存允许在 effect 提交后保持陈旧
- `tri-state-safe` 显式区分 hit, miss 与 error, error 时不执行 effect 也不保存 completion
- 查询恢复后, 未 completed 的任务重新进入同一 production entry
- `outage-after-effect` 先提交 effect 与 receipt, 在 completion 保存前中断, 随后 receipt query 故障
- `outage-before-effect` 没有历史 effect, 但 receipt query 同样故障, 用于检查安全停止是否会永久错误跳过必要操作
- completed replay 先正常完成后再次进入 production entry
- 夹具仅使用 Python 标准库与系统 awk, 不访问外部存储

## 实验设计

1. 三条路径执行 normal-miss, authoritative query 正常返回 miss
2. 三条路径执行 outage-after-effect, A 已提交 effect 与 receipt, completion 缺失, B 在查询故障时恢复, 查询恢复后 C 再次进入 production entry
3. 三条路径执行 outage-before-effect, 初始没有 effect, B 遇到相同查询故障, 查询恢复后 C 再次进入 production entry
4. 三条路径执行 completed-replay, A 完成后 B 重放
5. producer 输出 scenario, path, effect_count, receipt, completed, first_result, second_result, ops 与 event_order
6. producer 完整运行三次并比较 stdout TSV SHA-256, timing 单独写 stderr, 不污染确定性轨迹
7. 独立 Python verifier 不导入 producer, 直接从 TSV 的 effect event, query 状态与 event order 重建关键断言
8. awk 第二验证实现只复核 outage-after-effect, tri-state 强反例与 completed replay
9. producer 与 verifier 执行 Python 语法编译检查

## 独立验证

Python verifier 与 producer 为两个独立文件

verifier 不导入 producer, 不读取 producer 内部成功布尔值或保存的期望对象

Python verifier 独立检查

- 12 个 scenario/path 组合完整且唯一
- effect_count 与 event_order 中实际 `effect_committed` 数一致
- 每个 effect commit 之前存在对应 actor 的 permission check
- normal-miss 三条路径均从 authoritative miss 执行一次必要 effect
- outage-after-effect 中 error-as-miss 与 negative-cache-fallback 都出现 effect 数 2
- tri-state-safe 在 query error 后先 safe stop, 查询恢复后 receipt hit 再保存 completion, effect 数保持 1
- outage-before-effect 中 tri-state-safe 先停止, 查询恢复得到真实 miss 后执行一次必要 effect, 因而安全停止没有被误实现为永久零写入
- completed replay 三条路径都保持 effect 数 1

三次 Python verifier 均返回 `PY_VERIFIER_PASS`

awk 第二实现返回 `AWK_PASS`

producer 与 verifier 均通过 `py_compile`

两个 verifier 仍共享 TSV 字段语义, 原始事件轨迹与同一系统运行环境

因此本轮不是独立远端 receipt 服务的实现验证

## 强反例

- outage-before-effect 中没有历史副作用, `tri-state-safe` 在查询故障阶段确实延迟了一个必要操作, 但查询恢复并得到 authoritative miss 后会执行该 effect. 这反驳了“安全路径只是不做事”的解释, 同时暴露安全性与即时可用性的真实取舍
- normal-miss 中三条路径结果完全相同, 只测试正常查询无法识别 error-as-miss 的重复风险
- completed replay 中三条路径也都只保留一次 effect, 不能替代 effect 已发生但 receipt 查询不可用的 unknown-outcome 窗口
- negative cache 曾经准确为 miss, 也不能证明后续 effect commit 之后 receipt 仍不存在
- 最终 outage-after-effect 三条路径都 completed=1 且 receipt=1, 只有 effect 计数与 event order 能区分一次 effect 和两次 effect 的历史

## 路径比较

| 路径 | authoritative miss | query error + prior effect | query error + no prior effect | completed replay | 主要边界 |
| --- | --- | --- | --- | --- | --- |
| error-as-miss | effect 1 | effect 2 | 立即 effect 1 | effect 1 | 把未知证据错误降级为不存在 |
| negative-cache-fallback | effect 1 | effect 2 | 立即 effect 1 | effect 1 | 负缓存可能跨 effect commit 变陈旧 |
| tri-state-safe | effect 1 | effect 1, 延迟 completion | 延迟后 effect 1 | effect 1 | error 时牺牲即时进展, 保留副作用单次性 |

正常 authoritative miss 下三条路径操作数都是 6

outage-after-effect 中操作数为 9, 10, 9, 但前两条虽然立即 completed, 已经产生重复 effect

outage-before-effect 中 tri-state-safe 需要第二次 production entry 才完成, 操作数为 9, 高于 error-as-miss 的 7 与 negative-cache-fallback 的 8

因此本轮不能用更少操作或更快 completed 作为首要质量指标

## 暂时结论

状态保持观察

本轮支持把 prior-effect 查询结果建模为至少三态, `hit`, `miss`, `error`

对 unknown outcome 的非幂等副作用, query error 不能降格成 authoritative miss, 历史负缓存也不能自动替代当前权威 miss

当当前执行权限仍有效但 prior-effect evidence 暂时不可取得时, 安全路径可以暂停新的 effect, 不写 completion, 等证据链恢复后重新进入 production entry

该策略会牺牲故障期间的即时可用性, outage-before-effect 已显示必要 effect 会被延迟

本轮只验证了受控 receipt store 模型, 不证明所有真实系统都应采用相同停止策略

## 事实分层

### 已验证事实

- 三次 producer stdout TSV SHA-256 完全一致
- Python verifier 三次通过
- awk verifier 通过
- producer 与 verifier 均通过 Python 编译检查
- authoritative miss 正常基线下三条路径均执行一次必要 effect
- outage-after-effect 中 error-as-miss 与 negative-cache-fallback 都产生第二次 effect
- tri-state-safe 在 receipt query error 时没有新增 effect 或 completion, 查询恢复后 receipt hit 只恢复 completion
- outage-before-effect 中 tri-state-safe 查询恢复后从 authoritative miss 执行一次必要 effect
- completed replay 三条路径均保持单次 effect
- event order 能区分最终 completed 与 receipt 相同但历史 effect 数不同的路径

### 基于证据的推断

- prior-effect evidence 至少需要区分“存在”, “确认不存在”与“当前无法判定”
- stale negative cache 不是 effect commit 之后的当前缺失证明
- 对非幂等 unknown outcome, 在无法取得 authoritative prior-effect evidence 时安全停止比把未知折叠为 miss 更能保护副作用单次性, 代价是故障窗口内降低可用性

- 未验证 receipt TTL 与 query outage 同时发生时如何区分 expired 与 unavailable
- 未验证多个恢复者在 query 恢复瞬间并发进入时的行为
- 未使用独立语言或独立运行时 verifier
