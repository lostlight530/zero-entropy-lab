## 研究问题

Lease 选出新 leader 之后, 旧 worker 已缓存的领导身份、已成功的 preflight、终态成功或数量相等的 receipt 能否证明非幂等 effect 获得 effect-time permission 并满足当前动态成员集合, 以及同一 sink transaction 内对 epoch、permission、target incarnation、membership revision 的联合检查能否拒绝 TOCTOU stale write

## 来源依据

2026-10-18 核验三家独立发布者的原始合同, 文档只证明各自语义, 不构成本地实验或线上故障的独立实证

- [Kubernetes coordinated leader election](https://kubernetes.io/docs/concepts/cluster-administration/coordinated-leader-election/): Lease holder、renewTime、leaseDurationSeconds、resourceVersion 与 leader election 的控制平面语义, 不能据此推断第三方 sink 自动具备 fencing
- [Temporal Activity definition](https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/activities/activity-definition.mdx): Activity 可能在 effect 已发生但未回报时重试, 需要应用侧 idempotency, 不自动证明跨 sink exactly-once
- [AWS DynamoDB conditional write](https://aws.amazon.com/blogs/database/handle-conditional-write-errors-in-high-concurrency-scenarios-with-amazon-dynamodb/): 条件表达式在数据库写入边界校验版本并拒绝不匹配写入, 不能推广为所有外部 effect sink 的保证

本轮 SQLite 使用 `BEGIN IMMEDIATE`、同事务读取控制行与 effect insert, 是本地模拟 protected boundary, 不声称复现 Kubernetes Lease 或 DynamoDB 行为

## 可证伪假设

H1 terminal success 足以 COMPLETE, H2 receipt count 等于 member count 足以 COMPLETE, H3 仅在 effect sink 提交边界联合核验 current epoch/holder、permission、incarnation、membership revision/member, 并在恢复时重新核验 historical authorization、exact prior-effect evidence 与 protected current witness, 才能区分 COMPLETE、RECONCILE、STOP_UNKNOWN、RETRY_ALLOWED 和 BLOCKED
