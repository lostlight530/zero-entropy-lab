# Ballast 日记录 2026-07-28

类型: 每日专题
主题: 重复字段输入中的共享解析器共同失效

## 研究问题

生产器与验证器共享默认 JSON 解析语义时, 两者一致通过能否证明原始输入没有产生语义歧义.

## 来源依据

查询日期为 2026-07-28.

- [RFC 8259 Section 4](https://www.rfc-editor.org/info/rfc8259/) 发布于 2017-12, 规定对象成员名应保持唯一, 并说明重复成员名会导致接收软件行为不可预测, 不同实现可能保留最后一个、报错或保留全部.
- [Python json 标准库文档](https://docs.python.org/3/library/json.html#repeated-names-within-an-object) 当前文档说明默认解码器接受重复名称并只保留最后一项, `object_pairs_hook` 可改变该行为. 边界是 Python 实现行为, 不代表所有解析器.
- [NASA IV&V Overview](https://www.nasa.gov/ivv-overview/) 说明技术独立性要求验证者以独立于开发者的专业方法评估过程与产物. 本实验只实现不同语义入口和独立进程, 不具备管理与财务独立性.

## 可证伪假设

路径 A 的生产器用默认解析器读取重复 `status` 字段, 只保留最后的 `complete`, 再把规范化产物交给使用同一解析语义的验证器. 预计两者一致通过, 但原始输入的 `failed` 状态已不可见.

路径 B 的验证器直接回读原始输入, 使用保留成员序列的钩子拒绝重复名称, 再比较原始输入与产物合同. 预计歧义输入被拒绝, 唯一字段控制输入通过, 已验证控制结果重放写入为 0.

如果默认路径不接受歧义输入, 异构路径不能识别重复字段, 唯一字段控制输入被拒绝, 或重放产生额外写入, 对应假设被推翻.

## 控制条件

- 歧义输入与控制输入只有重复 `status` 字段这一项实质差异.
- 两者都包含相同任务、最终可见状态与处理结果.
- 生产器和共享验证器都使用 Python 默认 `json.loads`.
- 独立验证器在另一 Python 文件和进程中读取原始字节与产物, 使用 `object_pairs_hook` 保留成员顺序并拒绝重复名称.
- 所有样本位于系统临时目录, 使用 UTF-8 并在结束前清理.

## 实验设计

1. 构造同时含 `status=failed` 与 `status=complete` 的单个 JSON 对象.
2. 默认解析器读取后生成规范化产物, 共享解析语义的验证器检查任务、状态与结果.
3. 独立验证器从原始输入重新解析成员序列, 在规范化前检查重复名称.
4. 使用只含一个 `status=complete` 的控制输入重复生产与两条验证路径.
5. 对已验证控制产物执行同输入重放判断, 只有验证失败才允许重写.
6. 检查临时清理与完整验证耗时.

## 原始观测

- 歧义输入经默认解析后可见状态为 `complete`, 生产器写入 1 个规范化产物.
- 共享解析语义验证器判定歧义产物有效.
- 独立验证器回读原始输入后以 `duplicate_name:status` 拒绝, 退出状态为 1.
- 唯一字段控制输入被共享验证器与独立验证器同时接受, 两者检查的键集合为 result、status 与 task.
- 控制产物完成后重放写入为 0, 字节保持不变.
- 三项机制断言全部通过, 临时状态清理通过.
- 验证后的有效耗时为 156.393 毫秒.

## 独立验证

`verify_parser_independence.py` 在独立进程中同时读取原始输入和最终产物, 在对象折叠为字典前检查成员名唯一性, 再验证任务级合同与源产物一致性.

它不信任生产器规范化后的输入摘要或共享验证器的通过状态. 独立性限制是两条路径仍使用 Python 同一 JSON 词法实现, 只在对象成员处理和输入来源上分离, 因此不能证明对所有解析器差异都具有技术独立性.

## 强反例

歧义输入经过生产器后得到结构完整、字段齐全、状态 complete、结果正确的规范化产物, 共享验证器也再次解析并通过. 原始输入中的 failed 字段已经在两条路径的共同折叠规则中消失.

这个状态推翻了生产器与验证器一致就等于原始任务语义唯一的解释. 唯一字段控制输入同时通过两条路径, 说明严格拒绝不是对所有输入的机械失败.

## 路径比较

| 路径 | 读取事实源 | 歧义输入 | 控制输入 | 首次写入 | 重放写入 |
| --- | --- | --- | --- | ---: | ---: |
| 默认生产加共享解析验证 | 规范化对象 | 错误接受 | 通过 | 1 | 未作为有效路径重放 |
| 原始输入成员检查 | 原始文本与产物 | 拒绝 | 通过 | 1 | 0 |

独立路径增加一次原始输入解析, 但阻止了共享假设造成的假成功. 本实验不比较绝对吞吐, 有效耗时包含外部验证与清理.

## 暂时结论

状态为观察.

在本次重复字段实验中, 共享默认解析语义让生产器和验证器同时丢失同一证据, 一致通过仍是假成功. 验证器保留原始输入并改变对象成员处理路径后识别了歧义.

单次解析器机制不足以升级为候选或长期发现.

## 复验条件

使用不同语言或独立解析实现复验, 改变重复字段位置、Unicode 转义名称、数字范围和嵌套深度. 让生产路径签名规范化产物, 检查签名前后验证是否仍能追溯原始语义.

## 事实分层

### 已验证事实

- 默认解析器与共享语义验证器同时接受了重复 status 字段产生的规范化产物.
- 回读原始输入并保留成员序列的验证器拒绝重复字段.
- 唯一字段控制输入通过两条验证路径, 完成后重放写入为 0.

### 基于证据的推断

- 验证独立性不仅是独立进程, 还包括事实源和语义转换路径的分离.
- 只验证规范化产物会永久丢失规范化前的歧义证据.

### 未验证事项

- 不同语言解析器能否复现相同差异.
- 签名、Schema 验证和规范化顺序如何影响重复字段检测.
- 完全独立实现是否会发现本实验未覆盖的其他输入歧义.

- 中断恢复: 未评估.
