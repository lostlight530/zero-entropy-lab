# Ballast 日记录 2026-08-12

类型: 每日专题
主题: 退避等待跨越任务有效期后的过期重试

## 研究问题

服务端返回临时不可用并要求延迟重试后, 如果任务自身的业务有效期先于下一次允许重试时间到期, 仅遵守 `Retry-After`、只设置通用传输重试 deadline、以及在生产重试入口同时核对任务 `valid_until` 三条路径中, 哪一种能避免服务恢复后仍执行已经失效的旧任务

本题不重复 2026-08-09 的基准漂移研究. 8 月 9 日由其他操作推进权威 generation, 今天固定业务状态不发生并发变化, 只让时间推进穿过任务自身有效期, 用于区分传输层可重试与语义层仍有执行权限

## 来源依据

查询日期为 2026-08-12

- [RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html) 发布于 2022-06. Section 10.2.3 定义 `Retry-After` 为用户代理在后续请求前应等待的时间, 值可以是 HTTP-date 或接收响应后的秒数. 该字段描述服务端建议的等待边界, 没有声明等待结束后原业务意图仍然有效
- [Google Cloud IAM Retry failed requests](https://docs.cloud.google.com/iam/docs/retry-strategy) 访问于 2026-08-12. 文档建议对安全可重试请求使用带 jitter 的截断指数退避, 并明确在调用方选择的 `deadline` 后停止重试. 对 `409 ABORTED` 还要求重新执行完整 read-modify-write 序列而不是只重放 write, 说明重试策略必须保留调用上下文而不是只看一次失败响应
- [AWS Builders' Library: Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) 访问于 2026-08-12. 文档讨论 retries and side effects, late arriving requests 与 same client request ID, different intent, 强调可安全去重并不等于所有迟到请求仍保持相同业务语义

三个来源分别提供 HTTP 等待语义, 调用方 retry deadline 和幂等重试语义边界. 它们支持把传输恢复条件与任务有效期分开研究, 但不直接证明本轮受控夹具的结果

## 可证伪假设

- H1: 只要严格等待 `Retry-After` 后服务已经恢复, 原请求就可以继续执行, 因为服务器已经给出重新尝试时间
- H2: 设置一个通用 transport retry deadline 足以约束过期操作, 只要下一次尝试仍早于该 deadline 就可以发送
- H3: 任务有效期是独立于传输重试窗口的执行前置条件, 每次生产重试入口都必须在发送副作用前重新核对 `valid_until`, 超过任务有效期时即使服务已经恢复也应停止写入

如果服务恢复后 H1 路径没有执行越过任务有效期的请求, H1 的风险解释被削弱

如果 transport deadline 仍为有效状态时 H2 路径能识别任务已经语义过期并停止写入, H2 的不足解释被削弱

如果 H3 在 `t > valid_until` 时仍执行副作用, H3 被推翻

## 控制条件

- 初始请求在逻辑时钟 t=0 发出, 服务返回 `503` 与确定性 `Retry-After`
- 任务业务有效期固定为 `valid_until=5`
- 通用 transport retry deadline 固定为 `10`, 它只限制客户端最长重试时间, 不代表任务业务有效期
- 正常基线使用 `Retry-After=2`, 下一次尝试同时早于任务有效期与 transport deadline
- 故障注入使用 `Retry-After=8`, 服务在 t=8 已恢复, 但任务在 t=5 已失效, transport deadline 仍到 t=10 才结束
- `retry_after_only` 路径只等待服务器建议时间后继续发送
- `transport_deadline` 路径只检查 t 是否超过通用 retry deadline
- `task_bound` 路径在生产重试入口先比较 t 与任务 `valid_until`, 过期则返回 `task_expired` 且不发送副作用
- 已应用请求使用稳定 intent key 去重, 用于检查同输入重新经过同一生产入口是否产生第二次写入
- 实验只使用 Python 标准库与系统已有 awk, 文件只位于本轮系统临时目录, 文本显式 UTF-8

## 实验设计

1. 正常基线让三条路径在 t=0 收到 503 与 `Retry-After=2`, 在 t=2 重新经过生产入口
2. 记录重试结果、写入次数、最终 value 与任务有效期
3. 故障注入让三条路径收到 `Retry-After=8`, 不改变任何业务状态或 intent 内容, 只推进逻辑时间
4. 在 t=8 假定服务已经恢复并会对到达请求返回 200
5. 比较三条路径是否在 `valid_until=5` 已过期后仍执行副作用
6. 对成功路径的相同 intent 重新经过同一生产入口, 检查幂等记录是否阻止第二次写入
7. 生产夹具输出固定九列 UTF-8 TSV 事件轨迹, 不向独立验证器输出内部期望布尔值
8. 独立 Python 进程根据事件时间与 `valid_until` 重建 stale retry 条件, 检查基线、故障注入、最终 value 与写入计数
9. 使用 awk 第二实现独立解析相同 TSV, 重新计算故障场景中的 stale accept 与最终写入
10. 完整夹具运行三次并比较事件摘要与验证分类

## 原始观测

三次完整生产轨迹均包含 23 个事件行, SHA-256 都为 `63f2145b5ab40c9ac37c4de694fe75e304813558975c0f0c68d0e9d397c0a6bd`

| 场景 | 路径 | t=下一次尝试 | 结果 | 最终 value | 写入次数 |
| --- | --- | ---: | --- | --- | ---: |
| 正常基线 | 仅 Retry-After | 2 | 200_applied | effect-applied | 1 |
| 正常基线 | transport deadline | 2 | 200_applied | effect-applied | 1 |
| 正常基线 | task-bound | 2 | 200_applied | effect-applied | 1 |
| 任务有效期已过 | 仅 Retry-After | 8 | 200_applied | effect-applied | 1 |
| 任务有效期已过 | transport deadline | 8 | 200_applied | effect-applied | 1 |
| 任务有效期已过 | task-bound | 8 | task_expired | initial | 0 |

正常基线中三条路径在 t=2 都仍满足 `t <= valid_until=5`, 因而各执行 1 次副作用

故障注入中服务在 t=8 已恢复, 所以弱路径都得到传输级成功. 但 t=8 已超过任务 `valid_until=5`, `retry_after_only` 和 `transport_deadline` 仍各执行 1 次已经失效的副作用

`transport_deadline` 路径在 t=8 仍满足 `t <= 10`, 因而证明通用重试 deadline 只能限制重试总时长, 不能自动替代更短的任务语义有效期

`task_bound` 路径在发送副作用前返回 `task_expired`, 最终 value 保持 `initial`, 写入为 0

对基线中已成功的相同 intent 再次经过同一生产入口时, 三条路径都返回 `already_applied`, 写入数仍为 1, 没有产生第二次副作用

## 独立验证

独立 Python 验证器不调用生产重试函数, 只读取 TSV 中的 scenario、path、t、event、result、writes、valid_until、retry_deadline 与 value

验证器直接按 `RETRY` 事件的 `t > valid_until` 推导语义过期, 并从 FINAL 事件检查最终 value 与写入数

三次 Python 独立进程验证均通过, 重新得到:

- 正常基线三条路径最终写入都为 1
- 故障场景 `retry_after_only` stale accept 为 1
- 故障场景 `transport_deadline` stale accept 为 1
- 故障场景 `task_bound` stale accept 为 0
- `task_bound` 故障场景最终写入为 0, value 为 `initial`
- 基线同输入生产入口重放没有增加写入

awk 第二实现不使用 Python 对象模型, 独立解析同一 TSV 后得到 `AWK_PASS`, 对两条弱路径各识别 1 次过期副作用, 对 task-bound 路径识别 0 次

验证仍共享同一事件语义合同与生产夹具生成的轨迹, 因此不是独立真实服务验证

## 强反例

强反例刻意让服务端条件全部恢复正常

在 t=8 时服务已经健康, `Retry-After=8` 已满足, transport retry deadline=10 也尚未结束, 稳定 intent key 还能保证同一请求最多执行一次

如果只验证 HTTP 成功、等待是否足够、retry deadline 和幂等写入次数, 两条弱路径都会被判定为成功

但任务自身 `valid_until=5` 已经过去 3 个逻辑时间单位. 该副作用即使只执行一次也已经不再属于当前有效任务

这证明 `at-most-once` 只能约束重复次数, 不能证明一次副作用仍然应该发生. 同样, `Retry-After` 只规定最早何时可重试, 不能充当任务授权续期

## 路径比较

| 路径 | 等待服务建议 | transport deadline | 任务有效期复核 | 过期场景写入 | 结果质量 |
| --- | --- | --- | --- | ---: | --- |
| 仅 Retry-After | 是 | 否 | 否 | 1 | 传输成功但语义过期 |
| transport deadline | 是 | 是 | 否 | 1 | 在客户端重试窗口内仍执行过期任务 |
| task-bound retry | 是 | 是 | 是 | 0 | 过期后安全停止 |

弱路径操作最少, 但减少一次语义检查换来错误副作用

transport deadline 增加全局重试边界, 能防止无限重试, 但如果它比任务业务有效期更长, 仍允许已经失效的旧任务执行

task-bound 路径在真正发送重试前增加一次任务有效期比较, 本轮故障场景少执行 1 次过期副作用

## 暂时结论

状态为观察

在本次确定性时间模型中, 传输层已经恢复、服务器建议等待已经满足、通用 retry deadline 未到和请求幂等都不足以证明旧任务仍应执行

任务自身有效期必须作为独立执行前置条件带到每次生产重试入口. 如果等待跨过该有效期, 更安全的行为是以 0 写入停止, 由当前任务状态决定是否生成新的有效意图

今天只形成一个新的受控实验单元, 三次同条件重复不计为三个独立实验, 不升级为候选或发现

## 复验条件

使用真实返回 429 或 503 与 `Retry-After` 的服务复验, 将任务有效期设置为短于与长于服务器等待时间两组

## 事实分层

### 已验证事实

- 三次 23 行生产轨迹 SHA-256 完全一致
- 正常基线三条路径均在任务有效期内成功写入 1 次
- `Retry-After=8` 故障场景中两条弱路径都在 `valid_until=5` 之后执行 1 次副作用
- task-bound 路径在相同场景返回 `task_expired`, 写入 0, value 保持 initial
- Python 独立进程验证三次通过, awk 第二实现通过
- 已完成相同 intent 重新经过同一生产入口时没有产生第二次写入
- 本轮系统临时实验目录在验证后清理

### 基于证据的推断

- retry backoff 与 transport deadline 解决的是何时以及多久继续尝试, 不自动回答任务在该时点是否仍有业务执行权限
- 幂等可以把重复副作用压到一次, 但不能把已经过期的一次副作用变成有效完成
- 对有业务有效期的 Agent 任务, 有效完成需要把时间有效性与当前意图一起带到最终副作用入口

### 未验证事项

- 真实服务对 429 与 503 的 Retry-After 组合语义
- HTTP-date 与客户端墙钟偏差
- 多层 SDK 自动重试隐藏的实际等待时长
- 队列延迟、断网恢复与 suspend/resume 对任务有效期的影响
- 不可逆远端副作用是否能在服务端共同验证 intent identity 与 task validity
