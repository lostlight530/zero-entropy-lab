## 研究问题

当 selector-bound persistent-state task 要求所有当前匹配 `worker` 的成员都为 `marked` 时, 如果恢复器持有一份曾经准确的 UID membership cache, 但 watch 历史发生 gap 或旧 resourceVersion 已不可连续验证, 是否可以把旧 cache 继续当作 current membership proof

关键窗口为 `CACHE rv10 {A1,B1 marked} -> watch gap -> authority changes to {A1,C1 clean} at rv12 -> recovery -> completion`

进一步构造同名重建 `B1 -> B2 clean`, 检查 cache 中 logical member 与旧 UID 都曾真实存在时, history continuity 丢失是否仍会导致零写入假完成

## 来源依据

查询日期为 2026-09-01

- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) 说明 watch 可以从指定 resourceVersion 继续变化流, 但服务器不需要永久保留旧版本; 请求过旧 resourceVersion 时可能返回 HTTP 410 Gone, 客户端必须容忍该情况. 同一文档还警告某些 watch 初始化语义可能返回任意陈旧数据. 适用边界是 Kubernetes API collection/watch semantics, 不直接证明 Ballast 夹具结果
- [PostgreSQL Transaction Isolation](https://www.postgresql.org/docs/16/transaction-iso.html) 说明 Read Committed 下两个连续 SELECT 可以因为并发提交而看到不同 snapshot, 并把 phantom 类异常与 predicate 结果集合变化联系起来. 适用边界是 PostgreSQL transaction visibility, 不直接等价于任意 Agent membership cache

两个独立官方来源共同支持有限前提: 曾经正确的集合观察不能在缺少 continuity 或 current snapshot guarantee 时自动续期为当前集合事实

外部资料不证明本轮 false completion、effect_count 或恢复结果

## 可证伪假设

- H1: membership cache 曾经由准确 UID set 构成, 即使 watch history 出现 gap, 只要 cache 内所有成员仍满足任务就可以直接 completion
- H2: watch gap 或 410 Gone 可以等价解释为 no membership change
- H3: history continuity 无法证明时, membership evidence 应降级为 unknown, 重新建立 authoritative current set 后才能恢复 completion decision
- H4: 每次都重新读取 current membership 并把 current set 绑定 protected completion 可以避免依赖旧 watch continuity, 但操作数高于连续 watch 正常路径
- H5: gap 实际没有遗漏任何 membership change 时, safe relist 应增加读取成本但不能制造无效 effect
- H6: completed replay 不能替代 `membership changed during watch gap -> completion missing -> production entry replay` 窗口

H1 的反证条件是旧 cache 中 A1/B1 都 marked, 但 authority 已变为 A1/C1 且 C1 clean, 路径仍 completed 且 effect_count=0

H2 的反证条件是 gap 被标记为 no-change 后继续 cache predicate, 最终 current contract 为 false

H3 的反证条件是 gap-safe path 把 gap 标记 unknown 后仍不 relist current membership, 或必要 effect 前没有重新确认 current permission

## 控制条件

- historical prior-effect evidence 固定为 hit, 本轮只研究 current completion membership evidence
- current execution permission 的 intent、holder、valid_until、task status、credential capability 与 approval binding 固定有效
- task semantics 固定为所有 current `worker` members 的 value 都必须为 `marked`
- 初始 authority 与 local cache 都是 A=`uid-A1`, B=`uid-B1`, value=marked, local revision=1, collection revision=10
- missed-replace-clean 场景在 gap 中把 B1 替换为 C1 clean, authority revision 推进到 12
- missed-recreate-clean 场景在 gap 中把 B1 替换为同名 B2 clean, authority revision 推进到 12
- gap-no-change 场景产生相同 gap 信号但 authority 保持 rv10 与 A1/B1 marked
- `cache-trust` 不区分 watch continuity, 直接信任旧 cache predicate
- `gap-as-nochange` 显式收到 gap 但把它解释为 no change
- `gap-safe-relist` 把 gap 分类为 unknown, authoritative relist current set, 必要 effect 前重新确认 current permission
- `current-list-protected` 每次从 authority 建立 current membership, 并比较 collection revision 与完整 member identity/state 后再 protected completion
- completed replay 从已持久化 completion 重新进入同一 production entry
- 夹具只使用 Python 标准库与系统 awk

## 实验设计

## 强反例

第一强反例攻击 stale membership cache

cache 的 A1/B1 UID set 在 rv10 时确实权威且两者都 marked, 但 watch gap 内 B1 被 C1 clean 替换后继续使用旧 cache, 形成 effect_count=0 的 false completion

第二强反例攻击 same-name recreation

旧 cache 不是伪造数据, 它真实保存 uid-B1; 问题在于 history continuity 已失效, authority 已经是同名 uid-B2 clean, cache-trust 仍错误完成

反方向强反例是 gap-no-change

gap 信号存在但没有任何 membership change, gap-safe-relist 必须允许重新建立 current truth 并 effect_count=0, 不能把 unknown 永久等价成任务失败

## 路径比较

- cache-trust 操作最少, 但把曾经正确的 membership 事实错误续期为 current truth
- gap-as-nochange 显式观察到 evidence gap 仍把它降格为 no-change, 两类 missed-change 都形成零写入假完成
- gap-safe-relist 在 gap 时多一次 current read, changed case 只恢复当前 clean member, no-change case 不产生 effect
- current-list-protected 不依赖旧 watch continuity, 但正常路径也需要 current list 与 protected compare
- 本轮强路径改进来自 evidence classification 与 current-state re-establishment, 不是来自减少操作数

## 暂时结论

证据状态为观察

本轮支持把 dynamic membership evidence 的 freshness 进一步拆成两个问题: 当前 witness 身份内容是否正确, 以及从该 witness 到当前 decision boundary 的历史 continuity 是否仍可证明

曾经准确的 UID set 在 watch gap、过期 resourceVersion 或无法证明的 history hole 后只能作为历史事实, 不能自动续期为 current membership proof

history continuity 无法建立时, 本轮 strong path 将 membership evidence 分类为 unknown, 通过 authoritative relist 或等价 current snapshot 重新建立 current relevant set, 再进入 protected completion

该结论没有改变现行 METHOD 的稳定规则, 因为 METHOD 已要求 current membership witness、coherent snapshot/freshness 与 protected decision boundary共同成立

## 事实分层

### 已验证事实

- 受控夹具中 cache rv10 的 A1/B1 membership 在初始时刻真实存在且两者均 marked
- watch gap 后 authority 变为 A1/C1 clean 或 A1/B2 clean 时, cache-trust 与 gap-as-nochange 都得到 completed=1、contract_ok=0、effect_count=0
- gap-safe-relist 将 gap 分类为 unknown, relist authoritative current membership 后只恢复当前 clean member, 最终 contract_ok=1
- 两个 changed case 中必要 effect 前均存在 `PERMISSION:1`
- gap-no-change 中 safe relist 增加读取但 effect_count=0
- completed replay 四条路径均 effect_count=0
- producer 三次轨迹 SHA-256 完全一致, Python verifier 3/3 PASS, awk PASS, producer/verifier py_compile PASS

### 基于证据的推断

- historical membership correctness 与 current membership freshness 是不同证明义务
- history continuity 无法证明时, 把 gap 解释为 no change 会把 unknown 错降为 current truth
- authoritative relist 可以重新建立当前集合事实, 但 relist 之后到 completion 的变化仍需要 protected boundary 处理
- whole dynamic-set completion 仍需要 task semantics、current membership identity、member state freshness 与 completion boundary共同成立

- 尚未在真实 Kubernetes API 触发 410 Gone 并运行 controller recovery
- 尚未测量真实 watch cache、relist、quorum read 或数据库 snapshot 的延迟与成本
- 尚未覆盖跨区域 watch、compaction、分页、bookmark、network partition 与高 churn 组合
- 尚未证明任意 local cache 在何种 lease 或 session contract 下可以安全继续使用
