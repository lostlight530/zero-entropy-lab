## 研究问题

当 selector-bound persistent-state task 要求所有当前匹配 `worker` 的成员都为 `marked` 时, 如果恢复器持有一份曾经准确的 UID membership cache, 但 watch 历史发生 gap 或旧 resourceVersion 已不可连续验证, 是否可以把旧 cache 继续当作 current membership proof

关键窗口为 `CACHE rv10 {A1,B1 marked} -> watch gap -> authority changes -> recovery -> completion`

本次同日修正进一步攻击 `GAP -> authoritative relist -> membership changes again -> completion` 窗口, 检查 relist 是否只是重新建立某一时点的 current truth, 而不是自动关闭 relist 到 completion 之间的 TOCTOU

## 来源依据

查询日期为 2026-09-01

- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) 说明 watch 可以从指定 resourceVersion 继续变化流, 但服务器不需要永久保留旧版本; 请求过旧 resourceVersion 时可能返回 HTTP 410 Gone, 客户端必须容忍该情况. 文档还明确警告 `Get State and Start at Any` 语义可能返回任意陈旧数据. 适用边界是 Kubernetes API collection/watch semantics, 不直接证明 Ballast 夹具结果
- [PostgreSQL Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html) 说明 Read Committed 下两个连续 SELECT 可以因为并发提交而看到不同 snapshot, 且 phantom read 属于 predicate 结果集合变化相关的并发异常. 适用边界是 PostgreSQL transaction visibility, 不直接等价于任意 Agent membership cache

两个独立官方来源共同支持有限前提: 曾经正确的集合观察不能在缺少 continuity 或 current snapshot guarantee 时自动续期为当前集合事实, 单次重新读取也只证明其自身观察时点

外部资料不证明本轮 false completion、effect_count 或恢复结果

## 可证伪假设

- H1: membership cache 曾经由准确 UID set 构成, 即使 watch history 出现 gap, 只要 cache 内所有成员仍满足任务就可以直接 completion
- H2: watch gap 或 410 Gone 可以等价解释为 no membership change
- H3: history continuity 无法证明时, membership evidence 应降级为 unknown, authoritative relist 可以重新建立 relist 时点的 current set
- H4: authoritative relist 本身不足以保护后续 completion; 如果 relist 后 membership 再变化, 未绑定 protected compare 的路径仍可能 false complete
- H5: 每次从 authority 建立 current membership, 并把 collection revision 与完整 member identity/state 绑定到 protected completion, 可以检测 relist 后 membership drift
- H6: gap 实际没有遗漏任何 membership change 时, safe relist 应增加读取成本但不能制造无效 effect
- H7: completed replay 不能替代 `membership changed during watch gap or after relist -> completion missing -> production entry replay` 窗口

H1 的反证条件是旧 cache 中 A1/B1 都 marked, 但 authority 已变为 A1/C1 且 C1 clean, 路径仍 completed 且 effect_count=0

H2 的反证条件是 gap 被标记为 no-change 后继续 cache predicate, 最终 current contract 为 false

H4 的反证条件是 relist 真实看到 A1/B1 marked, 随后 C1 clean 在 completion 前加入 selector, 路径仍 completed=1、contract_ok=0

H5 的反证条件是同一 post-relist insertion 发生后 protected path 没有检测 compare conflict, 或恢复 effect 前没有重新确认 current permission

## 控制条件

- historical prior-effect evidence 固定为 hit, 本轮只研究 current completion membership evidence
- current execution permission 的 intent、holder、valid_until、task status、credential capability 与 approval binding 固定有效
- task semantics 固定为所有 current `worker` members 的 value 都必须为 `marked`
- 初始 authority 与 local cache 都是 A=`uid-A1`, B=`uid-B1`, value=marked, local revision=1, collection revision=10
- missed-replace-clean 在 gap 中把 B1 替换为 C1 clean, authority revision 推进到 12
- missed-recreate-clean 在 gap 中把 B1 替换为同名 B2 clean, authority revision 推进到 12
- gap-no-change 产生相同 gap 信号但 authority 保持 rv10 与 A1/B1 marked
- post-relist-insert-clean 让 relist 先真实看到 rv10 A1/B1 marked, 随后在 completion 前加入 C1 clean 并推进到 rv11
- `cache-trust` 不区分 watch continuity, 直接信任旧 cache predicate
- `gap-as-nochange` 显式收到 gap 但把它解释为 no change
- `gap-safe-relist` 把 gap 分类为 unknown 并 authoritative relist current set, 但不把 relist witness 与 completion commit 放进同一 protected boundary
- `current-list-protected` 从 authority 建立 current membership, 并把 collection revision 与完整 member identity/state 绑定 protected completion; compare conflict 后重新读取 current set, 必要 effect 前重新确认 current permission
- completed replay 从已持久化 completion 重新进入同一 production entry
- 夹具只使用 Python 标准库与系统 awk

## 强反例

第一强反例攻击 stale membership cache

cache 的 A1/B1 UID set 在 rv10 时确实权威且两者都 marked, 但 watch gap 内 B1 被 C1 clean 替换后继续使用旧 cache, 形成 effect_count=0 的 false completion

第二强反例攻击 same-name recreation

第三强反例攻击 plain relist

反方向强反例是 gap-no-change

## 路径比较

- cache-trust 操作最少, 但把曾经正确的 membership 事实错误续期为 current truth
- gap-as-nochange 显式观察到 evidence gap 仍把它降格为 no-change, 两类 pre-relist missed-change 和 post-relist insertion 都可能 false complete
- gap-safe-relist 正确把 gap 分类为 unknown, 能修复已经发生于 relist 之前的 membership drift, 但它只是恢复步骤, 不是最终完成边界
- current-list-protected 把 current collection revision 与完整 member identity/state 绑定 protected completion; post-relist membership drift 会触发 conflict 与重新协调
- 本轮改进来自 evidence classification、current-state re-establishment 与 protected completion 的组合, 不是来自减少操作数

## 暂时结论

证据状态为观察

本轮支持把 dynamic membership evidence 拆成三个连续义务: historical witness 是否曾经正确, witness 到 current observation 的 history continuity 是否可证明, current observation 到 completion commit 是否仍由 protected boundary 约束

watch gap 或过旧 resourceVersion 使旧 witness 降级为 historical fact; authoritative relist 可以重新建立某一时点的 current membership, 但不能自动保护 relist 之后发生的变化

因此 gap recovery 的完整受控路径应写成 `gap -> unknown -> authoritative relist/current snapshot -> protected membership/member-state compare -> completion`, 需要执行恢复 effect 时仍先重新确认 current execution permission

该修正与现行 METHOD 一致, METHOD 已明确写明普通 relist 只能移动最终观察时点, membership 在 relist 后仍可变化时必须把 membership witness 与相关 member identity/freshness 放入 protected decision boundary

### 基于证据的推断

- historical membership correctness、history continuity 与 completion-bound freshness 是三个不同证明义务
- gap 被解释为 no change 会把 unknown 错降为 current truth
- authoritative relist 重新建立的是 relist 线性化点上的 current truth, 不是 relist 后到 completion 的永久证明
- dynamic-set completion 仍需要 task semantics、current membership identity、member state freshness 与 predicate-complete protected completion 共同成立
