## 研究摘要

本轮研究 EndpointSlice ready=false 与 serving/terminating 的语义分离, 并检验单纯 ready=false 或 snapshot serving=false 能否证明无旧连接、精确 UID 和受保护完成, 仅为合成模型研究, 不声称真实集群实证

## 研究问题

旧 Pod 处于 terminating 且 ready=false 时, 是否仍可能 serving=true 或存在未完成连接, 以及同名重建、watch 断档、额外 endpoint 和伪造 receipt 能否使弱路径错误报告 drain COMPLETE

## 来源依据

- [Kubernetes EndpointSlices](https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/) 2026-11-02 核验, ready 通常为 serving 且非 terminating 的快捷条件, publishNotReadyAddresses 是例外, 终止中的 serving endpoint 仍可能接收特定 Service 流量
- [Kubernetes API EndpointConditions](https://kubernetes.io/docs/reference/kubernetes-api/discovery/endpoint-slice-v1/) 2026-11-02 核验, ready/serving/terminating 三字段的合同及 nil 语义, 仅限 API surface
- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) 2026-11-02 核验, list/watch resourceVersion、410 Gone 与连续性限制
- [HAProxy Master CLI](https://www.haproxy.com/documentation/haproxy-runtime-api/master-cli/) 2026-11-02 核验, 旧 worker 停止新流量后仍可处理已有连接, 这是不同 publisher 对 draining 与 in-flight 区分的独立例证, 不能当作 Kubernetes proxy 的实现证明
- [etcd API guarantees](https://etcd.io/docs/v3.5/learning/api_guarantees/) 2026-11-02 核验, watch 可能延迟且受 compaction 历史窗口限制, 属独立项目的存储合同, 不等同于 Kubernetes apiserver end-to-end proof
