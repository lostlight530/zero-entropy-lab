## 研究问题

旧 effect 已经发生且 completion 未持久化, recovery 时用于 approval 的 signing capability 已被撤销, 恢复器如果只看 current revoked 状态, 是否会把撤销前合法发生的 historical effect 错误判为无效

反方向问题是如果恢复器只比较 effect_time 与 revocation notice time, 是否会在 key compromise 的 invalidity time 早于 revocation processing time 时错误接受一个已经落入失效区间的 historical effect

本轮把 historical occurrence、revocation processing time、historical invalidity boundary 与 current new-effect authorization 分开

## 来源依据

查询日期为 2026-09-15

- [RFC 5280 Internet X.509 Public Key Infrastructure Certificate and CRL Profile](https://www.rfc-editor.org/rfc/rfc5280.html) 的 5.3.2 说明 invalidity date 表示已知或怀疑 private key compromised 或 certificate otherwise invalid 的日期, 并且该日期可以早于 CRL entry 的 revocation date. 本轮只采用有限命题: revocation 被处理或发布的时间不一定等于实际失效边界, 不把 X.509 certificate 直接等同于人工 approval
- [NIST SP 800-57 Part 1 Revision 5](https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-57pt1r5.pdf) 的 key revocation guidance 要求通知包含 key identity、revocation date/time 与 reason, 并指出某些撤销原因下可以继续认可撤销前签名, 而 key compromise 情况需要单独评估撤销通知日期以前的信息. 本轮只采用有限命题: revocation reason 与历史时点会影响旧签名证据的处理, current revoked 状态不能自动决定全部历史

两个独立权威来源共同支持有限设计前提: revocation notification、effective invalidity 与 historical verification 是可分离的时间事实. 外部来源不证明本地 valid_completion、effect_total 或 PASS

## 可证伪假设

- H1: recovery 时只要 signing capability 当前 revoked, historical HIT 就应一律判为 invalid completion
- H2: historical effect_time 早于 revocation processing time 即足以证明旧 approval 在 effect 时有效
- H3: ordinary revocation 可以允许撤销前的 historical effect 保持有效, 但 compromise backdating 需要使用更早的 invalidity boundary
- H4: prior HIT 的 historical authorization 与 authoritative MISS 后是否允许新 effect 必须分开判断
- H5: completed replay 必须从 production entry 重入并保持零新增 effect

H1 的反证条件是 revoked-after-effect: effect_time=90, privilege withdrawal revocation_time=100, recovery_time=110. current-revocation-stop 会 false reject, 但 historical boundary 仍位于 effect 之后

H2 的反证条件是 compromise-backdated-hit: effect_time=95, revocation_time=105, invalidity_time=90. revocation-date-only 会认为 95<105 因而接受, 但 invalidity boundary 已经早于 effect

## 控制条件

- historical effect identity 固定为 `op-115`
- active-hit: prior=HIT, effect_time=90, capability active
- revoked-after-effect: prior=HIT, effect_time=90, reason=privilegeWithdrawn, revocation_time=100
- compromise-backdated-hit: prior=HIT, effect_time=95, reason=keyCompromise, revocation_time=105, invalidity_time=90
- miss-current-valid: prior=MISS, current capability active, current approval valid
- miss-current-revoked: prior=MISS, current capability revoked, approval bit 仍为 valid, 用于检查 revoked state 是否仍独立阻止新 effect
- unknown-compromise: prior=UNKNOWN, historical effect fields 存在但不得把它们当成 occurrence proof
- completed-replay 已有持久化 completion, 从相同 production entry 重入
- occurrence-only 对 HIT 只使用 occurrence
- current-revocation-stop 对 HIT 只使用 recovery 时的 current revoked 状态
- revocation-date-only 对 HIT 只比较 effect_time 与 revocation processing time
- invalidity-bound-reconcile 对 keyCompromise 优先使用 invalidity_time, 对其他撤销原因使用 revocation_time, 对 MISS 独立检查 current revoked 与 current approval
- fixture 只使用 Python 标准库与系统 awk

## 强反例

第一强反例攻击 current revoked 足以否定 historical completion

revoked-after-effect 的 effect_time=90 早于 ordinary privilege withdrawal revocation_time=100. current-revocation-stop 在 recovery_time=110 看到 revoked 后产生 false negative completion, 说明 current capability state 不能自动追溯成为历史边界

第二强反例攻击 revocation notice time 足以定义 historical validity

compromise-backdated-hit 的 effect_time=95 虽早于 revocation_time=105, 但 invalidity_time=90. revocation-date-only 仍 valid_completion=1, 说明处理撤销的时间可以晚于实际失效边界

反方向强反例是 miss-current-valid

prior effect 确认未发生且 current capability 未撤销、current approval 有效时, stronger path 应允许一次必要 effect, 不能因为强调 historical revocation evidence 而永久零写入

## 路径比较

- occurrence-only 操作最少, 可以恢复 ordinary historical HIT, 但会把 compromise-backdated stale effect 错误认作 valid completion
- current-revocation-stop 同样简单, 对 compromise case 保守停止, 但也把 ordinary revocation 前合法 historical effect 一并错误否定
- revocation-date-only 能区分 ordinary revocation 前后的 effect, 但在 compromise invalidity_time 早于 revocation processing time 时产生 false positive
- invalidity-bound-reconcile 根据 revocation reason 选择 historical boundary, 对 HIT 重建历史授权, 对 MISS 独立检查 current capability 与 current approval
- stronger path 在 HIT 场景增加 reason 与 historical boundary 检查, 但同时消除方向相反的 false negative 与 false positive
- 本地 fixture 与 Python 进程耗时不外推真实 PKI、HITL 或远端 authorization service 性能

## 暂时结论

证据状态为观察

本轮支持 H3、H4、H5, 推翻 H1、H2

current revoked 是 recovery-time capability fact, 不能默认追溯成为 historical effect-time authorization fact

同样, revocation processing time 也不一定是实际 invalidity boundary. 当 authority 明确提供更早的 compromise invalidity time 时, historical verification 需要绑定该边界而不是只看撤销被处理的时间

prior HIT 的 occurrence、historical authorization boundary 与 prior MISS 后 new-effect current permission 继续是不可互相替代的恢复事实

### 基于证据的推断

- current revocation、revocation processing time 与 effective invalidity boundary 应被视为不同时间事实
- historical completion recovery 需要根据 revocation reason 与可用 historical invalidity evidence 选择正确边界, 而不是机械使用 current state 或 latest revocation timestamp
- 外部标准与本地 fixture 在方向上相容, 但本轮没有证明任何真实 PKI、HITL 或 authorization service 的具体恢复行为

### 未验证事项

- 未在真实 CRL、OCSP、JWKS、HITL issuer 或外部 effect sink 中复现
- 未验证 authority 的 invalidity evidence 自身如何获得独立可信时间与防篡改保证
- 未验证 invalidity time 缺失、冲突或事后修订时的安全分类
- 未验证 key compromise 与 ordinary administrative revocation 在具体业务 approval policy 中是否采用相同历史语义
