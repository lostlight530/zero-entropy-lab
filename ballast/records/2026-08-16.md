# Ballast 日记录 2026-08-16

类型: 每日专题
主题: effect identity 在同名目标重建后的实体别名风险

## 研究问题

Agent 在 unknown outcome 恢复中已经能够查询 effect identity 时, 如果副作用目标资源被删除后以相同名称重建, 只绑定 idempotency key、绑定 key 加规范化 action、以及绑定 key 加 action 加目标实体 incarnation, 哪一种能够避免把旧资源上的历史副作用误认成新资源已经完成, 同时仍保持同一实体上的未知结果重放不重复执行.

本题承接 2026-08-15 的 effect identity 恢复结论, 但攻击对象从“有没有 effect evidence”推进到“这份 evidence 指向哪一个真实实体”. 当前执行权限与 effect evidence 继续分开处理. 重建场景中假定任务已经重新取得对新实体的当前执行权限, 本轮只验证旧 receipt 能否证明新实体上的后置条件已经满足.

## 来源依据

查询日期为 2026-08-16.

- [Stripe API Reference: Idempotent requests](https://docs.stripe.com/api/idempotent_requests) 访问于 2026-08-16. 文档说明同一 idempotency key 的后续请求会复用第一次执行结果, 但会比较后续请求参数与原始请求参数, 参数不同会报错以避免误用. 文档同时说明 key 在至少 24 小时后可被清理, 清理后复用会形成新的请求. 适用边界是 Stripe API 的幂等缓存合同, 不直接定义任意业务对象的实体身份.
- [Amazon EC2: Ensuring idempotency in API requests](https://docs.aws.amazon.com/ec2/latest/devguide/ec2-api-idempotency.html) 访问于 2026-08-16. 文档要求 client token 不应复用于其他 API 请求, 同 token 且相同参数的成功请求重试不会再次执行, 同 token 但参数变化会返回 `IdempotentParameterMismatch`. 适用边界是 EC2 支持 client token 的 API, 不自动证明业务资源名称足以区分实体生命周期.
- [Kubernetes: Object Names and IDs](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/) 访问于 2026-08-16. 文档说明同一种资源在同一 namespace 中同名对象同一时刻唯一, 但删除后可以创建同名新对象, 每个对象都有跨集群生命周期唯一的 UID, UID 用于区分相似实体的历史实例. 适用边界是 Kubernetes object identity, 不等价于外部支付或消息系统 receipt.

Stripe 与 AWS 独立支持“幂等身份应与同一请求语义绑定而不是只看 token”, Kubernetes 提供“同名资源可跨生命周期复用, 需要独立 UID 区分实体 incarnation”的公开对象模型. 三者共同支持本轮实验的身份边界设计, 但不直接证明实验结果可以推广为通用 exactly-once.

## 可证伪假设

- H1: effect receipt 只绑定 idempotency key 已经足够. 只要 key 曾经出现过, 后续恢复都可以认为副作用已经完成.
- H2: effect receipt 绑定 key 与规范化 action 已经足够. 只要资源名称和 payload 未变化, 历史 receipt 就能证明当前目标已经完成.
- H3: effect receipt 还必须绑定真正承载副作用的目标实体 incarnation. 同一 UID 上未知结果重放应去重, action 变化应拒绝旧 receipt, 同名资源重建为新 UID 后旧 receipt 不应证明新实体已经完成.

如果 key-only 在 action 改变后不误报已生效, H1 的风险解释被削弱.

如果 key-action 在同名资源重建后不误报已生效, H2 的实体别名解释被削弱.

如果 key-action-target 在同一 UID unknown-result replay 中产生第二次写入, 或只改变无关 metadata 就失去已有 receipt, H3 被推翻.

## 控制条件

- idempotency key 固定为 `task-42`.
- 逻辑资源名称固定为 `job-a`.
- 初始实体 UID 为 `uid-old`, payload 为 `marked`, 无关 metadata 为 `note=n0`.
- `key-only` receipt identity 只包含 task key.
- `key-action` receipt identity 包含 task key、目标名称与 payload.
- `key-action-target` receipt identity 再包含目标 UID.
- action drift 场景只把 payload 从 `marked` 改为 `sealed`, UID 不变.
- recreate 场景先在 `uid-old` 上完成历史副作用, 再删除并创建同名 `job-a` 的 `uid-new`. 任务已经按当前授权重新绑定到 `uid-new`, 因此本场景只测试历史 receipt 是否还能证明当前实体完成.
- metadata-only 强反例只把同一 UID 的 `note` 从 n0 改为 n1.
- unknown outcome 场景在 effect receipt 与业务写入完成后、task completion 持久化前中断, 随后重新进入同一 production entry.
- completed replay 先正常完成再重新进入同一入口.
- 实验只使用 Python 标准库、系统 awk 与系统临时目录, 输出 UTF-8 TSV.

## 实验设计

1. 正常基线分别执行三条路径, 验证同一实体上都恰好写入一次并保存完成状态.
2. 构造同一实体 unknown outcome, 在 effect 已写入但 completion 缺失时重放生产入口, 检查是否出现第二次写入.
3. 预置旧 action receipt 后修改 payload, 再以相同 key 恢复, 比较 key-only 是否错误把旧 action 当作新 action 已完成.
4. 预置 `uid-old` 上的历史 receipt, 删除目标并以相同名称创建 `uid-new`, 同时把当前任务授权绑定到 `uid-new`, 再进入生产入口.
5. 检查 key-only 与 key-action 是否因为旧 receipt 而零写入跳过 `uid-new`, 以及 key-action-target 是否能把新 UID 当作新的 effect identity.
6. 构造强反例, 只改变同一 UID 上的无关 metadata, 检查 UID 绑定是否会因无关变化过度失效.
7. 正常完成后重放 production entry, 检查三条路径是否都保持零新增写入.
8. producer 输出固定 11 列 TSV, 不输出预设通过布尔值.
9. 独立 Python verifier 只依据场景、路径、结果、写入计数、当前实体值、UID、receipt 数与 completion 状态重建期望.
10. awk 第二实现只复核正常基线、action drift、同名重建与 metadata-only 强反例.
11. 完整 producer 执行三次并比较轨迹 SHA-256.

正常基线和同一实体 unknown outcome 中三条路径都保持单次写入. 因此更强 identity 并没有破坏同一真实实体上的安全重放.

action drift 中 key-only 直接返回 `effect_already_applied` 并把 completion 恢复为完成, 但当前目标值仍为 clean, 形成零新增写入的错误完成. 两个 action-bound 路径都返回 `identity_mismatch`, 没有把旧 payload receipt 当作新 payload 的证据.

同名目标重建是本轮决定性故障. key-only 与 key-action 都看到历史 receipt 后返回 `effect_already_applied`, 当前 `uid-new` 的值仍为 clean. key-action-target 因当前任务已经绑定新 UID, 不复用旧 UID receipt, 对 `uid-new` 执行一次 `marked` 并保存第二个独立 receipt. 表中的总写入 2 包含旧实体上的 1 次历史写入与新实体上的 1 次当前写入.

metadata-only 强反例中目标 UID 不变, 三条路径都复用已有 receipt 并保持总写入 1. 因而 key-action-target 不是把任意对象 revision 都纳入 effect identity, 不会仅因无关 note 变化而重复执行.

## 独立验证

producer 与 Python verifier 为两个独立文件, verifier 不导入 producer, 不读取 producer 内部期望值或成功布尔值.

Python verifier 从 TSV 独立检查:

- 三条正常基线都恰好写入一次并完成.
- 同一 UID unknown outcome 重放均不产生第二次写入.
- action drift 时 key-only 错误恢复 completion 且当前值仍为 clean, 两个 action-bound 路径返回 identity mismatch.
- 同名资源重建为 `uid-new` 后 key-only 与 key-action 错误跳过, key-action-target 对新实体产生必要的第二个跨生命周期 effect.
- metadata-only 变化没有让 UID 绑定路径重复写入.
- completed replay 三条路径均保持单次写入.

三次独立 Python verifier 均返回 `PY_VERIFIER_PASS`.

第二验证器使用 awk 独立解析相同 TSV, 对正常基线、同名目标重建、action drift 和 metadata-only 强反例返回 `AWK_PASS`.

producer 与 verifier 均通过 `py_compile`. 两个验证器仍共享 TSV 字段语义、场景标签与同一 Python 运行时文件系统, 也没有访问真实 Stripe、EC2 或 Kubernetes API, 因此不能视为完全外部独立验证.

## 强反例

第一, action identity 不是 effect identity 的充分条件. `job-a + marked` 在资源删除重建前后完全相同, 但旧 receipt 对应 `uid-old`, 不能证明 `uid-new` 已经收到副作用. key-action 在这个场景与 key-only 一样发生零写入假完成.

第二, 绑定 target incarnation 也不能退化成绑定整个对象 revision. 只改变同一 UID 的无关 `note` 时, key-action-target 继续把旧 receipt 识别为同一真实副作用, 没有重复执行. 这说明 effect identity 需要覆盖承载副作用的实体身份, 但不应无差别吸收所有 metadata.

第三, unknown outcome 去重本身并没有失败. 同一 UID 上三条路径都能在 effect 已发生而 completion 缺失时恢复为完成且保持单次写入. 这反过来证明本轮问题不是“有没有 receipt”, 而是 receipt 的语义绑定范围是否足够.

## 路径比较

| 路径 | 同一实体 unknown outcome | action drift | 同名实体重建 | metadata-only | completed replay | 正常基线操作数 |
| --- | --- | --- | --- | --- | --- | ---: |
| key-only | 单次写入 | 错误跳过 | 错误跳过 | 正确去重 | 零新增写入 | 5 |
| key-action | 单次写入 | 冲突停止 | 错误跳过 | 正确去重 | 零新增写入 | 5 |
| key-action-target | 单次写入 | 冲突停止 | 对新实体执行一次 | 正确去重 | 零新增写入 | 5 |

三条路径在正常基线中操作数相同, 因而本轮没有“强路径明显更慢”的受控证据. 差异来自 identity 语义, 不是减少操作数.

key-only 同时在 action drift 与实体重建中把旧 receipt 当作当前完成证据.

key-action 修复了参数漂移, 但同名资源生命周期切换时仍发生 ABA 风格实体别名.

key-action-target 在本轮夹具中同时保留同一实体 unknown outcome 去重、action mismatch 安全停止、实体重建后必要执行与 metadata-only 不过度失效.

## 暂时结论

本轮观察支持把 `authoritative effect identity` 进一步拆成至少两层: 规范化 action identity 与真实 target incarnation identity.

只有 key 或 key 加逻辑名称与 payload, 仍可能在资源删除重建、名称复用或其他实体 reincarnation 后把历史副作用误认成当前完成. 在本轮受控条件下, 把 receipt 绑定到目标 UID 能区分两个历史实体, 同时不受同一实体无关 metadata 变化影响.

该结论不代表所有副作用都存在 Kubernetes 式 UID, 也不代表任意 UID 绑定都足够. 真实系统仍需要确定哪个远端稳定身份真正对应副作用承载对象, 以及 identity 的保留期、删除语义、跨区域作用域与授权重新绑定规则.

证据状态为观察, 不升级为候选或发现.

## 复验条件

后续至少需要在实质不同条件下复验以下边界:

- effect receipt 有 TTL, TTL 到期后旧 key 被重新使用, 检查 key 生命周期与业务任务生命周期错位.
- 目标是可变成员集合或多资源副作用, 检查单一 target UID 是否不足以表达完整 effect set.
- 真实外部服务提供 request ID 或 resource ID, 检查 receipt 与最终资源身份是否能够权威关联.
- 删除与重建发生在 effect 提交和 receipt 持久化之间, 检查时序证据能否区分 effect 属于旧实体还是新实体.
- 新实体当前执行权限没有重新授权时, 必须与本轮“已重新绑定当前权限”的夹具区分, 不能因 effect identity 缺失自动获得执行许可.

## 事实分层

### 已验证事实

- 18 行受控轨迹三次执行 SHA-256 完全一致.
- Python verifier 三次通过, awk 第二验证器通过, producer 与 verifier 均通过 Python 编译检查.
- key-only 在 action drift 场景返回已生效并恢复 completion, 但当前值仍为 clean.
- key-only 与 key-action 在同名资源从 `uid-old` 重建为 `uid-new` 后都错误跳过新实体必要副作用.
- key-action-target 在同一场景对 `uid-new` 执行一次必要写入, 同一 UID unknown outcome 与 metadata-only 场景均保持单次写入.

### 基于证据的推断

- effect evidence 要证明“这个副作用已经发生”, 不能只证明“某个逻辑名称和 payload 曾经发生过类似副作用”.
- 对具有可重建生命周期的目标, stable target incarnation 是 effect identity 的候选必要组成部分.
- current execution permission 与 prior effect evidence 仍是两个独立问题. 旧 receipt 失配只说明不能据此判定已完成, 不自动授予再次执行权限.

### 未验证事项

- 未验证真实 Stripe、EC2、Kubernetes 或其他外部 sink 的端到端行为.
- 未验证 receipt TTL、跨区域 scope、资源迁移、批量多实体 effect、级联删除与恢复.
- 未验证目标 UID 与业务语义之间是否存在额外 alias 或代理层.
- 未验证 effect receipt 与远端业务副作用能否原子持久化.
