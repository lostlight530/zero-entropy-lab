## 研究摘要

本轮从 2026-09-19 的 current token authority继续推进到 sender-constrained token的 request-time proof boundary.

核心问题是 token已经绑定正确 sender key时, key possession本身是否足以授权新的非幂等 request, 还是仍需要把 proof绑定到当前 method/URI并提供 replay freshness.

受控实验比较四条路径: bearer-active, key-bound, request-bound, replay-aware.

## 研究问题

一个 active 且绑定正确 sender key的 access token, 如果请求 proof被复制到不同 endpoint, 不同 method或同一 request再次提交, protected resource能否仅凭 token active和 key match安全地产生新的 effect.

进一步问题是 request binding与 replay detection是否是两个不可坍缩的 permission dependency.

## 来源依据

查询日期 2026-09-20.

- RFC 9449 https://www.rfc-editor.org/rfc/rfc9449.html 定义 DPoP proof-of-possession. DPoP proof绑定 HTTP method和 URI, 使用唯一 jti与 iat, resource server需要检查 proof与 access token及当前请求的一致性. RFC还明确讨论 proof replay并给出 server-provided nonce作为进一步降低 replay机会的机制.
- RFC 8705 https://www.rfc-editor.org/rfc/rfc8705.html 定义 mutual-TLS certificate-bound access tokens. Protected resource必须确认当前 TLS client certificate与 token绑定的 certificate匹配, 使 stolen bearer token不能由不持有对应 private key的一方直接使用.

两个标准共同支持 sender constraint是 bearer token之上的 proof-of-possession边界, 但 DPoP与 mTLS的 request freshness机制并不相同. 本轮 fixture只建模 DPoP式 request proof replay, RFC 8705只作为独立 sender-binding机制的交叉来源, 不把 mTLS等同于 DPoP.

外部标准不证明本地 fixture PASS或真实 resource server replay cache行为.

## 可证伪假设

- H1 active bearer token足以授权新 effect, sender proof不构成独立 dependency.
- H2 token与正确 sender key绑定后, key match足以拒绝 request-context replay.
- H3 method/URI request binding足以拒绝同一 proof在相同 request上的重复提交.
- H4 request binding加 proof replay witness可在本轮 modeled boundary拒绝 wrong key, wrong URI, wrong method, stale proof与 duplicate proof.
- H5 prior HIT即使 current proof invalid仍只做 historical reconciliation, 不产生新 effect.
- H6 prior UNKNOWN即使 current proof valid仍保持 safe stop.

## 暂时结论

状态为观察.

H1, H2, H3被推翻.

H4, H5, H6在本地 modeled boundary内得到支持.

sender constraint不是单一布尔属性. 至少在 DPoP式 request proof中, current permission需要区分 token active, proof-of-possession key, request method/URI binding, proof temporal freshness与 replay witness.

正确 sender key只能证明 presenter拥有对应 key, 不能单独证明这个 proof属于当前 request或此前没有被接受.

本轮不声称 replay cache是唯一实现方式. RFC 9449 nonce等机制可以进一步缩小 replay机会, 真实部署还需要处理 distributed replay state与 clock skew.

## AGI-scale action-integrity relevance

长期自主 Agent可能持有 sender-constrained delegated credential并跨多个 tool endpoint重复恢复同一 action.

如果系统只验证 credential holder identity而不验证 request identity与 proof replay状态, stolen proof, duplicated dispatch或 recovery race仍可能产生重复 effect.

因此 delegated authority需要与 delivery correctness和 replay safety在 effect boundary组合, 但 historical occurrence仍必须独立重建.
