## 研究摘要

本轮从 2026-09-19 的 current token authority推进到 sender-constrained token的 request-time proof boundary. 比较 bearer-active, key-bound, request-bound, replay-aware四条路径, 同时保持 prior HIT与 UNKNOWN的历史证据边界.

## 研究问题

active且绑定正确 sender key的 token, 如果 proof被复制到不同 endpoint, method或同一 request再次提交, protected resource能否仅凭 token active和 key match安全产生新的 effect. request binding与 replay detection是否是两个不可坍缩的 permission dependency.

## 来源依据

查询日期 2026-09-20.

- RFC 9449 https://www.rfc-editor.org/rfc/rfc9449.html 定义 DPoP. Proof绑定 HTTP method和 URI, 使用 jti与 iat, resource server需要检查 proof与 access token及当前请求的一致性. RFC还讨论 proof replay与 server-provided nonce.
- RFC 8705 https://www.rfc-editor.org/rfc/rfc8705.html 定义 mTLS certificate-bound access token. Protected resource必须确认当前 TLS client certificate与 token绑定 certificate匹配.

两者都支持 proof-of-possession不是普通 bearer语义, 但 DPoP与 mTLS的 request freshness机制不同. 本轮只建模 DPoP式 request proof replay, 不把 mTLS等同于 DPoP. 外部标准不证明本地 fixture PASS或真实 replay cache行为.

## 可证伪假设

- H1 active bearer token足以授权新 effect.
- H2正确 sender key足以拒绝 request-context replay.
- H3 method/URI request binding足以拒绝同一 proof重复提交.
- H4 request binding加 replay witness可拒绝 wrong key, wrong URI, wrong method, stale proof与 duplicate proof.
- H5 prior HIT即使 current proof invalid仍只做 historical reconciliation.
- H6 prior UNKNOWN即使 current proof valid仍保持 safe stop.

## 强反例

wrong-uri与 wrong-method中 token active且 sender key正确, key-bound仍产生 new-effect, request-bound拒绝. 这推翻 H2.

duplicate-proof-same-request中 token, key, method, URI与 proof freshness都正确, 但同一 jti已经接受. request-bound仍产生 new-effect, replay-aware拒绝. 这推翻 H3.

## 路径比较

bearer-active遗漏 sender possession, request context与 replay freshness, 产生 5 false accept. key-bound修复 wrong-key但仍有 4 false accept. request-bound修复 target与 temporal freshness但 duplicate proof仍 false accept. replay-aware在 modeled boundary内 0 false accept / 0 false reject.

HIT与 UNKNOWN四路径均 new_effect=0, current sender proof不覆盖 historical occurrence classification.

## 暂时结论

状态为观察. H1, H2, H3被推翻. H4, H5, H6在本地 modeled boundary内得到支持.

sender constraint不是单一布尔属性. DPoP式 current permission至少区分 token active, proof-of-possession key, request method/URI binding, proof temporal freshness与 replay witness. 正确 sender key不能单独证明 proof属于当前 request或此前没有被接受.

本轮不声称 replay cache是唯一实现方式. RFC 9449 nonce可以进一步缩小 replay机会, 真实部署还需处理 distributed replay state与 clock skew.

## AGI-scale action-integrity relevance

长期自主 Agent可能持有 sender-constrained delegated credential并跨 tool endpoint恢复同一 action. 只验证 credential holder identity而不验证 request identity与 proof replay状态, duplicated dispatch或 copied proof仍可能产生重复 effect. Historical occurrence仍需独立重建.
