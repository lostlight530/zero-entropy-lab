## 研究问题

当人工批准的是一个动态 selector 在批准时解析出的具体 effect set 时, 只绑定规范化 action、只绑定批准时成员 UID 集合、绑定 whole-global revision、以及绑定成员 identity 加 approval-relevant policy 的相关状态投影, 哪一种能够在暂停恢复后避免把旧批准扩展到未经批准的新成员或已改变授权属性的成员

本轮重点攻击两个不同 under-fencing 窗口

`APPROVE {uid-A1,uid-B1 standard} -> selector 加入 uid-C1 -> RESUME -> EFFECT`

以及

`APPROVE uid-B1 policy=standard -> same uid-B1 policy=restricted -> RESUME -> EFFECT`

第二个窗口专门检查 member identity set 完全不变时, identity-only approval binding 是否仍会漏掉 approval-relevant attribute drift

## 来源依据

查询日期为 2026-09-04

- [NIST SP 800-162 Guide to Attribute Based Access Control](https://www.nist.gov/publications/guide-attribute-based-access-control-abac-definition-and-considerations-1), NIST 页面标注发布于 2019-02-25. 文档把授权定义为对 subject、object、requested operation 与可选 environment attributes 按 policy 进行求值. 本轮只采用有限命题: 授权结论可以依赖对象与动作属性, 因而对象集合或授权相关属性改变时, 旧授权不能仅凭 action 字符串自动视为仍适用. 适用边界是 ABAC 定义与设计考虑, 不直接证明 Ballast 夹具结果
- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/), 当前官方文档说明 collection response 与 watch 使用 resourceVersion 表示集合状态并跟踪后续 create、delete、update. 本轮只采用有限命题: selector 对应的对象集合是可随时间变化的权威状态, 需要可核验的集合版本或等价 current membership evidence. 适用边界是 Kubernetes API collection semantics, 不代表任意 selector 系统都自动具有相同事务保证
- [OpenAI Agents SDK Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/), 当前官方文档说明默认 approval 按具体 tool call ID 保存, pending approval 暴露 tool name 与 arguments, paused RunState 可以恢复. 本轮只采用有限命题: approval 有具体 call/action 身份与暂停恢复生命周期. SDK 本身不证明应用层动态 target set 或 target policy 在等待期间保持不变

NIST、Kubernetes 与 OpenAI 来自三个不同权威体系. 它们共同支持实验建模所需的三个边界: approval 对具体操作有对象, 动态对象集合会变化, paused approval 可以在之后恢复. 外部资料不证明本轮 unauthorized effect 数量或路径优劣

## 可证伪假设

- H1: 只要规范化 action 没变, 已批准动作可以在恢复时直接作用于 selector 当前解析出的所有成员
- H2: approval 绑定规范化 action 与批准时 member UID set 已经足够, 只要成员 identity set 未变就可以继续执行
- H3: whole-global revision 可以阻止相关状态漂移, 但会把只改变无关 metadata 的场景也判为 approval conflict
- H4: relevant projection 需要同时覆盖 action、当前 effect-set identity 与每个成员真正影响本次授权或语义的属性; 任一相关字段改变都拒绝旧批准, 无关 metadata 改变不应单独使批准失效
- H5: completed replay 不能替代 approval 后 relevant state drift 到 effect 之间的 production-entry replay

H1 的反证条件是 approval 时只有 A1/B1, 恢复前 C1 新加入 selector, action-only 仍对 C1 产生 effect

H2 的反证条件是 A1/B1 UID set 完全不变, 但 B1 policy 从 standard 变为 restricted, identity-bound 路径仍对 B1 产生 effect

H3 的 over-fencing 反例是只推进 selector 外 note metadata, whole-global path 拒绝而 relevant projection 仍能执行原批准 effect set

H4 的反证条件是新成员、同名重建或 policy drift 后 relevant projection 仍执行旧批准, 或无关 metadata 变化时也无条件停止

## 控制条件

- approval contract 明确限定为批准时解析出的 current worker effect set, 不授权未来加入 selector 的成员
- approval 时 action 固定为 `mark selector=worker`
- 初始成员为 job-a=`uid-A1` 与 job-b=`uid-B1`, 两者 policy 都为 standard, value 都为 clean
- approval-time UID set 固定为 `uid-A1,uid-B1`
- approval-relevant member projection 固定为 `(uid-A1,standard),(uid-B1,standard)`
- 初始 global revision 为 10
- join-standard 在 approval 后加入 job-c=`uid-C1`, policy=standard, global revision 推进到 11
- same-name-recreate 在 approval 后把 job-b 从 `uid-B1` 重建为同名 `uid-B2`, policy=standard, global revision 推进到 11
- policy-restricted 保持 `uid-B1` identity 不变, 仅把 policy 从 standard 改为 restricted, global revision 推进到 11
- irrelevant-metadata 只修改与本次批准无关的 note, global revision 也推进到 11
- action-only 只比较规范化 action
- membership-id-bound 比较规范化 action 与 current UID set
- global-revision-bound 比较规范化 action 与 whole-global revision
- relevant-projection-bound 比较规范化 action 与 current `(UID, policy)` projection
- completed replay 从已持久化 completion 重新进入同一 production entry
- 夹具只使用 Python 标准库与系统 awk

## 实验设计

1. 四条路径运行 normal baseline
2. approval 后新增 standard 成员 C1, 检查旧 approval 是否错误扩展到新 effect target
3. approval 后同名重建 B1 为 B2, 检查 logical selector 与名称不变时 identity drift 是否被识别
4. approval 后保持 UID set 不变, 只把 B1 policy 从 standard 改为 restricted, 专门攻击 identity-only projection
5. 只改变无关 metadata, 检查 whole-global revision 的 over-fencing
6. completed replay 重新进入原 production entry, 检查新增 effect 为 0
7. producer 输出 scenario、path、completed、new_effect、unauthorized_effect、approval_contract_ok、ops、result、event_order 与 global revision

## 强反例

第一强反例攻击 action-only approval

人工批准时 effect set 真实只有 A1/B1, 但 C1 在等待期间加入 selector. 恢复时 action 文本完全相同, action-only 把旧批准扩展到 C1 并产生未经批准 effect

第二强反例攻击 identity-only approval projection

A1/B1 UID set 在批准前后完全相同, 但 B1 policy 已从 standard 变为 restricted. membership-id-bound 仍认为 approval applicable 并对 B1 写入, 证明只覆盖 identity set 仍可能漏掉真实授权依赖

第三个反方向强反例攻击 whole-global over-fencing

只改变与本次批准无关的 note metadata 时, global revision 仍变化并拒绝旧批准, 但 relevant projection 的 action、UID set 与 policy 均未变化, 可以安全执行原 effect set

这三个反例共同限制结论: approval freshness 需要的是 task-specific relevant authority projection, 既不能只绑定 action 或 identity, 也不能为了省事把所有无关状态都纳入 approval identity

## 路径比较

- action-only 操作最少, 但 join、recreate 与 policy drift 都可能把旧批准用于 approval contract 外的 effect
- membership-id-bound 能识别成员加入与 incarnation replacement, 但 policy-restricted 证明 identity set 完整仍不等于 authorization dependency 完整
- global-revision-bound 在本轮相关变化中都安全停止, 但 irrelevant-metadata 也发生额外 conflict
- relevant-projection-bound 覆盖 action、current member identity 与 policy, 三类相关变化都零写入停止, 只改变无关 metadata 时继续执行原批准 effect set
- 本轮有效改进来自依赖集合完整性, 不是来自减少操作数

## 暂时结论

证据状态为观察

本轮支持把 approval relevant projection 的完整性再拆成 `action identity + current effect-set identity + approval-relevant member attributes`

对于动态 selector, 只保存 selector 文本或批准时 action 不能证明恢复时 effect set 仍是人批准的对象. 即使进一步绑定 UID set, 仍需要覆盖会改变成员授权或动作语义的相关字段

whole-global revision 可以提供更强围栏, 但无关 metadata 强反例说明它可能牺牲有效执行而没有增加本轮 task-specific 结果质量

该观察与现行 METHOD 的 stable rule 一致: relevant projection 必须显式列出依赖字段并保守覆盖全部授权与语义前提, 无法证明完整时应使用更强围栏或安全停止

### 基于证据的推断

- approval action identity、effect-set identity 与 approval-relevant member attributes 是不同证明义务
- dynamic selector 的 current effect set 属于 approval applicability 的相关状态, 不能只靠 selector 字符串推断未变化
- member identity proof 不能替代授权属性 freshness proof
- task-specific relevant projection 可以减少 whole-global revision 的 over-fencing, 前提是依赖字段覆盖完整
