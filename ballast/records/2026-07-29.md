# Ballast 日记录 2026-07-29

类型: 每日专题
主题: 去重保留窗口过期后的迟到恢复

## 研究问题

非幂等操作已经提交但确认丢失, 恢复发生在服务端去重记录过期之后时, 直接重放、只按关联标识查询、以及绑定原请求与当前意图的权威结果核对, 哪条路径能阻止重复副作用和错误跳过.

## 来源依据

查询日期为 2026-07-29.

- [RFC 9110 第 9.2.2 节](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) 发布于 2022-06, 说明客户端不应自动重试非幂等请求, 除非已知其语义实际幂等或能够确认原请求未应用.
- [AWS Builders' Library: Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) 为官方工程资料, 说明迟到请求需要保留窗口, 调用者提供的唯一请求标识应与创建资源关联, 同一标识承载不同参数时应返回不匹配. 页面没有显示稳定更新日期.
- [Stripe Idempotent requests](https://docs.stripe.com/api/idempotent_requests) 为当前官方 API 文档, 说明去重键在至少 24 小时后可被删除, 删除后复用旧键会形成新请求, 同时要求保留期内比较参数以阻止错误复用. 页面没有显示稳定更新日期.
- [Stripe advanced error handling](https://docs.stripe.com/error-low-level#idempotency) 进一步限定网络错误后的安全重试依赖同一键、同一参数和 24 小时窗口, 并建议使用本地标识关联后续协调得到的对象.

RFC 给出重试边界, AWS 说明迟到请求和意图标识, Stripe 明确展示有限保留窗口. 来源没有证明所有服务都使用 24 小时窗口, 本实验中的 24 小时只是可控边界.

## 可证伪假设

路径 A 在逻辑时间 0 提交后丢失确认, 逻辑时间 25 的服务端去重记录已经过期, 仍直接使用旧键重放. 预计服务把它当作新请求并创建第二个资源.

路径 B 只查询关联标识, 看到一个由其他请求和不同意图创建的资源后直接跳过. 预计操作数为 0, 但当前任务没有有效完成.

路径 C 在请求前持久保存关联标识、原请求标识和意图摘要, 迟到恢复时查询权威资源, 只有恰好一个资源同时匹配三项约束且不存在冲突时才跳过重放. 预计恢复与同输入重放都写入 0, 独立验证通过.

如果旧键过期后仍不产生第二个资源, 路径 B 能识别冲突, 或路径 C 重新提交、遗漏冲突或验证失败, 对应假设被推翻.

## 控制条件

- 三条路径使用相同关联标识、请求标识和原始意图.
- 原始意图是创建数量 1 的受控资源, 冲突意图只把数量改为 2.
- 服务端去重窗口固定为 24 个逻辑小时, 首次提交在时间 0, 迟到恢复在时间 25.
- 确认丢失发生在资源与去重记录写入之后.
- 每条路径使用隔离的资源、去重与本地意图状态.
- 独立验证器在另一 Python 进程中读取最终资源、本地意图和调用时当前意图.
- 全部样本位于系统临时目录, 使用 UTF-8 并在退出前清理.

## 实验设计

1. 路径 A 首次提交一个资源并丢失响应, 在去重记录过期后使用同一请求键重放.
2. 路径 B 预置一个关联标识相同但请求标识和意图不同的资源, 让只按标识查询的恢复器决定是否重放.
3. 路径 C 首次提交并丢失响应, 删除已过期去重记录, 再按关联标识、原请求和意图三项查询权威资源.
4. 对路径 C 再执行一次同输入恢复, 检查远端调用与状态写入.
5. 独立验证三条最终状态, 从最终资源重新计算精确匹配数和冲突数.
6. 检查五项机制断言、完整耗时与临时目录清理.

## 原始观测

- 路径 A 首次调用和迟到重放都返回 applied, 远端调用 2 次, 资源数 2, 状态写入 4 次.
- 路径 A 的独立验证发现精确匹配资源为 2, 以 exact_resource_count_mismatch 拒绝, 退出状态为 1.
- 路径 B 查询到 1 个相同关联标识并返回 skipped_existing_marker, 远端调用与状态写入均为 0.
- 路径 B 的独立验证发现精确匹配为 0、冲突资源为 1, 以 exact_resource_count_mismatch 和 conflicting_marker_resource 拒绝, 退出状态为 1.
- 路径 C 首次远端调用 1 次, 服务状态写入 2 次, 去重过期维护写入 1 次.
- 路径 C 恢复与同输入重放都返回 verified_existing_effect, 两次恢复写入合计为 0.
- 路径 C 的独立验证确认精确匹配为 1、冲突为 0, 退出状态为 0.
- 五项机制断言全部通过, 有效完成为真, 系统临时目录清理通过.
- 验证后的有效耗时为 333.723 毫秒.
- 提交前两次复验保持相同资源计数、验证判断、零写入重放与清理结果, 验证后有效耗时分别为 249.868 和 277.939 毫秒.

首次准备执行在默认系统临时根创建目录后受到 ACL 拒绝, 未进入机制实验. 该精确残留被清理, 随后以同一系统临时根完成正式实验, 环境失败不计入路径证据.

## 独立验证

`verify_retention_expiry.py` 在独立进程中回读资源清单与请求前持久保存的本地意图, 使用调用时传入的当前意图重新计算摘要. 它要求相同关联标识下恰好一个资源同时匹配原请求标识与当前意图, 并拒绝任何同标识冲突资源.

验证器不读取恢复器的完成状态、查询命中数或服务端去重记录. 独立性限制是两条路径仍共享 JSON 合同、意图字段形状和 SHA-256, 且权威资源仍由同一受控文件模拟.

## 强反例

路径 B 只进行一次读取, 没有重试和写入, 并且确实查到一个关联标识相同的资源, 因而看起来比其他路径更快且副作用更少. 该资源实际由其他请求创建, 数量也与当前意图不同.

这个状态推翻了查询到一个同标识资源就足以安全跳过的解释. 低操作数只有在资源身份和当前意图都通过验证时才构成改进.

## 路径比较

| 路径 | 迟到远端调用 | 恢复写入 | 最终精确资源 | 冲突资源 | 独立验证 |
| --- | ---: | ---: | ---: | ---: | --- |
| 过期请求键直接重放 | 1 | 2 | 2 | 0 | 拒绝 |
| 只按关联标识跳过 | 0 | 0 | 0 | 1 | 拒绝 |
| 原请求加意图绑定核对 | 0 | 0 | 1 | 0 | 通过 |

路径 A 产生重复副作用. 路径 B 操作最少但结果质量失败. 路径 C 增加权威查询和内容比较, 保持一个有效资源, 恢复与重放均零写入. 本实验没有分别测量每条路径的独立耗时, 不能声称路径 C 绝对更快.

## 暂时结论

状态为观察.

在本次有限去重窗口实验中, 旧请求键在过期后不再提供重复保护. 只按关联标识查询会把不同请求和不同意图的资源误认为当前结果. 将关联标识、原请求标识和当前意图一起用于权威结果核对后, 迟到恢复与重放保持零写入.

该实验为既有当前状态绑定发现增加保留窗口边界证据, 但本机制单次出现, 不新建候选或长期发现.

## 复验条件

使用真实远端 API 或持久服务复验不同保留期, 注入去重过期与资源索引延迟、结果查询暂时不可用、资源删除后迟到请求、多个精确匹配资源和服务端协调结果晚到.

使用不同实现的验证器或不同意图规范化规则攻击共享假设. 权威查询不能证明唯一结果时必须安全停止.

## 事实分层

### 已验证事实

- 去重记录过期后重放同一键创建了第二个资源.
- 只按关联标识的路径对不同请求和不同意图的资源错误跳过.
- 绑定原请求与当前意图的路径确认现有资源后没有重交, 同输入重放写入 0.
- OpenAI 开发者站点的当前三轮探测成功, 但不能回溯证明触发时段没有异常.

### 基于证据的推断

- 去重窗口需要成为恢复决策的显式输入, 不能把曾经安全的请求键视为永久保护.
- 迟到恢复的权威查询必须证明资源属于当前请求和当前意图, 不能只证明某个相似资源存在.

### 未验证事项

- 真实服务在去重过期、索引延迟和后续协调同时发生时的行为.
- 本地意图记录丢失或被污染时能否安全恢复.
- OpenAI Developer Forum 出现 staff only 文案的准确 URL、身份状态、起止时间、范围和根因.
