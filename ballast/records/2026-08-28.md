# Ballast 日记录 2026-08-28

类型: 每日专题
主题: target reincarnation 后 completion compare 的 identity binding

## 研究问题

当 persistent-state task 已经读取满足的 current postcondition, 并准备通过 atomic compare-and-complete 保存 completion 时, 如果目标在读取后被删除重建, 新实体复用相同逻辑名称、相同 value 与相同 local revision, 只比较 revision 是否仍会把新 incarnation 误当成旧 observation 的延续

本轮组合 8 月 25 日的 completion commit TOCTOU 与 8 月 27 日的 target incarnation alias, 改变的故障位置是 compare-and-complete 自身的条件集合

关键窗口为 `read uid-B1 value=marked revision=1 -> delete and recreate same name as uid-B2 value=marked revision=1 -> atomic completion compare -> commit`

## 来源依据

查询日期为 2026-08-28

- [Kubernetes Object Names and IDs](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/) 说明对象删除后可以重新创建同名对象, 而 UID 用于区分对象身份. 适用边界是 Kubernetes object identity, 不直接证明任意 Agent state store 都具有 UID
- [etcd API](https://etcd.io/docs/v3.6/learning/api/) 说明 transaction 是 atomic If/Then/Else, compare 可以检查 value、version、create revision 或 mod revision, 全部 compare 在同一事务中原子应用. 适用边界是 etcd key-value transaction, 不直接提供业务 target incarnation 语义

两个独立官方来源共同支持一个有限设计前提: 原子 compare 能保护它实际比较的字段, 但业务实体 identity 是否属于 compare contract 仍需由任务语义决定

本轮用受控夹具检验 revision-only atomic compare 在 incarnation replacement 下是否存在 observation under-binding

## 可证伪假设

- H1: 只要 completion commit 使用 atomic revision compare, 就足以关闭 read 到 completion 之间的 target replacement 窗口
- H2: 如果 local revision 只在 incarnation 内有意义, incarnation-bound task 的 atomic compare 需要同时绑定 target UID 与 revision
- H3: identity compare 不应机械外推到 selector-bound task, 如果任务语义接受任何当前同名实体且 current predicate 满足, UID 变化本身不应强制失败
- H4: completed replay 不能替代 replacement-before-commit 窗口测试

H1 的反证条件是旧 B1 与新 B2 都使用 revision 1, revision compare 成功但旧任务错误继承 completion

H2 的反证条件是 UID 已变化时 UID+revision compare 仍提交 completion, 或同一 incarnation 仅发生合法 value/revision 变化时不能识别 conflict

H3 的反方向强反例让任务 contract 改成 logical selector, B2 同名且仍满足 `marked`, contract-aware compare 应允许 completion

## 控制条件

- historical effect evidence 已经确认, 本轮只研究 current completion read 到 completion commit 的并发边界
- current execution permission 的 relevant world state、intent、holder、valid_until、task status、credential capability 与 approval binding 固定有效
- incarnation-bound contract 明确要求当前目标仍是 `uid-B1`
- selector-bound contract 只要求逻辑目标名仍为 `job-b` 且 current value 为 `marked`
- 初始目标统一为 name=`job-b`, UID=`uid-B1`, value=`marked`, local revision 1
- delete/recreate 后目标变成 name=`job-b`, UID=`uid-B2`, value=`marked`, local revision 重新从 1 开始
- `no-compare` 读取后直接保存 completion
- `revision-compare` 在 completion commit 时原子比较 local revision, 但不比较 UID
- `contract-aware-compare` 对 incarnation-bound task 原子比较 UID+revision, 对 selector-bound task 比较 logical selector 与 current predicate
- 同一 incarnation 被合法反转到 `clean` 时 revision 推进, compare conflict 后强路径重新读取 current state, 再次执行 effect 前重新确认 current execution permission
- unrelated metadata 只改变 note, 不改变 UID、value 或 local revision
- completed replay 重新进入同一 production entry 并经过 completed short circuit
- 实验只使用 Python 标准库与系统 awk, 不访问真实 Kubernetes、etcd 或外部 effect sink

## 实验设计

1. 三条路径运行 normal baseline, 验证原 target 不变时都能保存 completion
2. 注入 same-incarnation-reversal, 读取后把 B1 从 marked 改为 clean 并推进 revision, 检查 compare path 是否冲突并在 effect 前重新确认 permission
3. 注入 recreate-revision-reuse, 读取旧 B1 后删除并重建 B2, 保持 value=marked 且 local revision 复用 1, 检查 revision-only compare 是否错误成功
4. 注入 unrelated-metadata, 检查 contract-aware compare 是否避免无关字段 over-fencing
5. 注入 selector-recreate 作为反方向强反例, 任务语义改为 logical selector, 检查强路径是否按 contract 而不是机械 UID binding 判断
6. 运行 completed-replay, 让已完成任务重新进入 production entry, 检查新增 effect 是否为 0
7. producer 输出固定 TSV, 保存 scenario、contract、path、completion、UID、value、revision、effect_count、ops 与 event order
8. 完整 producer 运行三次并比较 TSV SHA-256
9. 独立 Python verifier 不导入 producer, 从 event order 与最终权威状态重建判定, 检查 revision reuse 假完成、UID+revision conflict、permission-before-effect 与 selector 反例
10. awk 第二实现独立复核三个决定性组合, producer 与 verifier 执行 `py_compile`

Python verifier 独立检查

- 18 个 scenario/path 组合完整且唯一
- normal 与 completed-replay 三条路径均 completed=1 且新增 effect=0
- same-incarnation-reversal 中 no-compare 在 authoritative value=clean 时仍 completed=1, 两条 compare path 都先 conflict, 再记录 permission check 与 exactly one recovery effect
- recreate-revision-reuse 中 no-compare 与 revision-compare 都在 authoritative UID=`uid-B2` 时 completed=1, revision-compare event order 明确记录 `COMPARE_REV:1`

## 强反例

第一强反例是 local revision reuse

incarnation-bound task 已经读取旧 B1 r1, B2 重建后也从 r1 开始, revision-only atomic compare 因而完全成功, 但 task target identity 已经失效

这推翻 H1, 说明 atomic compare 只对被比较字段提供保护, 不会自动补齐遗漏的业务 identity dependency

第二个反方向强反例是 selector-recreate

如果 task contract 本来只要求任何当前 `job-b` 满足 marked, B2 替代 B1 后仍可以有效完成

contract-aware path 因此没有机械要求 UID 相等, 而是按 task semantics 选择 compare identity

该反例限制 H2 的适用边界, 防止把 incarnation binding 错误推广到 logical-selector task

unrelated-metadata 同样保持 completion, 说明强路径没有退化成 whole-object global fencing

completed replay 全部安全, 仍不能替代真实 replacement-before-commit 窗口

revision-compare 相比 no-compare 已能关闭同一 incarnation 内的普通 state drift, 但在 local revision 可以随实体重建复用时仍 under-bind observation

contract-aware-compare 没有增加正常路径操作数, 改进来自 compare set 与任务真实依赖对齐, 不是减少操作或增加重试

## 暂时结论

本轮推翻 H1, 支持有边界的 H2 与 H3, 并再次支持 H4

对于明确绑定具体 target incarnation 的 completion contract, `compare-and-complete` 的 compare set 必须覆盖 incarnation identity 与该 incarnation 内的 freshness evidence

revision equality 不能跨 incarnation 解释, 即使 compare 本身是原子的也一样

如果 task contract 是 logical selector 而不是 concrete incarnation, compare identity 应按 selector semantics 构造, 不能机械加入 UID 导致错误 over-fencing

因此可靠性来自 `task semantics -> relevant identity set -> atomic compare-and-complete` 的连续绑定, 而不是“使用了 CAS”这一局部事实

## 事实分层

### 已验证事实

- 受控模型中旧 `uid-B1` 与新 `uid-B2` 可以具有相同 logical name、相同 marked value 与相同 local revision 1
- revision-compare 在 replacement-before-commit 场景记录 compare success 并 completed=1, 当前 authoritative target 已是 uid-B2
- contract-aware-compare 在 incarnation-bound contract 下记录 UID+revision conflict, completed=0 且没有对 B2 执行旧任务 effect
- same-incarnation-reversal 中 revision compare 与 contract-aware compare 都检测 conflict, 在 recovery effect 前重新确认 current permission
- selector-bound contract 下 contract-aware compare 接受满足当前 selector predicate 的 B2
- completed replay 三条路径新增 effect 均为 0
- 三次 producer 轨迹 SHA-256 完全一致, Python verifier 3 次通过, awk 第二验证通过

### 基于证据的推断

- 原子 compare 的保护强度受 compare field set 限制, 原子性不能替代遗漏的业务 identity dependency
- local revision 只有在已确认同一 incarnation 的前提下才适合作为 freshness evidence
- compare identity 必须由 task completion semantics 决定, concrete-instance contract 与 logical-selector contract 不能共享机械的 UID 规则
- current completion 可靠性需要 task semantics、identity、freshness 与 commit boundary 连续绑定

### 未验证事项

- 尚未在真实 Kubernetes、etcd 或其他事务系统复现 local revision reuse 与 completion commit
- 尚未验证 identity observation 自身 stale 时 UID+revision compare 的行为
- 尚未验证多资源 completion 中部分 target reincarnation 与 fractured view 的组合
- 尚未验证 target 与 completion 分属不同事务域时如何维持同等保证
