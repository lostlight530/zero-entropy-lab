## 研究摘要

This Daily advances Ballast from deletion and cleanup proof into ambiguous external creation recovery.

The failure window is a provider creating an external resource and then losing the response or failing to persist the external identity back into the control object. Missing local success state then cannot be collapsed into proof that no external effect occurred.

Current Crossplane documentation explicitly calls provider-created but unmanaged resources leaked resources. It records external-create-pending before creation and external-create-succeeded or external-create-failed after a known result. If pending is newer than both terminal creation annotations, the provider treats the outcome as potentially leaked and stops reconciliation rather than blindly creating again.

No real external non-idempotent create is executed or blindly retried.

## 研究问题

When an external create attempt has an ambiguous result, can missing local success metadata, a negative lookup, or a known external name prove authoritative prior-effect absence strongly enough to permit a new non-idempotent create.

## 来源依据

Checked 2026-10-04 against current Crossplane documentation.

[Crossplane Managed Resources](https://docs.crossplane.io/latest/managed-resources/managed-resources/) documents external-name, external-create-pending, external-create-succeeded and external-create-failed annotations. It states that nondeterministic external naming can create a resource before the provider records its external name, producing a leaked resource.

The same documentation states that when external-create-pending is newer than the latest succeeded or failed timestamp, the provider may have leaked a resource and stops reconciliation until a human determines it is safe to proceed.

The documentation also instructs operators to inspect the external system around the pending timestamp and remove the pending annotation only after they are sure no leaked resource exists. It further notes that some external systems delay reporting newly created resources and that failing to account for this delay could cause duplicate creation.

[Crossplane Import Existing Resources](https://docs.crossplane.io/latest/guides/import-existing-resources/) separately demonstrates that external-name is an identifier used to bind a managed resource to a provider-side resource, while additional provider attributes may be necessary to identify a specific external resource.

These contracts support ambiguity, identity and visibility semantics only. They do not prove this bounded fixture or any live provider result.

## 路径比较

annotation-only is safest only when it preserves ambiguity, but it becomes unsafe when missing terminal metadata is interpreted as no effect. It disagrees with six expected outcomes in this fixture.

external-name-only recovers a known exact hit, but a single identifier lookup remains vulnerable to stale negative results, incomplete candidate identity and same-name incarnation confusion.

freshness-aware removes stale-read ambiguity and respects current permission and historical authorization, but still false-retries when a fresh point miss does not cover the full candidate identity set and false-binds a same-name wrong incarnation.

full-evidence-safe has zero disagreement in this bounded study because it treats prior-effect classification and current retry permission as different decisions and requires identity plus coverage rather than only lookup success.

The stronger path can stop with UNKNOWN or identity-reject instead of making progress. That is intentional for non-idempotent effects.

## 暂时结论

Missing local create success is not proof that the external effect did not occur.

external-create-pending is an ambiguity marker, not an authoritative miss.

A fresh negative point lookup is not automatically an authoritative miss when the external identity or candidate set is incomplete.

Even an authoritative prior-effect miss does not imply current execution permission.

H4 is supported only inside this bounded model. It is not a live Crossplane or cloud-provider result.

## AGI-scale action-integrity relevance

Long-running agents increasingly invoke provider bridges and APIs that create resources with nondeterministic identities.

A lost response after a real create is one of the most dangerous retry windows because a locally absent success record can coexist with a costly external effect.

Action integrity therefore needs separate proof for historical occurrence, historical authorization, current permission, exact target identity, candidate-set completeness and current completion. A system should be allowed to remain UNKNOWN when those proofs are unavailable.
