## 研究问题

当 selector-bound persistent-state task 的 completion contract 要求所有当前匹配 `worker` 的目标都为 `marked` 时, Agent 已经读取并绑定当前成员 A/B 的 UID 与 revision, 如果新的成员 C 在最后一次普通读取之后、completion commit 之前加入 selector, 只原子比较旧 A/B 的完整 identity 与 revision 是否仍可能把过期成员集合误当成完整 current completion evidence

本轮改变的故障位置不是固定成员内部的 fractured read 或 target reincarnation, 而是 task 所依赖的目标集合本身在 completion boundary 前发生 membership 变化

关键窗口为 `LIST {A,B} -> C joins selector as clean -> atomic compare only observed A/B -> completion`

## 来源依据

查询日期为 2026-08-30

- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) 说明 collection list response 带有 `resourceVersion`, 用于标识 collection 构造时的版本, list 与 watch 可以从该版本继续观察后续变化. 适用边界是 Kubernetes API collection consistency, 不直接证明 Ballast 受控夹具中的 selector epoch
- [PostgreSQL Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) 将 phantom read 定义为同一查询条件重新执行时返回的行集合发生变化, 并说明更强隔离级别需要处理 predicate 相关并发变化. 适用边界是 PostgreSQL transaction isolation, 不直接等价于任意 Agent selector 或跨服务资源集合

两个独立官方来源共同支持一个有限设计前提: 当业务不变量依赖一个动态集合或 predicate 时, 完成证据不仅需要绑定已观察成员, 还需要说明集合 membership 或 predicate view 自身属于哪个可核验一致性边界

外部文档只支持一致性模型边界, 不证明本轮 effect count、completion 结果或 selector-set compare 的受控实验结论

## 可证伪假设

- H1: 如果 completion commit 原子比较所有已观察成员的 UID 与 revision, 就足以证明 selector-bound current completion
- H2: completion 前再普通 relist 一次可以关闭 dynamic membership 变化, 不需要把 membership witness 与 completion commit 绑定
- H3: 对要求所有 current selector members 满足 predicate 的任务, protected compare 需要同时覆盖成员 identity/freshness 与 selector membership witness, membership 变化时重新读取完整 current set 再决定恢复或完成
- H4: whole-store global revision compare 可以发现本轮 membership join, 但无关 selector 外变化会造成额外 conflict
- H5: 新成员加入 selector 但已经满足 `marked` 时, membership-aware path 可以要求重新证明集合完整性而不机械执行 effect
- H6: completed replay 不能替代 member join before completion 的 production-entry 窗口

H1 的反证条件是 A/B 的 UID 与 revision 全部未变且原子 compare 成功, 但 C 已经加入 selector 且为 `clean`, 路径仍保存 completion

H2 的强反例把 C join 放在最后一次 relist 之后、completion commit 之前, 如果 relist 路径仍 completed 且 current contract 不成立, 则普通重读只能移动窗口而不能关闭窗口

H3 的反证条件是 selector membership 已变化或既有成员 revision 已变化时 strong path 仍直接接受旧 observation set, 或 conflict 后没有重新读取 current full set

H4 的限制反例只推进 selector 外对象的 global revision, 如果 global compare 仍冲突而 selector-set compare 不冲突, 说明 global fence 范围过宽

H5 的反证条件是 C 加入时已经 marked, strong path 仍无条件执行额外 effect

## 控制条件

- historical prior-effect evidence 固定为 hit, 本轮只研究 current completion evidence
- current execution permission 的 intent、holder、valid_until、task status、credential capability 与 approval binding 固定有效
- task semantics 固定为所有当前匹配 selector `worker` 的成员 value 都必须为 `marked`
- 初始 selector set 固定为 A=`uid-A1`, B=`uid-B1`, 两者 value=`marked`, local revision 1
- 初始 selector membership witness 抽象为 selector epoch 5, whole-store global revision 为 10
- `frozen-member-compare` 原子比较首次 list 中 A/B 的 UID 与 revision, 但不比较 selector membership witness
- `relist-then-complete` 在 completion 前再普通 list 一次, 但 relist 与 completion commit 仍是两个分离步骤
- `global-compare-complete` 使用 whole-store global revision 保护 completion commit
- `selector-set-compare` 同时比较首次观察成员的 UID/revision 与 selector membership witness, conflict 后重新读取 current full set, 必要恢复 effect 前记录 current permission, 再重新绑定新的成员集合与 witness
- selector epoch 只在 selector membership 变化时推进, 成员 value/revision 漂移由逐成员 compare 负责
- selector 外对象变化只推进 global revision, 不改变 selector epoch 或成员状态
- 新成员 C 可分别以 `clean` 或 `marked` 加入 selector
- completed replay 从已持久化 completion 重新进入同一 production entry 并通过 short circuit 返回
- 夹具只使用 Python 标准库与系统 awk, 不访问真实 Kubernetes、PostgreSQL 或外部 effect sink

## 强反例

第一强反例是 frozen member set 的零写入假完成

A/B 的 UID、value 与 revision 全部保持不变, completion commit 甚至对 A/B 执行了原子 compare, 但 clean C 已经进入 selector

因此 H1 被直接推翻: 对动态 selector task, 完整比较已观察成员仍不等于完整比较 current relevant set

第二强反例是普通 relist

C 在最后一次 relist 后加入时, relist 路径仍 false complete, 因此 H2 被推翻: 重读可以缩短 membership race window, 但不能替代与 protected completion 绑定的集合 witness 或 predicate boundary

第三个限制反例是 selector 外变化

whole-store global revision 能保守发现 C join, 但无关对象变化也会触发 conflict, 说明 H4 只在安全性上成立, 不是最精确的相关状态边界

第四个反方向反例是 marked C join

selector-set compare 仍拒绝旧 membership proof 并重新读取 current set, 但发现 C 已经满足任务 predicate 后不执行 effect, 支持 H5 并限制 membership change 必须重新写的错误外推

completed replay 四条路径都安全, 再次说明 completed 状态下的幂等性不能替代真实 membership-change-before-completion 窗口

## 路径比较

| 路径 | clean member join after final read | member state drift | selector 外变化 | marked member join | completed replay | 主要边界 |
| --- | --- | --- | --- | --- | --- | --- |
| frozen-member-compare | 假完成 | 可由成员 revision compare 检出 | 不冲突 | 当前 contract 仍成立但 membership proof 过期 | 零新增 effect | compare set 固定在旧成员集合 |
| relist-then-complete | 假完成 | 最后 relist 后仍可漂移 | 不冲突 | 当前 contract 成立 | 零新增 effect | relist 与 completion 仍分离 |
| global-compare-complete | 检出并恢复 | 检出并恢复 | 额外 conflict | 重新证明, 零 effect | 零新增 effect | 安全但 whole-store over-fence |
| selector-set-compare | 检出并恢复 | 检出并恢复 | 不冲突 | 重新证明, 零 effect | 零新增 effect | 依赖 membership witness 完整覆盖 selector semantics |

正常基线中四条路径都不增加 effect

selector-set compare 的改进来自相关集合 identity 与成员 freshness 的证据质量, 不是操作数更少

global compare 在 selector 外变化中多一次 conflict/reconciliation, 说明更宽围栏可能安全但增加无效恢复工作

## 暂时结论

状态保持观察

本轮推翻 H1 与 H2, 支持有边界的 H3、H4、H5 与 H6

对于 selector-bound dynamic multi-resource completion contract, `relevant identity set` 不只是首次观察到的成员列表, 还包括能够证明当前 membership 或 predicate result 未发生语义变化的集合 witness

已观察成员的 UID+revision 原子 compare 只能证明这些旧成员没有变化, 不能证明 completion 时没有新的 required member 加入 selector

因此 current completion evidence 的稳定链可以进一步解释为 `task semantics -> current relevant membership and identity set -> coherent snapshot or freshness -> predicate-complete atomic protected completion`

该结论是现行 METHOD 的前向细化, 不建立新的第四条 NOTES 发现

## 事实分层

### 已验证事实

- 受控模型中 A/B 的 UID 与 revision 都未变化时, clean C 可以在 completion 前加入 selector
- frozen-member-compare 对 A/B 的原子 compare 成功后仍得到 completed=1 且 current contract=0
- 普通 relist 在 C join 发生于最后一次 relist 之后时同样 false complete
- selector-set compare 在 membership 变化时 conflict, 重新读取 current set 并只在必要时执行恢复 effect
- selector 外 global 变化不会使 selector-set compare 冲突, 但会使 global compare 额外冲突
- marked C join 会使 membership proof 过期但不需要新增 effect
- completed replay 四条路径新增 effect 均为 0
- 三次 producer 轨迹 SHA-256 完全一致, Python verifier 3/3 PASS, awk verifier PASS, producer/verifier py_compile PASS

### 基于证据的推断

- dynamic selector task 的 relevant identity set 需要包含 membership 或 predicate witness, 不能冻结为初始成员列表
- atomicity 只能保护 comparison set 中已经表达的条件, 不会自动证明没有 phantom member
- selector-scoped witness 可以比 whole-store global revision 更精确, 前提是它完整覆盖所有会改变 task membership semantics 的事件

### 未验证事项

- 尚未在真实 Kubernetes、PostgreSQL 或其他 predicate-aware store 上复验
- 尚未验证 member delete+join identity swap、分页 selector、stale membership index 与高并发 churn
- 尚未验证跨服务 target/completion store 无共享 transaction 时的完整恢复协议
- selector epoch 是受控夹具抽象, 不代表 Kubernetes 或任意产品直接提供相同字段
- verifier 仍共享事件标签与字段语义, 不能排除共同建模错误
