# Ballast 日记录 2026-08-18

类型: 每日专题
主题: 并发恢复接管中的 ownership claim 与 prior effect evidence 分离

## 研究问题

两个恢复者同时或先后接管同一个 unknown-outcome 任务时, 原子 claim 或 lease 是否足以避免重复副作用

本轮改变 2026-08-17 留下的并发恢复条件, 不再重复 receipt 与 effect 的双写顺序本身

重点攻击 `effect_committed -> completion_missing -> interruption -> claim_expired -> takeover -> replay` 窗口

## 来源依据

查询日期为 2026-08-18

- [etcd API: Transaction](https://etcd.io/docs/v3.6/learning/api/) 说明 transaction 是基于 compare 条件的原子 If/Then/Else, 可用于 compare-and-swap 与更高层并发控制. 适用边界是 etcd key-value store 内的原子条件与修改, 不直接证明外部副作用已经发生
- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) 说明客户端可把更新绑定到当前 `resourceVersion`, stale `resourceVersion` 会得到 409 Conflict, 用于检测 lost update. 适用边界是 Kubernetes API 对象的并发更新, 不等价于跨系统 effect receipt
- [PostgreSQL Documentation: Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) 说明 Serializable 事务要求成功提交的并发执行等价于某个串行顺序, 并可能通过 serialization failure 要求应用重试. 适用边界是数据库事务内部的并发可串行化, 不自动覆盖事务外部副作用

这些来源共同支持 claim 或 compare-and-act 可以约束并发所有权变化

把该合同进一步解释为“新 holder 因此知道旧 holder 没有产生外部 effect”属于本轮待证伪推断, 不是来源直接保证

## 可证伪假设

- H1: 不做并发 claim 仍能依靠 completion 避免重复副作用
- H2: 原子 lease claim 与 ownership epoch 足以同时解决普通并发和 unknown-outcome takeover
- H3: 在本轮模型中, claim 只回答当前谁有执行权, unknown-outcome takeover 还需要独立查询 authoritative effect receipt 才能判断是否应再次执行

H1 的反证条件是两个并发恢复者都通过入口并产生两个 effect

H2 的反证条件是旧 holder 已提交 effect 但未保存 completion, lease 过期后新 holder 合法接管仍产生第二个 effect

H3 的反证条件是新 holder 接管并查询 receipt 后仍重复 effect, 或 receipt 缺失时错误零写入完成

## 控制条件

- relevant world state, intent, task status, valid_until, credential, approval, action identity 与 target incarnation 全程保持不变
- 只改变 recovery ownership 与 effect/completion 历史
- 每次真正副作用尝试前都重新执行 current permission check
- `uncoordinated` 不建立 claim
- `lease-takeover` 使用原子 claim, claim 冲突拒绝并发 holder, claim 过期后允许新 holder 以递增 epoch 接管
- `lease-receipt` 在相同 claim 规则上, 每次持有 claim 后先查询 authoritative effect receipt
- receipt 由 effect commit 同步留下, completion 独立保存
- unknown outcome 在 effect 已提交且 receipt 已存在, completion 尚未保存时注入中断
- 之后显式让旧 claim 过期, 新恢复者重新进入同一 production entry
- completed replay 先正常完成再重新进入同一 production entry
- 夹具只使用 Python 标准库与系统 awk, 不访问网络或外部存储

## 实验设计

1. 三条路径执行 normal-concurrent, A 与 B 都进入 production entry
2. 三条路径执行 unknown-after-effect, A 在 effect commit 后中断, claim 路径随后发生 claim expiry, B 再进入 production entry
3. 三条路径执行 completed-replay, A 正常完成后 B 再进入同一 production entry
4. producer 输出 scenario, path, effect_count, receipt, completed, claim_epoch, ops 与 event_order
5. event_order 保存 permission check, claim epoch, claim conflict, effect commit, interruption, claim expiry, receipt hit/miss 与 completion save 的先后关系
6. producer 完整运行三次并比较 TSV SHA-256
7. 独立 Python verifier 不导入 producer, 直接解析 TSV 并从 effect 数, claim epoch 与 event order 复核关键历史
8. awk 第二验证实现只检查 unknown-after-effect 三条路径与 completed replay effect 数
9. producer 与 verifier 执行 Python 语法编译检查

## 独立验证

Python verifier 与 producer 为两个独立文件

verifier 不导入 producer, 不读取 producer 内部成功布尔值或保存的期望对象

Python verifier 独立检查

- normal-concurrent 的 uncoordinated effect 数为 2, 两条 claim 路径均为 1
- unknown-after-effect 的 uncoordinated 与 lease-takeover effect 数均为 2
- lease-takeover takeover 后 claim epoch 为 2, 且第二次 effect 位于 B 获得 epoch 2 之后
- lease-receipt takeover 后 claim epoch 同样为 2, 但 `receipt_hit` 位于 completion 前且 effect 总数为 1
- 三条 completed replay 都保持 effect 数为 1
- 所有真实 effect 尝试之前都能在 event order 中找到对应恢复者的 permission check

三次 Python verifier 均返回 `PY_VERIFIER_PASS`

awk 第二实现返回 `AWK_PASS`

producer 与 verifier 均通过 `py_compile`

两个 verifier 仍共享 TSV 字段语义, 原始轨迹与同一系统运行环境

因此本轮验证不是完全独立的分布式实现验证

## 强反例

- completed replay 三条路径全部保持单次 effect, 只测已完成重放会错误放过 uncoordinated 与 lease-takeover 的故障窗口
- normal-concurrent 中两条 lease 路径都只产生一次 effect, 只测试同时竞争会错误推断 lease 本身已经解决 unknown outcome
- ownership epoch 2 是当前执行权的新鲜证据, 但它没有说明 epoch 1 的 holder 在失联前是否已经提交 effect
- receipt 命中后零新增 effect 在本轮是正确恢复, 但这个结论依赖 receipt 与真实 effect 同步产生的控制条件, 不能外推到 2026-08-17 已证明不可信的 receipt-first 双写
- 最终 completed 都为 1, 因而最终任务状态无法区分一次 effect 与两次 effect 的历史

## 暂时结论

状态保持观察

本轮支持把恢复接管拆成两个独立问题

- claim 或 ownership generation 回答当前谁有副作用执行权
- authoritative effect evidence 回答旧 unknown attempt 是否已经产生副作用

新的 ownership epoch 不能作为旧 effect 不存在的证明

因此在涉及非幂等外部副作用的 takeover 中, 新 holder 即使合法取得当前执行权限, 仍应在重试前独立核验 prior effect evidence

本轮不证明 lease-receipt 是通用 exactly-once 方案

真实系统仍需要确认 receipt provenance, target incarnation, action identity, receipt retention 与查询一致性

## 事实分层

### 已验证事实

- 三次 producer 输出 SHA-256 完全一致
- Python verifier 三次通过
- awk verifier 通过
- producer 与 verifier 均通过 Python 编译检查
- normal-concurrent 中 lease-takeover 与 lease-receipt 都只产生一次 effect
- unknown-after-effect 中 lease-takeover 在 epoch 2 takeover 后产生第二次 effect
- unknown-after-effect 中 lease-receipt 在 epoch 2 takeover 后命中 receipt 并保持单次 effect
- completed replay 三条路径都保持单次 effect
- event order 能区分相同 completed 最终状态下的一次 effect 与两次 effect 历史

### 基于证据的推断

- current ownership evidence 与 prior effect evidence 是两个不同语义合同
- claim 的线性化可以防止同一时点的并发 holder, 但不能单独关闭跨 claim expiry 的 unknown-outcome 重放窗口
- 对本轮 receipt provenance 成立的控制条件, takeover 后先查 receipt 比直接执行更能保持历史副作用单次性

### 未验证事项

- 真实 etcd, Kubernetes 或 PostgreSQL 没有作为实验目标
- 没有测量真实网络延迟, lease 时钟漂移, split-brain, storage quorum 或多区域一致性
- 没有验证外部 sink 是否接受 ownership fencing token
- 没有验证 receipt retention, receipt 查询故障或 receipt 与 effect 跨系统原子性
- 没有使用独立进程或不同语言 verifier
