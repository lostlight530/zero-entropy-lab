## 研究问题

当 approval contract 的 action、UID、policy 与 credential scope 全部保持不变, 但 subject administrative state 从 active 变为 disabled 时, 漏掉 subject lifecycle state 的 shared semantic specification 是否会让不同实现的 producer 与 verifier 共同接受 stale unauthorized effect, 独立 authority representation 是否能识别该共同失效

关键窗口为 `APPROVE -> SUBJECT_DISABLE -> production entry -> incomplete compare -> effect -> completion`, 并与 dependency-complete projection、whole-global revision 和无关 metadata 反例比较

## 来源依据

查询日期为 2026-09-07

- [NIST SP 800-162 Guide to Attribute Based Access Control](https://www.nist.gov/publications/guide-attribute-based-access-control-abac-definition-and-considerations-0), 2019-08-02 发布. NIST 将授权定义为 subject、object、operation 与适用 environment attributes 对 policy 的联合求值, 并强调 subject attributes 需要由权威方管理. 本轮只采用有限命题: 如果 subject state 是真实授权依赖, projection 漏掉它不能证明当前授权仍成立
- [RFC 7643 System for Cross-domain Identity Management Core Schema](https://www.rfc-editor.org/info/rfc7643/), 2015-09 发布. RFC 7643 定义 User `active` 为用户 administrative status 的布尔属性, 典型语义中 false 可表示账户被暂停或不再允许访问. 本轮只采用有限命题: subject lifecycle 可以是独立于 action、target 与 scope 的权威状态
- [NASA IV&V Overview](https://www.nasa.gov/ivv-overview/), 页面 2024-07-23 更新. NASA 将 technical independence 描述为独立于开发者评估开发过程与产物. 本轮只采用有限命题: verifier 的独立性不能只由代码文件不同推断

这些来源不证明本地 effect 数量、PASS 结果或真实身份系统行为

## 可证伪假设

- H1: producer 与 verifier 代码实现不同后, 共享同一漏字段 approval specification 的一致 PASS 足以证明有效完成
- H2: action、UID、policy 与 credential scope 足以代表 approval applicability, subject administrative state 变化不影响授权
- H3: shared-spec producer 在 subject disabled 后仍会 match 并产生 unauthorized effect
- H4: dependency-complete producer 会在 effect 前拒绝 subject disabled, 同时允许只改变无关 note metadata
- H5: whole-global revision 会阻止 subject disabled 与 policy drift, 但也会 over-fence 无关 metadata
- H6: 从独立 authority CSV fixture 重建完整 approval contract 的 verifier 能识别 shared-spec unauthorized effect, 即使它不读取 producer 导出的 authority fields
- H7: completed replay 从 production entry 重入时保持零新增 effect

H1 的反证条件是两个不同 shared-spec verifier 中至少一个能仅凭同一漏字段 specification 拒绝 subject-disabled effect

H6 的反证条件是 raw verifier 从独立 authority fixture 读取 subject_active 后仍把 shared-spec effect 判为 authorized

## 控制条件

- approval 固定 action=`mark`, UID=`uid-A1`, policy=`standard`, scope=`mark:write`, subject_active=`1`
- normal 保持 revision=10
- subject-disabled 只把 subject_active 改为 `0`, revision=11
- policy-restricted 只把 policy 改为 `restricted`, revision=11
- metadata-only 只把 note 从 `n0` 改为 `n1`, revision=11
- shared-spec 比较 action、UID、policy、scope, 明确省略 subject_active
- complete-authority 比较 action、UID、policy、scope、subject_active
- global-revision 只接受 approval revision 10
- producer trace 与 authority CSV 分离, raw verifier 从 authority CSV 重建真值
- 两个 shared-spec verifier 分别使用显式行条件与集合索引, 不共享实现
- completed replay 重新进入 production entry 后先命中 completion short circuit
- 只使用 Python 标准库与系统 awk

## 实验设计

1. 对 normal、subject-disabled、policy-restricted、metadata-only 运行 shared-spec、complete-authority、global-revision 三条 production path
2. 记录每条路径的 terminal、effect、unauthorized、match、ops、result 与 event_order
3. subject-disabled 明确保存 `APPROVE -> CHANGE -> ENTRY -> COMPARE -> EFFECT` 时序
4. 两个 shared-spec verifier 分别检查漏字段 specification 的预期行为
5. raw verifier 只读取独立 authority CSV 与 effect trace, 不读取 producer 内部 success boolean 作为授权真值
6. 使用 awk 独立复核 subject-disabled/shared-spec unauthorized effect 与 metadata-only/complete-authority authorized effect
7. producer 与三个 verifier 执行 `py_compile`
8. 完整运行三次并比较 trace bytes 与 SHA-256
9. completed replay 重新进入 production entry, 检查新增 effect 为 0
10. 验证结束后清理临时目录

## 原始观测

每次 trace 包含 13 个 scenario/path 数据行, 三次 SHA-256 均为 `b86f87a712b764e9b613694a39664fda92d1b7c0e3fe781cc28bdd868895ae36`

| 场景 | 路径 | terminal | effect | unauthorized | match | ops | 结果 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| subject-disabled | shared-spec | 1 | 1 | 1 | 1 | 3 | applied |
| subject-disabled | complete-authority | 0 | 0 | 0 | 0 | 2 | safe-stop |
| subject-disabled | global-revision | 0 | 0 | 0 | 0 | 2 | safe-stop |
| metadata-only | shared-spec | 1 | 1 | 0 | 1 | 3 | applied |
| metadata-only | complete-authority | 1 | 1 | 0 | 1 | 3 | applied |
| metadata-only | global-revision | 0 | 0 | 0 | 0 | 2 | safe-stop |
| completed-replay | shared-spec | 1 | 0 | 0 | 0 | 1 | completed-short-circuit |

subject-disabled/shared-spec 的 event order 为 `APPROVE:rev10 -> CHANGE:subject-disabled:rev11 -> ENTRY -> COMPARE:shared-spec:1 -> EFFECT:uid-A1 -> COMPLETE`

subject_active 已经从 `1` 变为 `0`, 但 shared-spec 的四字段仍全部 match, 因而产生 1 次 unauthorized effect

complete-authority 在同一场景 effect=0, metadata-only 时 effect=1 且 unauthorized=0

global-revision 对 subject-disabled 安全停止, 但 metadata-only 也额外停止

## 独立验证

三次运行中显式 shared-spec verifier 均返回 `EXPLICIT_SPEC_PASS 13`, set-index verifier 均返回 `SET_SPEC_PASS 13`

这两个 PASS 证明它们忠实实现了同一个漏字段合同, 不证明 effect 有效

raw verifier 三次均返回 `RAW_AUTHORITY_PASS 13`. 它从独立 authority CSV 读取 action、UID、policy、scope、subject_active, 识别 subject-disabled/shared-spec 为 effect=1 且 unauthorized=1, 并确认 metadata-only/complete-authority 为 authorized effect

awk 返回 `AWK_PASS`

producer 与三个 verifier 均通过 `py_compile`, 三份 trace byte-for-byte 相同, 临时目录已清理

raw verifier 与 producer 仍共享 scenario vocabulary、批准常量与同一系统运行环境, 因而不构成真实外部 IV&V

## 强反例

第一强反例攻击 shared semantic specification: action、UID、policy、scope 全部保持批准值, 仅 subject administrative state 失效, shared-spec 仍执行一次 unauthorized effect

第二强反例攻击 implementation diversity: 两个 verifier 使用不同代码结构, 但都依赖同一漏字段 specification, 因而共同接受 weak path 的预期行为

第三强反例攻击 whole-global revision 的精度: metadata-only 不改变任何授权依赖, complete-authority 正常执行, global-revision 却额外停止

policy-restricted 控制中 shared-spec 正确停止, 证明 weak path 不是无条件执行, 失败定位在 omitted subject lifecycle dependency

## 路径比较

- shared-spec 字段更少, subject-disabled 时 ops=3 并产生 stale unauthorized effect
- complete-authority subject-disabled 时 ops=2 安全停止, metadata-only 时 ops=3 正常执行, 在本夹具中同时避免 under-fencing 与 global over-fencing
- global-revision 对相关变化保守停止, 但无关 metadata 同样停止
- 两个 shared-spec verifier 增加实现多样性却没有增加 subject lifecycle 语义覆盖
- raw authority verifier 能阻止把共同失效报告为有效完成, 但不能撤销已经发生的 effect
- 本地操作数只表示夹具分支步骤, 不外推真实系统性能

## 暂时结论

本轮观察支持: approval applicability 的 dependency set 如果漏掉真实 subject lifecycle attribute, producer 与不同实现 verifier 可以在共享错误 semantic specification 下共同失效

独立 authority representation 比读取 producer 导出的 raw authority fields 更强, 因为 verifier 的授权真值不依赖 producer 导出的字段集合. 但当前 fixture 仍共享批准常量与 scenario vocabulary, 因而只把结论保持为观察

9 月 5 日 environment、9 月 6 日 credential scope 与本轮 subject lifecycle 构成第三个支持性窗口. 数量上达到三轮, 但本轮不把它自动提升为长期发现, 原因是三轮仍共享同一受控 fixture 家族与上游批准语义, 尚缺少专门的跨窗口 independence audit 来确认不存在共同建模遗漏

## 复验条件

- 让 authority verifier 从独立生成的 policy 或 identity source 读取 subject state, 不共享批准常量
- 把 omitted dependency 改为 valid_until 或 approval issuer generation, 检查相同共同失效是否继续出现
- 在真实 SCIM 或身份生命周期系统中复现 active 到 inactive 的变化
- 对 9 月 5 日至 9 月 7 日三轮执行独立性审计, 再决定是否达到 NOTES 发现门槛
- 在跨服务 authorization authority 与 effect sink 上测试无共享事务时的 compare-and-effect

## 体系增量

- relevant state projection 的完整性检查应显式覆盖 subject lifecycle attribute, 不能只覆盖 action、target、policy 与 credential scope
- verifier independence 应区分实现独立、输入表示独立与上游合同独立, 三者不能互相替代
- whole-global revision 是保守 fence, 不是 dependency-complete projection 的精确替代
- 已完成重放继续要求从 production entry 进入, 只读 verifier 重跑不能替代 production replay

## 事实分层

### 已验证事实

- subject-disabled/shared-spec 在三次确定性运行中均产生 1 次 unauthorized effect
- complete-authority 在 subject-disabled 中零 effect, metadata-only 中执行 1 次 authorized effect
- global-revision 在 metadata-only 中额外停止
- 两个不同实现 shared-spec verifier 均接受同一漏字段合同的行为
- raw verifier 从独立 authority CSV 识别 subject lifecycle omission
- completed replay 新增 effect 为 0
- producer 与三个 verifier 通过 `py_compile`, 三次 trace SHA-256 相同, awk 关键边界复核通过

### 基于证据的推断

- 代码实现多样性不能单独证明 approval dependency set 的语义独立性
- authority representation 独立可以降低 producer 输出字段共同失效风险, 但仍需独立评估上游合同本身
- dependency-complete projection 在本夹具中比 whole-global revision 更精确
