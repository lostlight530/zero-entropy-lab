# Ballast 日记录 2026-08-23

类型: 每日专题
主题: 历史 effect receipt 在补偿反转后的完成语义失效

## 研究问题

当 unknown outcome 的副作用已经发生且 authoritative receipt 已真实提交, completion 尚未持久化, 随后该副作用又被补偿事务或外部合法状态变化反转时, receipt hit 是否仍足以恢复 completed

本轮改变故障位置: 不测试 receipt miss, query error, stale read, retention 或资源删除, 而测试 `effect committed + receipt committed -> completion missing -> effect reversed -> replay`

本轮只讨论可逆且完成语义要求当前后置条件仍成立的 stateful effect, 不把结论外推到发送邮件等 occurrence 本身就是业务完成语义的不可逆事件

## 来源依据

查询日期为 2026-08-23

- [AWS Prescriptive Guidance: Saga patterns](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-patterns.html) 说明 saga 中已完成的本地事务可以在后续失败时通过 compensating transactions 撤销先前数据库变化, 支持“effect 曾发生”和“effect 当前仍成立”可以分离的故障模型. 适用边界是分布式业务事务与补偿恢复, 不直接证明任意 Agent effect receipt 语义
- [Microsoft Azure Architecture Center: Compensating Transaction pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction) 说明补偿事务用于撤销已经完成步骤的 effect, 且补偿可能在原操作提交后运行, 其他并发事务也可能改变中间状态. 适用边界是 eventually consistent 长流程, 不等价于任意外部 sink 的完成合同

两个独立官方来源共同支持一个设计前提: 历史成功 occurrence 可以在稍后被合法反转, 因此历史 receipt 与当前后置条件不是天然同一证据

把这个边界用于 Agent unknown-outcome replay 属于本轮待证伪假设

## 可证伪假设

- H1: exact authoritative receipt hit 足以恢复 completed, 无需重新核对当前后置条件
- H2: 如果所有补偿动作都记录在 exact compensation ledger 中, receipt hit 联合 ledger miss 足以证明 effect 仍成立
- H3: 对完成语义要求当前目标仍为 `marked` 的可逆 stateful effect, receipt hit 后重新读取 current postcondition 能发现已经被反转的历史 effect, 并在重新确认当前执行权限后恢复必要 effect
- H4: completed replay 不能替代 effect 后补偿再重放窗口, 因为 completion short circuit 会绕过 receipt 与当前后置条件复核

H1 的反证条件是 receipt hit 后直接 completed, 但当前 value 已被补偿恢复为 `clean`

H2 的反证条件是 effect 被另一个合法状态变化反转, 但该变化不写入当前任务的 compensation ledger, ledger miss 后仍错误 completed

H3 的反证条件是 current postcondition 明确为 `clean` 时, postcondition 路径仍不执行必要恢复 effect 或未在 B 侧 effect 前重新确认 permission

H4 的反证条件是 completed replay 能暴露上述补偿后 receipt stale 问题

## 控制条件

- task, normalized action 与 target incarnation identity 固定为同一 effect identity
- 当前 task status, intent, ownership, valid_until, credential 与 approval binding 在 replay 时保持有效
- 每个 B 侧真实 effect commit 前重新记录 `B:permission_valid`
- authoritative receipt 只在真实 effect commit 后保存, 因而本轮不攻击 receipt provenance 或 effect/receipt 双写顺序
- `receipt-only` 在 exact receipt hit 后直接恢复 completion
- `compensation-ledger` 在 receipt hit 后查询 exact compensation identity, exact compensation hit 时重新执行 effect, ledger miss 时恢复 completion
- `receipt-postcondition` 在 receipt hit 后重新读取当前目标后置条件, 只有 value 仍为 `marked` 才恢复 completion, 否则重新确认 permission 后执行 effect
- `compensated-after-effect` 使用同一 identity 的显式补偿把 value 从 `marked` 反转为 `clean`
- `external-reversal-after-effect` 使用不进入当前任务 compensation ledger 的合法外部变化把 value 反转为 `clean`, 用于攻击 ledger 完整性假设
- completed replay 固定在 completion 已保存后重新进入同一 production entry
- 夹具只使用 Python 标准库与系统 awk, 不访问真实 AWS, Azure 或外部 effect sink

## 实验设计

1. 三条路径执行 normal-no-prior, 没有历史 receipt, 检查是否各执行一次必要 effect 并达到 `marked`
2. 三条路径执行 compensated-after-effect, A 提交 effect 与 receipt 后在 completion 前中断, 随后 exact compensation 反转状态, B 重新进入 production entry
3. 三条路径执行 external-reversal-after-effect, A 同样产生 effect 与 receipt 后中断, 但反转动作不进入当前 task compensation ledger, 检验 ledger miss 是否能代表 effect 仍成立
4. 三条路径执行 completed-replay, A 已保存 completion 后再次进入相同 production entry
5. producer 输出 scenario, path, effect_count, completed, value, result, ops 与 event_order, 完整运行三次并比较 stdout TSV SHA-256
6. 独立 Python verifier 不导入 producer, 从 event_order 重建真实 forward effect commit 数, 检查每个 B effect 前的 current permission evidence, 并复核决定性反例
7. awk 第二验证实现独立复核显式补偿, 外部反转与 completed replay 三组关键结果
8. producer 与 verifier 执行 `py_compile`

verifier 不导入 producer, 不读取 producer 内部成功布尔值或保存的期望对象

Python verifier 独立检查

- 12 个 scenario/path 组合完整且唯一
- event_order 中真实 forward effect commit 数与输出 effect_count 一致
- 每个 B 侧 effect commit 前都存在 `B:permission_valid`
- normal-no-prior 三条路径都执行一次必要 effect, completed 为 1 且 value 为 `marked`
- compensated-after-effect 的 receipt-only 为 effect 1, completed 1, value `clean`
- compensated-after-effect 的 compensation-ledger 与 receipt-postcondition 都恢复到 effect 2, completed 1, value `marked`
- external-reversal-after-effect 的 receipt-only 与 compensation-ledger 都停在 effect 1, completed 1, value `clean`
- external-reversal-after-effect 的 receipt-postcondition 为 effect 2, completed 1, value `marked`
- completed-replay 三条路径都保持 effect 1 与 value `marked`

三次 Python verifier 均返回 `PY_VERIFIER_PASS`

awk 第二验证实现返回 `AWK_PASS`

producer 与 verifier 均通过 `py_compile`

两个 verifier 仍共享 TSV 字段语义, event label 约定与同一系统运行环境

因此本轮不是对真实 Saga engine, compensation ledger 或远端 stateful sink 的端到端验证

## 强反例

- compensated-after-effect 证明 exact receipt 本身可以完全真实且 provenance 正确, 但如果完成语义要求当前 effect 仍成立, receipt-only 仍会形成 `completed=1 / value=clean` 的假完成
- external-reversal-after-effect 进一步推翻“查询 compensation ledger 就够了”: 只要存在不进入该 ledger 的合法反转路径, ledger miss 就不能证明 effect 当前仍成立
- receipt-postcondition 在 external reversal 场景仍恢复 `marked`, 说明当前后置条件读取可以覆盖本轮未被 ledger 记录的反转, 但前提是该后置条件确实完整表达任务完成语义
- completed-replay 三条路径全部安全, 因为 completion 已存在时根本不会进入 receipt freshness 或 current postcondition 判断, 所以不能替代补偿后 replay 窗口

## 路径比较

| 路径 | normal | exact compensation 后 replay | ledger 外反转后 replay | completed replay | 主要边界 |
| --- | --- | --- | --- | --- | --- |
| receipt-only | effect 1 | effect 1, clean 假完成 | effect 1, clean 假完成 | effect 1 | receipt 只证明历史 occurrence |
| compensation-ledger | effect 1 | effect 2, marked | effect 1, clean 假完成 | effect 1 | 依赖反转事件被完整记录并正确绑定 |
| receipt-postcondition | effect 1 | effect 2, marked | effect 2, marked | effect 1 | 依赖当前后置条件完整且读取足够权威 |

在两个反转场景中 receipt-only 操作数最少, 但结果质量错误

receipt-postcondition 需要额外读取并在后置条件失效时再次执行 forward effect, 因而 forward effect 历史数会从 1 增为 2, 但第一次 effect 已被反转, 第二次是当前完成语义所需的恢复动作, 不能简单按“重复次数更少”评价质量

受控操作数不是远端延迟或成本测量, 不用于推断真实系统性能

## 暂时结论

状态保持观察

本轮支持把 `authoritative receipt hit` 与 `任务当前完成` 继续分开: receipt 可以可靠证明某个 effect 曾经发生, 但对可逆 stateful effect, 随后的 compensation 或其他合法状态变化可能使该 occurrence 不再满足当前完成语义

如果任务完成定义要求当前 postcondition 持续成立, 恢复 completion 前还需要把历史 effect evidence 与当前权威 postcondition 重新绑定

compensation ledger 可以作为反转证据的一部分, 但只有在能够证明其覆盖全部会使完成语义失效的反转路径时才足够; 无法证明完整性时不能用 ledger miss 替代当前状态验证

该结论不适用于业务语义只要求“某事件至少发生一次”的不可逆 occurrence-only effect, 这类任务需要不同的完成合同

## 复验条件

- 使用真实 Saga 或补偿工作流验证原 effect receipt, compensation record 与当前业务状态三者的可见顺序
- 加入 compensation 完成但 ledger 写入延迟或丢失的窗口, 检验 ledger freshness 与 provenance
- 加入人工修正, 其他任务写入和外部系统回滚等 ledger 外状态变化, 检查 current postcondition 是否仍能完整覆盖完成语义
- 对 occurrence-only effect 与 persistent-state effect 分别建模, 验证不同 completion contract 是否需要不同 prior-effect 规则
- 加入当前后置条件 stale read, revision drift 与 target incarnation 变化, 检验本轮 postcondition 路径与既有 freshness 门的组合行为

## 体系增量

- 为 unknown-outcome 恢复增加 `historical occurrence != current completion` 的正向证据边界
- authoritative receipt 的职责限定为证明历史 effect occurrence, 是否能直接恢复 completion 取决于任务完成合同是否是 occurrence-only
- 对要求当前状态持续满足的 effect, completion 恢复需要重新绑定 current authoritative postcondition
- compensation evidence 本身也需要 identity, provenance, freshness 与 coverage 完整性, ledger miss 不天然等价于“没有反转”
- 保留 current execution permission 与 prior-effect evidence 两条独立证据链, 任何重新执行 effect 的路径仍必须在副作用前重新确认当前权限

## 事实分层

### 已验证事实

- 受控夹具中 exact receipt 在真实 effect 后提交, 因而 receipt hit 不是伪造或 ghost receipt
- exact compensation 后 receipt-only 得到 effect 1, completed 1, value `clean`
- exact compensation ledger 能识别同 identity compensation 并触发恢复 effect, 最终 value `marked`
- ledger 外合法反转后 compensation-ledger 得到 ledger miss 并错误 completed, value 仍为 `clean`
- receipt-postcondition 在两类反转后都读取到 `clean`, 重新确认 permission 并执行恢复 effect, 最终 value `marked`
- completed replay 三条路径都保持 forward effect 1
- 三次 producer 轨迹哈希完全一致, Python verifier 三次通过, awk 第二验证实现通过, 两个 Python 文件通过 `py_compile`

### 基于证据的推断

- 对 persistent-state completion contract, authoritative receipt hit 只证明历史 occurrence, 不能单独证明当前完成
- compensation ledger 只有在覆盖全部语义反转路径时才能作为 receipt 的有效性修饰证据, 未证明 coverage 时 ledger miss 仍有假完成风险
- current postcondition 可以作为本轮更强的 completion 证据, 但其完整性, freshness 与读取绑定仍需要沿用既有 Ballast 门

### 未验证事项

- 未验证真实 AWS 或 Azure Saga 实现
- 未验证真实补偿日志与业务状态的原子性, 线性一致性或跨区域复制
- 未验证 postcondition 查询故障, stale read, retention 与 compensation 同时发生的组合窗口
- 未验证人工反转或其他任务修改是否始终可由一个明确 current postcondition 检测
- 未验证不可逆 occurrence-only 副作用应采用的独立 completion contract
