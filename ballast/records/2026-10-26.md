## 研究摘要

本轮研究 Temporal Workflow Update 的 ACCEPTED / COMPLETED 阶段、validator rejection、update/run/attempt identity 与外部 effect 完成之间的证明断层

在隔离 V8 中实际执行 52 个 reset-per-scenario 受控合成场景、三条判定路径共 156 行决策，随后从已提交源码再次执行 producer 与独立实现 verifier，52 个 scenario payload 和 156 行 CSV 与已提交证据逐字节一致

Reference 模型得到 3 COMPLETE、16 STOP_UNKNOWN、28 RECONCILE、2 EVIDENCE_CONFLICT、1 RETRY_ALLOWED、2 BLOCKED，49/49 非完成控制场景符合 authored controls，伪造首行决策被实际行验证器拒绝

52 个场景中的 68 条 receipt 是合成 primitive fixture，真实 Temporal API 请求和真实 external effect 均为 0，不能把模型内 PASS 晋升为线上准确率

## 研究问题

Workflow Update 已 ACCEPTED 或已 COMPLETED，是否足以证明 exact A+B 两个外部非幂等 effect 已发生、发生时获授权、属于正确 workflow run/update/attempt 和 target incarnation，并且当前 protected A+B completion predicate 成立

若 Update ID 被去重、validator 拒绝、handler 完成、receipt 与 authoritative negative MISS 冲突或 current membership 被替换，弱控制面代理与完整参考路径是否产生可复算的分歧

## 来源依据

权威来源于 2026-10-26 访问，Temporal 相关页面同属一个 publisher，不能计作多个独立 publisher

- [Temporal Workflow message passing](https://docs.temporal.io/encyclopedia/workflow-message-passing) 将 Updates 定义为可等待处理结果的 tracked write requests，与不等待响应的 Signals 不同
- [Temporal Nexus Java Update walkthrough](https://docs.temporal.io/develop/java/nexus/development-walkthrough/add-messaging) 明确 Update-backed operation 可等待 ACCEPTED 并在之后通过 completion callback 完成，validator rejection 不运行 handler 且不进入 Event History
- [Temporal Cloud Actions](https://docs.temporal.io/evaluate/cloud/actions) 将 accepted Update 与 rejected Update 分开计量，重复 Update ID 的 deduplicated update 不再计一次 Action，Action 计数不是外部 effect receipt
- [AWS Step Functions callback patterns](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html) 作为不同产品的独立 publisher 类比，callback token 通过 SendTaskSuccess / SendTaskFailure 推进控制面，不是 Temporal 具体实现的独立证明

来源证明供应商声明的控制面语义，不证明本轮 synthetic receipts 对应真实 Temporal handler、Activity 或外部 sink

## 可证伪假设

H1 accepted_stage_proxy 将 ACCEPTED / COMPLETED 视为 COMPLETE，若 accepted 但没有 effect 就出现 false completion

H2 update_completed_proxy 将 COMPLETED 视为 COMPLETE，若 completed 但 A+B effect 缺失、identity 错误或 current witness 失效就出现 false completion

H3 full_reference 只有在 exact run/update/attempt/effect identity、effect-time grant、update temporal bounds、current member UID set 与 protected guard 同时满足时才返回 COMPLETE

H4 没有 receipt 的 unknown outcome 只有在覆盖精确 identity、effect set、水位、retention/lifecycle 的 authoritative MISS 和当前 permission、protected guard 同时成立时才允许 RETRY_ALLOWED

若任一 duplicate、extra effect、same-count swap、wrong run/update/attempt、invalid approval、MISS conflict 或 TOCTOU 被 full_reference 判为 COMPLETE，则推翻 H3 的当前模型实现

## Action-integrity state

- Current permission 仅用于新 effect retry，已完成且历史授权合法的 effect 不因当前 permission revoked 自动失效
- Historical occurrence 仅由 synthetic exact receipt journal 表示，ACCEPTED、COMPLETED、validator 状态与 billing Action 均不替代 receipt
- Historical authorization 按每个 effect 的 task、update、effect、approval、有效区间与 revocation tick 独立判断
- Prior-effect HIT、authoritative MISS 与 UNKNOWN 分开，MISS 必须覆盖 workflow/run/update/attempt/target、A+B 集合、水位与 retention
- Current completion 需要 current A+B UID membership、revision、done predicate、read-after-effect 与 protected guard
- Temporal order 需要 acceptedAt <= effect tick <= completedAt < current readAt < protected commitAt，所有 tick 均为模型值
- Verifier independence 只有分离实现，没有独立数据源、独立语义推导或外部 authority

## 强反例

Update ACCEPTED 且没有外部 effect 时 accepted proxy 报 COMPLETE，reference STOP_UNKNOWN

Update COMPLETED 且 A+A 重复收据或额外 C 收据时 completed proxy 报 COMPLETE，reference RECONCILE

当前成员从 A+B 变为 A+C 且数量仍为 2，或 B 保留同名但 UID 被替换，两个弱代理继续 COMPLETE，reference RECONCILE

已覆盖的 authoritative MISS 与 positive A/B receipt 同时出现，reference EVIDENCE_CONFLICT，不把负证据吞并为 HIT 或将 MISS 误用为 retry permit

Covered MISS、当前 permission revoked 或 protected guard 缺失分别返回 BLOCKED / STOP_UNKNOWN，不能因为 Update accepted 就发出非幂等新 effect

当前 permission 在合法历史 effects 之后 revoked，reference 仍可 COMPLETE，证明模型没有把当前权限错误倒推成历史授权
