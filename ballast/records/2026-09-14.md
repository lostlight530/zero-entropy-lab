## 研究问题

旧 effect 已经发生且 completion 未持久化, recovery 时 approval issuer 已从 signing key `k1` 轮换到 `k2`, 恢复器如果只使用当前 JWKS 或当前 issuer generation 验证历史 approval, 是否会错误否定过去合法 effect

反方向问题是如果恢复器只检查 approval 存在而不绑定 historical `kid` 或 issuer generation, 是否会把从未受信任的历史 key `k0` 对应 approval 错误恢复为 valid completion

本轮把三个事实分开: historical occurrence, historical approval key generation and trust, current approval for any new effect

## 来源依据

查询日期为 2026-09-14

- [RFC 7515 JSON Web Signature](https://www.rfc-editor.org/rfc/rfc7515.html) 的 4.1.4 与 6 说明 `kid` 用于指示保护 JWS 的具体 key, 可以显式信号 key change, 接收方需要能够确定实际用于签名的 key, 且用于信任判断的 key identification 信息需要受到完整性保护. 本轮只采用有限命题: 历史签名证据需要绑定具体 signing key identity, 不把 JWS 直接等同于人工 approval
- [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html) 的 signing key rotation 说明 signer 通过 `kid` 信号新 key, verifier 遇到未知 `kid` 时重新获取 JWKS, 并建议 JWKS 在合理时间内保留近期退役 signing keys 以支持平滑过渡. 本轮只采用有限命题: current key set 与 historical verification key lifecycle 可以不同, key rotation 本身不应自动抹除仍可验证的历史签名

两个独立规范共同支持有限设计前提: historical authorization evidence 需要绑定产生它的 key identity, current issuer key 不能替代 historical key identity. 外部来源不证明本地 valid_completion、effect_total 或 PASS

## 可证伪假设

- H1: recovery 时只使用 current JWKS 或 current issuer key generation 验证 historical approval 足以判断历史 completion
- H2: historical receipt HIT 加 approval 存在即可恢复 valid completion, 不需要绑定 historical signing key identity 与该代际的 trust
- H3: historical occurrence、historical approval key generation and trust、current approval for new effect 是三个不可互相替代的事实
- H4: prior HIT 应按 historical `kid` 与对应 historical trust evidence 验证旧授权, prior MISS 才转入 current issuer key 与 current approval 门决定是否允许新 effect
- H5: completed replay 必须从 production entry 重入并保持零新增 effect

H1 的反证条件是 authorized-hit-rotated: historical approval 由受信任 `k1` 产生, recovery 时 current key 已为 `k2`, current-jwks-only 因 key mismatch 拒绝历史合法 completion

H2 的反证条件是 unauthorized-hit-unknown-kid: historical effect 存在但 approval key 为从未受信任的 `k0`, unbound-approval 仍只凭 approval presence 标记 valid completion

## 控制条件

- authorized-hit-rotated: prior=HIT, historical_kid=`k1`, historical_trusted=1, current_kid=`k2`

## 强反例

第一强反例攻击 current issuer key 足以验证 historical approval

authorized-hit-rotated 的 effect 已由历史受信任 `k1` approval 合法授权, recovery 时 current issuer key 已切换到 `k2`. current-jwks-only 虽没有新增 effect, 但产生 false negative completion, 说明 current key mismatch 不能自动否定历史授权

第二强反例攻击 approval presence 足以恢复 historical HIT

unauthorized-hit-unknown-kid 的 effect 确实存在, 但 historical approval key 为从未受信任的 `k0`. unbound-approval 仍 valid_completion=1, 说明 occurrence 加 approval presence 不能替代 key-generation trust binding

反方向强反例是 miss-current-valid

prior effect 确认未发生且 current `k2` approval 有效时, generation-bound-reconcile 应允许一次必要 effect, 不能因为强调 historical verification 而永久零写入

## 路径比较

- current-jwks-only 只使用当前 key material, 操作较少但在合法 key rotation 后对 historical HIT 产生 false negative
- unbound-approval 同样操作较少, 可以恢复合法旧 HIT, 但也接受从未受信任的 historical key, 产生 false positive
- historical-key-registry 能正确判断 HIT 的 historical authorization, 但本身不定义 prior MISS 后的新 effect current permission
- generation-bound-reconcile 对 HIT 绑定 historical key generation and trust, 对 MISS 绑定 current key 与 current approval, 在历史和当前两个授权平面之间保持分离
- stronger path 在 HIT 场景增加 historical key lookup, 但同时消除两类方向相反的错误, 结果质量优先于少一次操作
- 本地 fixture 与 Python 进程耗时不外推真实 JWKS、HITL 或远端授权系统性能

## 暂时结论

证据状态为观察

本轮支持 H3、H4、H5, 推翻 H1、H2

current issuer generation 只描述当前验证或签发状态, 不能反向替代 historical approval 产生时的 signing key identity

historical occurrence 与 historical approval key trust 仍是两个事实; receipt HIT 或 approval presence 不能证明旧 effect 当时由可信 key generation 授权

对 prior HIT 的 completion recovery 需要绑定 historical approval identity、historical `kid` 或等价 issuer generation 与当时可验证的 trust evidence; 对 authoritative MISS 才转入 current issuer key 与 current approval 门决定新的 protected effect
