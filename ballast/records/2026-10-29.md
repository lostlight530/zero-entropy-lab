## 研究摘要

本轮只研究一个新机制: Cloud Tasks HTTP dispatch deadline 结束监听后, 旧 worker 仍可能继续处理, 同时新 attempt 被重新派发, task-name dedup 与 2xx 响应均不是下游不可逆 effect 的独立完成证明

实际在 V8 isolate 执行 producer 和单独实现的 primitive-fact verifier, 使用 49 个 reset-per-scenario authored synthetic fixtures, 三条决策路径和 147 行模型输出, 不把 49 个场景算作 49 个独立执行窗口

本轮无真实 Cloud Tasks API 调用, 无真实 external sink, 无真实 authority 查询, 所有 worker fence、receipts、approval、MISS 和 completion guard 都是可证伪的模型前提, 不是云端已证实事实

## 研究问题

Cloud Tasks HTTP worker 已返回 2xx 或同名 task 创建被去重拒绝时, 能否推断指定 run/attempt/target 的 A+B 非幂等 effects 曾获合法授权且当前任务完成

当第一个 attempt 超过 dispatchDeadline 后仍继续执行, 后续 attempt 重试, 旧 worker 未被 sink fence, receipt A+A 重复、A+C 等量替换、同名 task 新 incarnation、历史 HIT 与 covered MISS 冲突、授权撤销或 protected completion revision 漂移时, 哪些代理会产生 model-relative false COMPLETE

## 来源依据

2026-10-29 Asia/Shanghai 实际访问并核对当前文档, Google 文档于 2026-10-26 UTC 标记最近更新, 只支持 Google Cloud Tasks 自身 API 合同

- [Google Cloud Tasks Task REST resource](https://docs.cloud.google.com/tasks/docs/reference/rest/v2/projects.locations.queues.tasks) 明确 dispatchDeadline 触发 DEADLINE_EXCEEDED 与 retry, Cloud Tasks 停止监听响应并不保证 worker 停止执行, dispatchCount 包含尚无响应的 attempt
- [Google Cloud Tasks overview](https://docs.cloud.google.com/tasks/docs/dual-overview) 明确 at-least-once delivery、2xx worker response、task-name dedup 和删除后最多 24 小时的 task-name 记忆, 此窗口不是 downstream effect history
- [Google Cloud Tasks manage queues and tasks](https://docs.cloud.google.com/tasks/docs/manage-queues-and-tasks) 明确可以删除已派发 task, 但不提供删除即撤销外部 worker effects 的保证
- [AWS SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html) 为不同 publisher 与不同产品的 at-least-once / consumer duplicate 对照, 不能当作 Google Cloud Tasks 的独立实证

前三份同属 Google publisher, 仅 AWS 提供不同 publisher 的跨产品对照, 没有两个独立 publisher 直接证明 Cloud Tasks 的特定实现行为

## 可证伪假设

H1 http_proxy 仅凭最新 2xx 将任务判 COMPLETE, 在 old worker 未受保护、receipt 缺失或 effect-set 错配时产生 false COMPLETE

H2 name_proxy 将 task-name dedup 被拒且仍在 24 小时模型窗口内视为 COMPLETE, 在历史 effect 缺失、同名新 incarnation 或重复成员时产生 false COMPLETE, 在窗口结束但历史完成真实存在时产生 false negative

H3 full_reference 只有在 exact task/run/attempt/target incarnation、历史 HIT 查询范围、A+B 精确 receipt、effect-time grant、old worker protected fence 与当前 membership+revision protected completion 全部成立时才给 COMPLETE

H4 covered authoritative MISS 与无 positive receipt、current permission、old worker fence 和 protected retry guard 同时成立时, 模型才允许 RETRY_ALLOWED, covered MISS 与 positive receipt 冲突必须 EVIDENCE_CONFLICT

如果 reference 将任何重复/额外 receipt、等量成员替换、stale fence、非法授权、未知历史或未受保护的 current predicate 判为 COMPLETE, 则推翻 H3 在本轮输入域内的实现

## Action-integrity state

- Current permission: 只用于新的非幂等 effect retry, 当前撤销不追溯抹去过去合法 effect
- Historical occurrence: synthetic exact receipts 与覆盖两次 attempt 的查询, Cloud Tasks dispatchCount / 2xx / task-name dedup 不替代 sink receipt
- Historical effect-time authorization: 每个 effect 的 grant identity、from/to、revokedAt 和 effectAt 单独检查
- Prior effect: hit / authoritative miss / unknown 分开, MISS 要求 exact task/run/queue/incarnation/target UID/effect set/attempts、水位、retention、lifecycle 和完整查询
- Current completion: exact A+B UID set、target incarnation、current state、predicate completeness、coherent revision 与 protected guard
- Temporal ordering: 全部是同一合成整数 tick 域, 不代表跨服务可信时间或实际 happens-before
- Verifier independence: 代码函数独立实现, 但共享 fixture、语义合同、V8 环境和无外部权威

## 强反例

- deadline_worker_unfenced: deadline 超时与 HTTP 204 并存, old worker 未获 protected fence, 两条弱代理仍 COMPLETE, reference STOP_UNKNOWN, 不能把 Cloud Tasks 停止监听解释为 worker 已停止
- same_count_A_C: A+B 的两条 receipt 数量仍为 2, B 被 C 替换, 两条弱代理 COMPLETE, reference RECONCILE, count equality 不证明 effect-set 完整
- prior_miss_positive_conflict: 覆盖完整的 synthetic authoritative MISS 与 A+B positive receipts 同时存在, reference EVIDENCE_CONFLICT, 不把 negative 查询悄悄覆盖 positive receipt
- miss_covered_safe_retry: 无 receipt 且覆盖完整的 synthetic MISS、当前权限与保护 fence 均成立, reference RETRY_ALLOWED 而不是 COMPLETE
- current_revision_drift 与 current_extra_member: 即使历史 A+B receipts 合法, current completion guard 或 membership 不成立仍拒绝 COMPLETE
- grant_revoked_after_effect: grant 在两个 effect 之后撤销, reference 仍 COMPLETE, 证明模型没有用 current revocation 追溯否定合法历史

## 路径比较

http_proxy 只观察 HTTP status, name_proxy 只观察 dedup rejection 和模型化 age, 均忽略 old-worker effect race、sink authority、effect-set identity、historical grant 和 current completion

full_reference 增加查询范围、授权、exact receipt set、protected old-worker fence 与 guarded completion, 因而更保守, 但它的零未解释分歧只说明两个实现同意作者的模型, 不说明真实 Cloud Tasks 或外部 sink 正确

## 暂时结论

受控模型内, deadline cancellation、2xx response 和 task-name dedup 不足以推断历史 effect occurrence、合法 effect-time authorization 或当前任务完成, 而 protected old-worker fence 与完整 authoritative effect-set proof 是避免 unsafe completion/retry 的额外前提

这是与此前 SQS / Temporal 等研究不同的 Cloud Tasks deadline-to-worker execution boundary, 但尚不能晋升 CASE 或 NOTES 的新独立真实系统发现, 结论状态为 PARTIAL / BOUNDED_MODEL_ONLY
