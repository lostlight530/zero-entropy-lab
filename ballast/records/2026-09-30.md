## 研究摘要

This Daily tests a boundary left open by the 2026-09-29 protected-predicate experiment.

A transaction or advisory lock can protect exactly the identity supplied to it while the real decision depends on a wider scope such as target incarnation, request principal, admission parameters, namespace state or dynamic membership.

The study therefore separates coordination ownership from current permission and asks whether the coordination key covers the actual decision scope.

No real external non-idempotent effect is executed or blindly retried.

## 研究问题

Can a correctly acquired coordination primitive prove valid completion when the application-defined coordination identity is narrower than the real authorization, target and membership decision scope.

## 来源依据

Checked 2026-09-30.

PostgreSQL 17 explicit-locking documentation states that advisory locks have application-defined meanings and that the system does not enforce correct application use. It also distinguishes transaction-level advisory locks, which are automatically released at transaction end, from session-level locks.

PostgreSQL 18 advisory-lock function documentation states that advisory-lock resources are identified by application-defined integer keys. These semantics support the claim that PostgreSQL protects the chosen lock identity but does not prove that the application chose a complete task identity.

Kubernetes ValidatingAdmissionPolicy documentation states that CEL validation expressions can access object, oldObject, request, params, namespaceObject and an authorizer for the authenticated principal. It also states that matching policy, binding and parameter combinations are evaluated for admission. These semantics show that a real authorization decision can depend on a broader request and policy context than one logical target name.

These sources define coordination and policy primitives only. They do not prove this local combined fixture or a real PostgreSQL plus Kubernetes deployment.

## 可证伪假设

H1 a logical target-name coordination key is sufficient.

H2 binding the coordination identity to target incarnation is sufficient.

H3 adding current request authority and target incarnation is sufficient even if policy parameters or dynamic membership are outside the protected projection.

H4 a full-scope coordination identity and protected predicate that cover target incarnation, current principal and permission, policy or namespace parameters, membership, prior-effect class and transaction outcome reject the modeled false completions.

## 控制条件

Eight scenarios vary target incarnation, current principal and permission, policy or namespace parameter scope, dynamic membership, prior-effect class, historical authorization and transaction commit outcome.

Four paths are logical-name, target-incarnation, authority-target and full-scope.

All paths preserve prior UNKNOWN as UNKNOWN and reject a prior HIT whose modeled historical authorization is invalid.

The comparison isolates how much of the live decision scope is represented by the coordination identity.

## 实验设计

Evaluate 8 scenarios x 4 paths = 32 modeled decisions.

The compared paths are:

- logical-name: coordinates only the application logical target name
- target-incarnation: adds concrete target incarnation
- authority-target: adds current principal or permission to the target incarnation
- full-scope: additionally covers policy or namespace parameters and current membership, and requires successful protected transaction commit

Producer output is generated three times for determinism.

A separately written verifier recomputes all path decisions from primitive scenario fields without calling the producer decision function.

No real PostgreSQL advisory lock, Kubernetes admission request or external effect is executed.

## 强反例

same-logical-name-new-incarnation defeats H1 because one application logical name can refer to a replacement target incarnation.

request-principal-authority-changed defeats H1 and H2 because target identity can remain stable while the authenticated principal or current permission changes.

namespace-or-policy-param-drift defeats H1-H3 because a coordination key covering target and principal can still omit a policy parameter or namespace dependency used by the real admission decision.

dynamic-membership-expanded likewise defeats H1-H3 because the protected action set can change without changing the selected target key.

A prior UNKNOWN remains a safe stop, and historical HIT with invalid modeled historical authorization remains rejected, regardless of coordination ownership.

## 路径比较

logical-name coordinates the smallest domain and has four disagreements because logical identity aliases target reincarnation, authority changes and broader decision dependencies.

target-incarnation fixes the direct target alias but still omits principal, policy and membership scope.

authority-target covers current principal or permission plus target incarnation but still omits policy or namespace parameters and dynamic membership.

full-scope has zero disagreement inside this bounded fixture because the protected identity and predicate cover every modeled decision dependency and preserve prior-effect and historical-authorization axes.

## 暂时结论

Observation.

Reliable coordination does not prove correct coordination scope.

Coordination ownership is not current execution permission.

An application-defined advisory-lock key is not automatically a complete task identity.

A protected transaction can still produce a false completion when the protected predicate or coordination key omits a real decision dependency.

H4 is supported only inside this controlled model and is not a real PostgreSQL or Kubernetes runtime result.

## AGI-scale action-integrity relevance

Long-running autonomous systems can coordinate work through application-defined task IDs while authorization and target scope are determined by richer state from identity, policy, namespace, delegated authority and dynamic membership services.

A coordination primitive can therefore operate correctly while protecting the wrong semantic domain.

The action-integrity requirement is to bind coordination identity to the complete decision scope, not merely to acquire a lock successfully.

This is not an AGI capability claim.
