# Ballast 日记录 2026-08-21

类型: 每日专题
主题: receipt 保留期短于合法恢复窗口时的过期缺失与证据回退

## 研究问题

当 unknown outcome 的 authoritative receipt 查询本身成功且读取最新权威状态, 但历史 receipt 已按保留策略过期时, 当前的 `receipt miss` 是否足以证明此前没有副作用

本轮承接 2026-08-20 的 freshness 结论, 但改变故障位置: 不是副本滞后, 而是权威存储已经按策略删除历史 receipt, 同时任务仍处于允许恢复的业务有效期内

重点检验三个边界: receipt retention 是否需要覆盖仍可能合法恢复的时间窗, receipt 过期后能否依赖远端 effect evidence 恢复 completion, 以及过宽 marker fallback 是否会把无关历史误认成当前 effect

## 来源依据

查询日期为 2026-08-21

- [Stripe API idempotent requests](https://docs.stripe.com/api/idempotent_requests) 说明服务保存首个请求结果用于同 key 重试, 并允许至少 24 小时后清理 key; 原 key 被清理后再次使用会形成新请求. 适用边界是 Stripe API 的 idempotency key 合同, 不直接证明任意 receipt store 的保留策略
- [AWS Lambda Powertools idempotency](https://docs.aws.amazon.com/powertools/python/latest/utilities/idempotency/) 说明 idempotency record 有显式 expiration window, 默认一小时; 记录过期后相同 payload 不再被视为幂等重复, 可以再次执行 transaction. 适用边界是 Powertools 的持久层与过期语义, 不等价于任意外部 effect sink

两个独立官方来源共同支持一个设计前提: idempotency 或 dedupe 证据通常具有有限时间窗口, 超过窗口后相同 identity 可能再次被当作新操作

把这一时间窗口与 Agent 任务的合法恢复窗口, current permission 和 authoritative remote effect evidence 联合起来属于本轮待证伪假设

## 可证伪假设

- H1: 只要 receipt 查询是 authoritative current read, 返回 miss 就可以执行新的非幂等 effect, 无需关心 receipt 是否可能因 retention 到期而消失
- H2: 如果 receipt retention 至少覆盖任务仍可能合法恢复的时间窗, unknown-outcome replay 可以在合法恢复期间从 receipt hit 恢复 completion 而不重复 effect
- H3: receipt 已过期时, 绑定完整 action 与 target identity 的远端 effect evidence 可以作为替代 prior-effect 证据
- H4: 只按 task marker 或 correlation marker 回退会产生 false hit, 错误跳过当前仍必要的 effect
- H5: 当前任务已经越过 valid_until 时, 即使 receipt 已过期, current permission gate 也应在任何新 effect 之前停止, 因而不需要靠无限 retention 维持该任务的执行安全

H1 的反证条件是已有 effect 与 receipt, receipt 在合法恢复前过期, replay authoritative miss 后产生第二次 effect

H2 的反证条件是 receipt retention 已覆盖 valid_until, 但合法恢复期间仍无法从 receipt hit 保持 effect 总数 1

H3 的反证条件是 receipt 过期后 exact effect identity 已存在, identity fallback 仍执行第二次 effect

H4 的反证条件是只有同 task marker 但 action 或 target 不同的无关历史时, marker fallback 仍正确执行当前必要 effect

H5 的反证条件是 replay 已越过 valid_until 后仍产生新 effect

## 控制条件

- task identity 固定为 `task-a`, 当前 action 固定为 `charge:10`, target incarnation 固定为 `account:uid-1`
- task valid_until 固定为逻辑时刻 48, 首次 unknown attempt 在时刻 0, 合法迟到恢复在时刻 25, 过期恢复在时刻 49
- relevant world state, current intent, ownership, credential, approval 与 target incarnation 除指定反例外保持不变
- 每次真实 effect commit 前都重新执行 current permission check
- receipt 查询均为当前权威状态读取, 不重复 2026-08-19 的 query error 或 2026-08-20 的 stale replica 故障
- `receipt-ttl-only` 使用固定 24 单位 retention, miss 后直接执行 effect
- `receipt-horizon-bound` 让 receipt 保留到任务合法恢复窗口之后, 合法恢复期间优先 receipt hit
- `marker-fallback` 在 receipt miss 后只按 task marker 查远端历史
- `identity-fallback` 在 receipt miss 后要求 task, normalized action 与 target incarnation 全部匹配
- `unrelated-marker` 只注入同 task marker, 但 action 为 `charge:99` 且 target 为 `account:uid-other`
- completion 与 effect 分开保存, unknown 场景固定为 effect 与 receipt 已保存后, completion 保存前中断
- 夹具只使用 Python 标准库与系统 awk, 不访问真实 Stripe, AWS 或外部 effect sink

## 实验设计

1. 四条路径执行 normal-no-prior, 时刻 25 没有历史 effect 与 receipt, 检查是否各执行一次必要 effect
2. 四条路径执行 expired-after-effect, A 在时刻 0 已产生 effect 1 与 receipt, completion 保存前中断, B 在时刻 25 重新进入 production entry
3. `receipt-ttl-only`, `marker-fallback`, `identity-fallback` 的 receipt 在时刻 24 到期, `receipt-horizon-bound` 的 receipt 保留到时刻 49
4. 四条路径执行 unrelated-marker, 只存在同 task marker 但 action 与 target 均不同的远端历史, 用于攻击 marker fallback
5. 四条路径执行 task-expired, A 已产生 effect 1 且 completion 缺失, B 在时刻 49 重放, 用于检验 current permission 是否先于新的 effect
6. 四条路径执行 completed-replay, 检查 completed short circuit 是否会掩盖 retention crash-window
7. producer 输出 scenario, path, effect_count, completed, result, ops 与 event_order, 完整运行三次并比较 stdout TSV SHA-256
8. 独立 Python verifier 不导入 producer, 从 TSV event_order 重建 effect 数与 permission-before-effect 时序, 并核对关键反例
9. awk 第二验证实现独立复核 expired-after-effect 重复 effect, horizon-bound 单次 effect, unrelated-marker false hit 与 task-expired 停止
10. producer 与 verifier 执行 `py_compile`

## 强反例

- unrelated-marker 证明 receipt 过期后不能退化成只按 task 或 correlation marker 判定已完成, 否则无关 action 与 target 也会形成 false hit 与零写入假完成
- task-expired 证明 receipt retention 不需要被解释为无限历史保存才能阻止该任务继续执行, current permission gate 可以在合法恢复窗口结束后独立阻止新 effect
- normal-no-prior 证明保留更久的 receipt 不会在没有历史 receipt 时阻止必要 effect, 四条路径都执行一次
- completed-replay 四条路径都只保留 1 次 effect, 因为 completion 在 receipt 查询之前短路, 所以 completed replay 仍不能替代 effect 已发生, receipt 后来过期, completion 缺失的恢复窗口
- expired-after-effect 中四条路径最终 completed 或停止状态并不能单独区分一次 effect 与两次 effect, 仍需要 effect_count 与 event_order

## 暂时结论

状态保持观察

本轮支持把 authoritative miss 再增加一个时间维度: 即使查询没有报错, 读取也足够新鲜, miss 仍可能表示历史 receipt 已按 retention 过期, 而不是此前没有 effect

对于仍处于合法恢复窗口的非幂等 unknown outcome, receipt retention 应与任务可能恢复的时间范围协调, 或在 receipt 过期后使用仍可权威查询且绑定完整 action 与 target identity 的 effect evidence

只按 task marker 回退不安全, 因为它能把同 task 下语义不同的历史 effect 误认成当前完成

当前执行权限与 prior-effect evidence 继续保持两条独立证据链: valid_until 过期可以阻止新 effect, 但在 valid_until 之前不能用 permission valid 推断历史 effect 不存在

本轮与 7 月 retention expiry 实验的差异在于: 旧实验验证 dedupe key 过期后的重复创建与 intent-bound reconciliation, 本轮把 receipt retention 明确放入 unknown-outcome production replay, task valid_until 与 exact target/action fallback 的联合条件中

## 复验条件

以下条件之一出现时优先复验

- receipt retention 小于队列最大重试年龄, 人工恢复窗口或任务 valid_until
- receipt store 会物理删除记录, 且删除后 authoritative query 无法区分 expired 与 never-seen
- 远端 sink 提供 effect lookup, 但 lookup key 不包含 action digest 或 target incarnation
- completion store 与 receipt store 具有不同 retention policy
- 任务 valid_until 被续期或重新批准, 但 receipt retention 没有同步扩展
- receipt retention 或 remote effect evidence 在多区域复制中具有不同可见窗口

## 事实分层

### 已验证事实

- 在受控模型中, 固定 24 单位 receipt 已过期但任务仍可合法恢复时, authoritative miss 后直接重试使 effect 从 1 增加到 2
- 把 receipt 保留到合法恢复窗口之后时, 时刻 25 replay receipt hit, effect 保持 1
- receipt 过期后, exact task/action/target identity fallback 命中历史 effect 并只恢复 completion, effect 保持 1
- 只按 task marker fallback 在无关 action 与 target 历史下 effect=0, completed=1, 形成零写入假完成
- replay 越过 valid_until 后, 四条路径都在新 effect 前停止
- 三次 producer 轨迹 hash 完全一致, Python verifier 三次通过, awk 第二验证实现通过

### 基于证据的推断

- authoritative miss 的充分条件不仅包括 query success 与 read freshness, 还应考虑证据是否可能因 retention 被合法删除
- receipt retention 与 task retry or recovery horizon 存在合同关系, 但不必简单等同为永久保存
- receipt 过期后的 fallback 必须继续满足 effect identity 与 provenance 约束, 不能退化成宽 marker
- current permission 只能回答现在能否执行, 不能证明此前 unknown attempt 没有 effect

### 未验证事项

- 未验证真实 Stripe key pruning 的精确删除时刻, Stripe 内部持久化实现或其业务对象查询语义
- 未验证真实 AWS Powertools persistence layer, DynamoDB TTL 删除延迟或跨区域行为
- 未验证 receipt retention 与 completion retention 的真实配置漂移
- 未验证真实 remote effect lookup 的一致性, retention, tombstone 与 target migration
- 未验证任务续期, 重新批准或 ownership takeover 是否应同步延长 receipt retention
- 未验证 retention 成本, 存储规模或隐私删除要求与恢复安全之间的实际权衡
