## 研究摘要

One deterministic local experiment evaluates whether Kubernetes Indexed Job success signals prove a separate task-defined external effect contract. Thirteen scenarios and four decision paths yield 52 bounded decisions. No live Kubernetes mutation, external sink call or non-idempotent effect was performed.

## 研究问题

When an Indexed Job reports SuccessCriteriaMet or terminal Complete, does that prove the exact required external effects occurred once, were historically authorized, belong to the correct incarnations and still satisfy the current task semantics.

## 来源依据

Verified on 2026-10-09 Asia/Shanghai against [Kubernetes Jobs documentation](https://kubernetes.io/docs/concepts/workloads/controllers/job/) and [Job API reference](https://kubernetes.io/docs/reference/kubernetes-api/batch/job-v1/).

The Job successPolicy may intentionally accept only a subset of succeeded indexes. SuccessCriteriaMet is an intermediate controller milestone, and the terminal Complete condition follows Pod termination for Kubernetes 1.31 and later. A terminating failure policy can take precedence over success policy. Both pages share the Kubernetes documentation publisher, not independent source lineages. None of these contracts independently verifies external business effects.

## 可证伪假设

H1 SuccessCriteriaMet proves task-defined external completion. H2 terminal Complete proves task-defined external completion. H3 controller lifecycle checks suffice. H4 exact effect-set, historical authorization, prior-effect coverage, identity, permission and current postcondition checks reject the modeled false completions.

H1 is falsified by an accepted success subset with a missing required external effect. H2 and H3 are falsified by duplicate occurrence, authorization invalidity, stale target incarnation or reversed current postcondition. H4 is falsified by any modeled false positive in the strongest path.

## 控制条件

Thirteen immutable scenarios use a modeled Indexed Job and two task-required external effects a and b. The Job controller success subset is not assumed equal to the task effect set. Scenario dimensions vary one or more explicitly named fault conditions; multi-axis cases do not claim single-variable causation. Unknown non-idempotent effects are never blindly retried. Revocation after a valid historical effect does not retroactively invalidate it.

## 实验设计

The four paths are criteria-only, terminal-only, controller-lifecycle, and full-integrity. Controller-lifecycle waits for terminal state and Pod termination and honors failure precedence. Full-integrity additionally checks exact Job and target incarnation, prior-effect evidence, historical authorization, duplicate occurrence, required effect-set coverage, current permission if more work is needed and current postcondition.

The Python producer writes scenario JSON and decision CSV; a separately written Node.js verifier recomputes expected labels from primitive fields without calling producer decision functions. Reproduction scripts and the original evidence CSV accompany this Daily under ballast/tools and ballast/evidence.

## 强反例

Success-policy-subset-missing-required-effect: the modeled Job accepts a subset of succeeded indexes while required external effect b is absent, so controller-only paths incorrectly report verified. This is a business task-contract mismatch, not a Kubernetes controller bug.

Duplicate-index-effect-occurrence: terminal success coexists with two modeled occurrences for one external effect. Controller status does not prove exactly-once external effect execution.

Revoked-permission-after-valid-effect: historical effects and current completion remain valid despite current permission revocation, provided no new effect is required. This defeats a stronger-but-wrong rule that current revocation invalidates all past effects.

Failure-policy-preempts-success models documented terminating-policy precedence; real simultaneous controller timing is NOT_TESTED.
