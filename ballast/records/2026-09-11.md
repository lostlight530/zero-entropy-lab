## 研究问题

当非幂等 effect 已经成功提交但 completion 丢失, 恢复发生在 idempotency token 的服务端保留窗口之外时, 继续复用同一稳定 token 是否仍能作为零重复副作用与 historical occurrence 的充分证据

本轮攻击窗口为 `EFFECT committed -> completion missing -> interruption -> token retention expires -> production entry replay`

关键问题不是 token identity 是否稳定, 而是服务端是否仍承诺记得该 identity. 如果去重记录已经过期, 同一 token 字符串是否还能安全代表原 attempt

两个来源来自不同厂商, 都支持有限时间幂等记忆这一设计前提, 不证明本地 effect_total、PASS 或真实 API 在过期后必然创建重复资源

## 可证伪假设

- H1: 只要重放继续使用与旧 attempt 相同的 idempotency token, 无论恢复延迟多久都不会产生第二次 effect
- H2: token retention 已过期但 prior-effect evidence 仍为 unknown 时, ttl-aware path 应停止新 effect 而不是把 token miss 当 authoritative miss
- H3: token 过期后如果 authoritative receipt 能证明 historical HIT, 可以恢复旧 effect 且零新增 effect
- H4: token 过期后如果 authoritative receipt 能证明 historical MISS 且 current permission valid, 可以执行一次必要 effect
- H5: exact sink identity query 若可用, 可以作为 token retention 之外的竞争性 historical evidence
- H6: current permission invalid 仍只阻止新的 sink attempt, 不阻止只读 historical reconciliation
- H7: completed replay 从 production entry 重入时保持零 sink call 与零新增 effect

H1 的反证条件是 expired-hit-valid 初始已有一次 effect, token-replay 在 token EXPIRED 后再次执行, effect_total 从 1 增长到 2

H2 的反证条件是 ttl-aware-stop 在 token 过期且 prior 未解析时仍调用 sink

H4 的反证条件是 expired-miss-valid 中 authoritative receipt 明确 MISS 且 permission valid 后仍无法产生唯一必要 effect

## 控制条件

- effect identity 固定为 `op-111`
- within-ttl-hit-valid 初始 effect_total=1, token state=ACTIVE, receipt=HIT, sink identity=HIT, current permission valid
- expired-hit-valid 初始 effect_total=1, token state=EXPIRED, receipt=HIT, sink identity=HIT, current permission valid
- expired-miss-valid 初始 effect_total=0, token state=EXPIRED, receipt=MISS, sink identity=MISS, current permission valid
- expired-hit-cancelled 初始 effect_total=1, token state=EXPIRED, receipt=HIT, current permission invalid
- expired-unknown-valid 初始 effect_total=1, token state=EXPIRED, receipt 与 direct sink query 都为 UNKNOWN
- completed-replay 已有持久化 completion, token state=EXPIRED, 从相同 production entry 重入
- token-replay 只携带稳定 token 并依赖 sink 当前的 token dedup 记录
- ttl-aware-stop 在 token retention 不覆盖 old attempt 时保持 prior=UNKNOWN 并安全停止
- receipt-reconcile 使用独立 authoritative receipt 分类 historical occurrence
- sink-identity-reconcile 使用 exact sink effect identity 历史查询, 只在该能力真实存在时适用
- fixture 只使用 Python 标准库与系统 awk

## 强反例

第一强反例攻击 stable token 等于永久去重保证

within-ttl-hit-valid 中完全相同 token 正常抑制 duplicate, 但只改变 token retention state 为 EXPIRED 后, expired-hit-valid 的相同 token-replay 就产生第二次 effect. 这把失败定位到服务端 retention coverage, 而不是 token identity 不稳定

第二强反例攻击保守停止等于完整恢复

ttl-aware-stop 在 expired-hit-valid 中安全阻止 duplicate, 但在 expired-miss-valid 中也保持 effect_total=0. 因而识别 token expiry 只能证明不能盲重试, 不能单独证明任务已经完成

第三强反例使用 authoritative MISS

expired-miss-valid 的 receipt-reconcile 明确确认历史未发生后, 在 current permission valid 下执行一次必要 effect. 因而本轮结论不是 token 过期后一律永不执行, 而是需要换用仍覆盖历史窗口的 authoritative evidence

第四强反例使用 exact sink identity

如果 sink 具有独立的 exact historical identity query, expired-hit-valid 一次 direct query 即恢复 HIT. 因而 receipt 不是唯一正确机制, 核心合同是历史证据的 identity、provenance、freshness 与 lifecycle coverage

## 路径比较

- token-replay 在 ACTIVE retention 内最低成本并保持 effect_total=1, 但过期后仍盲信同一 token 会产生 duplicate
- ttl-aware-stop 不调用 sink, 能阻止过期 token duplicate, 但 authoritative MISS 场景也无法恢复必要 effect
- receipt-reconcile 增加一次历史查询, 对 HIT 阻止 duplicate, 对 MISS 在 current permission valid 后只执行一次必要 effect
- sink-identity-reconcile 在 exact historical query 可用时同样能区分 HIT/MISS, 但很多外部 sink 不提供该能力
- expired-unknown-valid 中 evidence-aware 路径保持 UNKNOWN, 不把 retention expiry 或 query 不确定性伪装成 never executed
- current permission invalid 只阻止新的 sink attempt, historical HIT 仍可被只读确认
- 本地 Python 耗时不外推真实系统性能, 有效成本比较 sink_calls、authority queries、最终副作用正确性与历史证据完整性

## 暂时结论

证据状态为观察

本轮支持: stable idempotency identity 与服务端 retention coverage 是两个不同证明义务. token 字符串保持不变不能证明服务端仍保留旧 attempt 的去重状态

恢复窗口超过 token retention 时, token miss 或重新执行成功不能单独证明 prior effect 未发生. 在新的非幂等 effect 前需要能够覆盖旧 attempt 历史窗口的 authoritative receipt、exact sink identity 或等价证据

识别 token expiry 后安全停止是正确的防重复策略, 但不是完成证明. authoritative MISS 与 current permission valid 仍应允许一次必要 effect

## 事实分层

### 已验证事实

- ACTIVE token 基线下 historical effect 保持 1 次且没有新增 effect
- 只把 token state 改为 EXPIRED 后, token-replay 把 historical effect 从 1 次增加到 2 次
- ttl-aware-stop 在 token EXPIRED 时保持 prior UNKNOWN 且零 sink call
- authoritative receipt HIT 与 direct sink HIT 都在 expired-hit-valid 中恢复 historical effect 且零新增 effect
- authoritative receipt MISS 在 expired-miss-valid 中允许一次必要 effect
- expired-unknown-valid 保持 UNKNOWN 且零新增 effect
- completed replay 四条路径均零新增 effect与零 sink call
- producer 三次轨迹 SHA-256 完全一致, Python verifier 3/3 PASS, awk 3/3 PASS, producer/verifier py_compile PASS

### 基于证据的推断

- stable token identity 不能替代服务端 retention coverage
- token retention expiry 后的 dedup miss 不能自动升级为 authoritative prior-effect miss
- 安全恢复需要把 token lifecycle、historical effect evidence 与 current permission 分开建模
- 如果 exact sink identity 或长期 receipt authority 可用, 可以在 token retention 之外继续建立 historical occurrence evidence

### 未验证事项

- 尚未对真实 AWS ECS RunTask 或 Google requestId 接口跨过实际 retention window 执行非幂等 replay
- 尚未证明真实 API 在最小保证窗口之后必然忘记 token, 官方文档只给出有限保证或明确 TTL
- 尚未测试 token retention 与 authoritative receipt retention 同时过期
- 尚未验证跨服务 receipt 与 sink 无共享事务时的 retention expiry 组合
- producer 与 verifier 仍可能存在共同建模错误
