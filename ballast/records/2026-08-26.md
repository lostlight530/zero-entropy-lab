# Ballast 日记录 2026-08-26

类型: 每日专题
主题: 多资源后置条件分离读取造成的 fractured completion

## 研究问题

当 unknown outcome 恢复已经命中 exact historical receipt, 任务 completion contract 同时要求资源 A 与 B 当前都满足时, 如果恢复器分别读取 A 与 B, 两次读取各自都来自权威当前状态但属于不同线性化时点, 是否可能拼出一个从未真实存在过的 `A satisfied + B satisfied` 组合并错误保存 completion

本轮改变故障位置: 不攻击单资源 read freshness 或 final-read-to-completion TOCTOU, 而攻击多资源 completion evidence 的共同快照身份

关键窗口为 `read A at state S1 -> atomic state transition -> read B at state S2 -> synthesize pair -> completion`

## 来源依据

查询日期为 2026-08-26

- [etcd API](https://etcd.io/docs/v3.7/learning/api/) 说明 transaction 是 key-value store 上的原子 If/Then/Else, 可以对不同 key 的 value、version 或 revision 执行 conjunction compare, 并在一个原子请求中处理多个操作. 适用边界是 etcd 多 key transaction, 不直接证明任意 Agent 状态源都提供共同快照或多 key compare
- [PostgreSQL Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html) 说明 Read Committed 下连续两个 SELECT 可以因为中间并发提交而看到不同数据快照, Repeatable Read 让同一事务的连续查询看到同一稳定 snapshot, Serializable 进一步拒绝不能对应任意串行执行的并发结果. 适用边界是 PostgreSQL MVCC 与事务隔离, 不直接等价于跨服务多资源 postcondition

两个独立官方来源共同支持一个设计前提: 多个相关读取如果要共同证明一个业务不变量, 需要说明这些观察是否属于同一一致快照, 或在受保护提交时对全部相关状态执行原子条件核对

把该边界用于 Ballast 的多资源 current completion evidence 属于本轮待证伪假设

## 可证伪假设

- H1: 只要 A 与 B 的每次读取各自都是 authoritative current read, 分离读取后可以直接合并为当前 completion evidence
- H2: 对 A 与 B 各自再读一次可以消除 fractured view, 不需要共同快照或提交时绑定
- H3: 在同一 authoritative snapshot 中读取 A 与 B 可以阻止本轮跨时拼接, 但本轮不把它扩展为已经关闭 snapshot-read 到 completion-commit 的后续 TOCTOU
- H4: 分离读取后在 completion commit 时同时比较全部相关资源 revision, 可以识别 earlier observation 已经失效
- H5: 只比较最后一次读取时采样的 whole-store global revision 不一定能追溯绑定更早的资源读取, 同时还可能因无关 global change 产生额外冲突
- H6: completed replay 不能替代 fractured multi-resource read 窗口测试

H1 的反证条件是 A 在 S1 为 `marked`、B 为 `clean`, 状态原子切换到 A=`clean`、B=`marked` 后读取 B, 两个单独读取都返回 `marked`, 但从未存在 A 与 B 同时 `marked` 的 authoritative state

H2 的强反例是在 A1、B1、A2、B2 四次读取之间交替切换两种互斥状态, 让四次读取都返回 `marked`, 但任一时点仍只有一个资源满足

H4 的反证条件是 A 或 B 任一 observed revision 已变化而 pair compare 仍允许旧 completion 声明提交

H5 的决定性限制是 global expected revision 在较晚的 B 读取时才采样, 如果 A 的旧观察发生在更早 revision, global revision 此时已经更新为当前值, 最终 global compare 仍可能成功而无法证明 A 与 B 属于同一 snapshot

## 控制条件

- task、normalized action、target incarnations A 与 B、historical receipt identity 固定
- 历史 forward effect 已真实提交一次并写入 receipt, completion 初始缺失
- replay 时 task status、intent、ownership、valid_until、credential 与 approval binding 保持有效
- completion contract 固定要求 authoritative A=`marked` 且 B=`marked`
- fractured 场景初始状态为 A=`marked`, B=`clean`, A revision 2, B revision 2, global revision 10
- `swap` 是本夹具中的单个原子状态转换, 把状态在 `marked/clean` 与 `clean/marked` 之间切换, 同时推进 A revision、B revision 与 global revision
- `independent-reads` 分别读取 A 与 B 后直接合成结果
- `double-read` 依次读取 A1、B1、A2、B2, 仍不要求四次读取属于同一 snapshot
- `atomic-pair-snapshot` 在一个逻辑 snapshot 中同时观察 A、B 与两个 revision
- `global-compare-complete` 分离读取 A、B, 以较晚 B 读取时看到的 global revision 作为 completion compare 条件
- `pair-compare-complete` 分离读取 A、B, completion commit 时原子比较 A observed revision 与 B observed revision 是否都仍为 current
- compare 或 snapshot 发现 postcondition 不成立后, 每次真实恢复 effect 前记录 `B:permission_valid`
- 恢复 effect 把 A 与 B 一起恢复为 `marked`
- completed replay 重新进入同一 production entry 并通过 completion short circuit 返回
- 夹具只使用 Python 标准库和系统 awk, 不访问真实 etcd、PostgreSQL 或外部 effect sink

## 实验设计

1. 五条路径执行 normal-stable, A 与 B 全程都为 `marked`, 验证正常 receipt replay 不增加 forward effect
2. 五条路径执行 fractured-one-pass, 在 A 读取后原子交换 A/B 状态, 检查分离读取是否合成从未存在的共同完成状态
3. 五条路径执行 oscillating-fracture, 在 double-read 的四次资源读取之间交替切换状态, 检查重复读取是否仍可能全部读到单项 satisfied 但没有共同 satisfied snapshot
4. 五条路径执行 unrelated-global-change, 只在最终相关读取后推进无关 global revision, 检查 global compare 与 pair compare 的差异
5. 五条路径执行 completed-replay, completion 已存在后重新进入同一 production entry
6. producer 输出 scenario、path、effect_count、completed、A/B value、A/B revision、global revision、result、ops 与 event_order, 完整运行三次并比较 TSV SHA-256
7. 独立 Python verifier 不导入 producer, 从 event_order 重建 effect commit 数、permission gate、互斥状态切换顺序、compare conflict 与 completed short circuit
8. awk 第二验证实现独立复核 oscillating-fracture、pair compare、global compare 漏检与 unrelated global over-fencing
9. producer 与 verifier 执行 `py_compile`

`fractured-one-pass` 的 independent-reads event order 为先读取 A=`marked`, 随后原子切换到 A=`clean`, B=`marked`, 再读取 B=`marked`, 最终保存 completion

因此两个 read 各自都是真实 authoritative observation, 但它们不能组成同一个 authoritative pair snapshot

更强的 `oscillating-fracture` 中 double-read 四次读取分别都得到对应资源 `marked`, 但状态在每次读取之间交替, 任一实际状态仍只有 A 或 B 其中一个满足, 最终得到 effect 1、completed 1、A=`clean`、B=`marked`

`global-compare-complete` 在 fractured-one-pass 中同样错误完成: B 读取发生在 swap 后并采样新的 global revision, 最后的 global compare 看到该 revision 仍为 current, 但它无法追溯证明更早的 A observation 也属于这个 revision

`pair-compare-complete` 同时比较 A 与 B 的 observed revision, A expected revision 已被 swap 推进, 因而 compare conflict, 随后重新读取 current pair、重新确认 current permission 并执行必要恢复 effect, 最终 A/B 均为 `marked`

`unrelated-global-change` 中 global compare 多一次 compare conflict 与 recovery read, pair compare 不冲突, 两条路径都不增加 forward effect

三次 process-level producer 加 verifier 总耗时分别约为 1623.748、1545.081 与 1757.383 毫秒, 只记录本轮环境的进程级夹具开销, 不用于推断真实事务系统性能

verifier 不导入 producer, 不读取 producer 内部成功布尔值或保存的期望对象

- 25 个 scenario/path 组合完整且唯一
- event_order 中真实 forward effect commit 数与 effect_count 一致
- 每个 B 侧恢复 effect commit 前都存在 `B:permission_valid`
- normal-stable 五条路径均为 effect 1、completed 1、A/B=`marked`
- completed-replay 五条路径都重新进入 production entry 并经过 `B:completed_short_circuit`, effect 总数保持 1
- fractured-one-pass 的 independent-reads 为 effect 1、completed 1、A=`clean`、B=`marked`, event order 明确包含 A old read、swap、B new read
- oscillating-fracture 的 double-read 四个单项 read 都返回 `marked`, 最终仍为 effect 1、completed 1、A=`clean`、B=`marked`
- atomic-pair-snapshot 在 fractured 场景看到同一时点 pair 中至少一个 `clean`, 因而不会直接保存 completion
- pair-compare-complete 在 fractured-one-pass 记录 compare conflict 并恢复为 effect 2、A/B=`marked`

因此本轮不是对真实数据库 snapshot isolation、etcd multi-key transaction 或跨服务状态聚合的端到端验证

## 强反例

`fractured-one-pass` 直接推翻 H1: 单项 authoritative current read 不能自动组合成 authoritative current pair

`oscillating-fracture` 进一步推翻 H2: 对各资源分别重复读取仍可能被精心交错的状态变化欺骗, 多读几次不等价于共同 snapshot

`global-compare-complete` 的失败限制 H5 的常见直觉: whole-store revision 本身足够宽, 但如果 expected revision 只在最后一次读取时采样, 它不能追溯绑定此前已经发生的 A read, 因而宽围栏仍可能 under-bind observation history

`unrelated-global-change` 又从相反方向限制 global compare: 当 expected revision 正确覆盖当前读取后, 无关 global state 推进仍会产生额外 conflict

因此问题不只是围栏宽或窄, 还包括每个 evidence observation 是否真正绑定到被比较的 snapshot identity

atomic-pair-snapshot 在本轮 fractured read 场景中有效, 但本轮没有在 snapshot read 后再次注入 reversal, 所以不能用它否定 8 月 25 日已经观察到的 snapshot/read-to-completion TOCTOU

## 暂时结论

状态保持观察

本轮支持把 multi-resource current completion evidence 的边界写得更精确: 每个资源各自 fresh 不等价于资源集合存在过共同 satisfied state

如果 completion contract 是多个资源的联合谓词, evidence 需要共同 snapshot identity, 或在 completion 提交边界对全部 relevant observed revision 做原子 compare

只在最后一次读取时采样 global revision 不能自动给更早读取补上 snapshot identity; 只增加重复读取也不能消除 fractured view

该结论目前只来自单日受控实验, 不升级 NOTES

## 事实分层

### 已验证事实

- 五条 production-entry 路径覆盖 normal、one-pass fracture、oscillating fracture、unrelated global change 与 completed replay 共 25 个组合
- independent-reads 在 one-pass fracture 中读取 A=`marked` 与 B=`marked` 后错误 completion, 但最终 authoritative pair 为 A=`clean`、B=`marked`
- double-read 在 oscillating fracture 中四次单项读取全部为 `marked` 仍错误 completion
- global-compare-complete 在 fractured 场景仍可能无 conflict 假完成, 因为 expected global revision 在较晚读取时才采样
- pair-compare-complete 在 fractured 场景识别 earlier A revision 已变化并恢复 A/B=`marked`
- completed replay 五条路径 effect 总数均保持 1
- 修正后的 producer 三次轨迹完全一致, Python verifier 与 awk 第二验证均通过

### 基于证据的推断

- 多资源联合后置条件需要证明 observation set 的共同一致性, 不能把各自 fresh 的单项读取直接视为共同 current state
- snapshot identity 与 fence scope 是两个不同维度: global fence 可以很宽但仍因采样时点不当无法绑定 earlier observation
- relevant per-resource compare 在本轮同时减少 fractured under-binding 与 unrelated global over-fencing, 前提是 compare set 完整覆盖全部 completion dependencies

### 未验证事项

- 尚未证明真实 etcd、PostgreSQL 或其他系统会以本夹具相同方式表现
- 尚未验证 atomic snapshot 后到 completion commit 的再次变化, 该问题仍受 8 月 25 日结论约束
- 尚未证明多服务、多区域或不可事务化资源能够建立统一 snapshot identity
- 尚未证明真实复杂任务的 relevant compare set 可以完整枚举
