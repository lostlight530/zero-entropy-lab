## 研究问题

历史 effect 已经存在且 completion 丢失, verifier 同时拿到一个早于 revocation 的 timestamp 时, 这个 timestamp 如果只证明 payload 早已存在, 是否会被错误解释为 approval signature 也在 revocation 前已经存在

反方向问题是 timestamp 确实覆盖 approval signature 且早于 revocation 时, recovery 时 current capability 已 revoked, 是否会把 current state 错误追溯为 historical invalidity

本轮把 historical occurrence、timestamp semantic coverage、signature creation evidence、revocation boundary 与 current new-effect authorization 分开

## 来源依据

查询日期为 2026-09-16

- [RFC 3161 Internet X.509 Public Key Infrastructure Time-Stamp Protocol](https://www.rfc-editor.org/rfc/rfc3161.html) 说明 TSA timestamp 为特定 datum 提供 proof-of-existence, Appendix A/B 的 signature timestamp 明确对 signature value 做 message imprint 并用于把 signature 放置到特定时间点. 本轮只采用有限命题: 时间证据的证明对象必须与要判断的 historical signature 对象一致
- [RFC 9921 COSE Header Parameter for Timestamp Tokens](https://www.rfc-editor.org/rfc/rfc9921.html) 的 semantic-confusion guidance 明确区分 payload data timestamp 与 cryptographic signature timestamp, 并指出把 payload timestamp 当作 signature creation time 可能错误接受 key revocation 后才产生的 signature. 本轮只采用有限命题: timestamp 时间正确仍不等于 timestamp 语义覆盖正确
- [NIST SP 800-57 Part 1 Revision 5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final) 说明 compromised key 不应继续用于新 cryptographic protection, 但在严格控制下, 具有可靠 timestamp 的历史 signature 可能用于判断 compromise 前的完整性. 本轮只采用有限命题: historical verification 与 current key state 可以分离, 不把 PKI 直接等同于人工 approval

RFC 3161 与 RFC 9921 为独立标准文本, NIST 为独立公共机构指导. 外部来源不证明本地 valid_completion、effect_total、PASS 或实验 trace

## 可证伪假设

- H1: 只要 payload timestamp 早于 revocation, historical approval signature 就可以视为 revocation 前已存在
- H2: timestamp 必须实际覆盖 signature, 且 signature timestamp 早于 revocation, 才能为 historical signature timing 提供本轮需要的证据
- H3: current capability revoked 可以反向否定所有 revocation 前已有可信 signature timestamp 的 historical completion
- H4: authoritative MISS 后的新 effect 仍必须独立检查 current capability 与 current approval
- H5: UNKNOWN 不得因存在 timestamp 字段而猜测 prior occurrence
- H6: completed replay 必须从 production entry 重入并保持零新增 effect

H1 的反证条件是 payload-ts-only: payload_ts=96 早于 revocation_time=100, 但 timestamp_covers_signature=0 且实际 signature_time=101 晚于 revocation

H3 的反证条件是 trusted-hit-current-revoked: signature timestamp=96, timestamp_covers_signature=1, revocation_time=100, recovery 时 current_revoked=1

反方向强反例是 miss-current-valid

## 路径比较

- occurrence-only 操作最少, 对所有 HIT 都恢复 completion, 因而无法区分撤销后 signature 或 timestamp semantic mismatch
- payload-timestamp 只增加一次 timestamp 比较, 但在 payload-ts-only 中用错误证明对象产生 false positive
- signature-timestamp 增加 coverage 与 signature-time 两项检查, 在 payload-ts-only 与 late-signature-ts 中都正确拒绝, 在 trusted-hit-current-revoked 中保留历史有效 completion
- signature-ts-current-gate 再多一次 current-state 检查, 对 MISS 有必要, 但把它追溯用于历史 HIT 时在 trusted-hit-current-revoked 中产生 false negative
- 本轮 stronger historical path 的额外操作换取 semantic coverage 与时间边界可区分性, 操作更少但证明对象错误的路径不视为有效优化
- 本地 validated elapsed 主要包含 Python 启动与文件 I/O, 不外推真实 TSA、PKI、HITL 或远端 authorization service 性能

## 暂时结论

证据状态为观察

本轮支持 H2、H4、H5、H6, 推翻 H1、H3

timestamp 的时间值与 timestamp 实际证明的对象必须同时进入 historical verification. 早于 revocation 的 payload timestamp 不能替代 signature timestamp

反过来, 已经由 signature-covering timestamp 放置到 revocation 前的 historical effect, 不能仅因 recovery 时 current capability revoked 就被追溯否定

historical occurrence、timestamp semantic coverage、historical signature timing 与 authoritative MISS 后 current new-effect authorization 继续是不可互相替代的恢复事实

### 基于证据的推断

- timestamp proof 的语义覆盖对象是 historical authorization verification 的独立依赖, 不能只检查 timestamp 数值是否早于 revocation
- current capability state 只应约束当前新 effect, 除非 authority contract 明确规定其历史追溯语义
- 对需要证明 signature 在某时间前已经存在的恢复语义, signature-covering timestamp 比 payload-only timestamp 提供更直接的 relevant evidence
