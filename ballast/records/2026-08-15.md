# Ballast 日记录 2026-08-15

类型: 每日专题
主题: 迟到恢复中的相关状态围栏与未知副作用重放

## 研究问题

Agent 的任务在排队、租约过期或中断后迟到恢复时, 如果权威目标状态已经推进, 仅依赖 task ID 完成记录、绑定整个对象 revision、以及绑定与本任务相关的状态 generation 并在副作用端保存 effect identity, 哪一种能够同时避免旧任务覆盖当前状态、避免无关状态变化造成过度拒绝, 并在副作用已经发生但完成标记丢失时安全恢复.

本题承接 2026-08-09 的迟到重试和 2026-08-14 的相关状态绑定, 但新增攻击点是未知结果恢复. 今天不只问旧任务是否仍有写权限, 还要求生产入口在“副作用已发生, task completion 尚未持久化”的中断点重新进入后区分已生效与未生效.

## 来源依据

查询日期为 2026-08-15.

- [Google Cloud Pub/Sub: Exactly-once delivery](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery) 访问于 2026-08-15. 文档说明 redelivery 保持相同 message ID, 但在 acknowledgement deadline 过期或重新投递后只有最新 acknowledgement ID 可以确认, 旧 acknowledgement ID 会失败. 文档同时要求在成功确认前保存处理进度以避免 acknowledgment 失败导致的重复工作. 适用边界是 Pub/Sub pull subscription 的 exactly-once 合同, 不直接等价于任意业务副作用的 exactly-once.
- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) 访问于 2026-08-15. 文档说明更新对象时客户端应携带读取到的 `resourceVersion`, API server 用它检测 lost update, stale `resourceVersion` 会返回 409 Conflict. 文档同时指出 JSON Patch 可以把条件限制到已有值, 而不是无条件依赖整个对象变化. 适用边界是 Kubernetes API 对象并发控制, 不自动提供业务副作用去重.
- [Amazon S3: How to prevent object overwrites with conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html) 访问于 2026-08-15. 文档说明 `If-Match` 会把写入绑定到当前对象 ETag, ETag 不匹配时条件写失败, 并说明并发条件写可能返回 409 或 412. 适用边界是 S3 对象条件写, 不证明应用层任务 identity 与 effect identity 已绑定.

Google、Kubernetes 与 AWS 来自三个独立实现体系. 三者共同支持“重试或恢复前重新绑定当前服务端状态, 不把旧身份本身当作继续执行许可”的设计方向, Pub/Sub 额外提供了旧 delivery token 失效和处理进度保存的公开合同. 这些资料只支持实验建模, 不直接证明本轮夹具结论.

## 可证伪假设

- H1: task ID 加完成布尔值已经足够. 只要任务没有标记 completed, 迟到恢复可以继续执行, 即使相关权威状态已经推进.
- H2: 把任务绑定到整个对象 revision 已经足够. revision 变化一律拒绝可以避免迟到覆盖, 而不会显著损伤有效恢复.
- H3: 执行权限应绑定任务实际依赖的相关状态 generation, 未知结果恢复还需要独立 effect identity. 相关 generation 变化时拒绝旧任务, 无关 metadata 变化时仍可执行, 副作用已发生但 completion 丢失时通过 effect identity 恢复为完成而不重复写入.

如果 id-only 在相关状态推进后不覆盖当前值, H1 的风险解释被削弱.

如果 global-revision 在只有无关 metadata 变化时仍能执行, H2 的过度围栏解释被削弱.

如果 projection-effect 在相关 generation 变化后仍写入, 或在 unknown-result replay 中产生第二次写入, H3 被推翻.

## 控制条件

- 任务固定为 `task-42`, payload 固定为 `late-old`.
- 初始相关状态 generation 为 1, 当前值为 `current-old`, 全局 revision 为 1, 无关字段 `note=n0`.
- `id-only` 只检查 task completion.
- `global-revision` 额外要求当前全局 revision 等于任务读取时的 revision.
- `projection-effect` 要求当前相关 generation 等于任务读取时 generation, 并在副作用 sink 保存 `task-42` effect identity.
- 正常基线没有任何状态变化.
- 迟到故障把相关 generation 从 1 推进到 2, 当前值改为 `current-new`, revision 同时变为 2.
- 强反例只把无关 `note` 从 n0 改为 n1 并推进全局 revision 到 2, 相关 generation 与当前值不变.
- unknown-result 故障在副作用写入后、task completion 持久化前中断, 随后让同一任务重新经过原生产入口.
- completed replay 先正常完成, 再让同一任务重新经过原生产入口.
- 实验使用 Python 标准库、系统 awk 和系统临时目录, 轨迹为 UTF-8 TSV.

## 实验设计

1. 正常基线分别执行三条路径, 验证都恰好写入一次 `late-old`.
2. 模拟迟到任务, 在任务恢复前把相关 generation 从 1 推进到 2 并把当前值设置为 `current-new`, 再让旧任务经过三条生产入口.
3. 比较 id-only 是否覆盖较新状态, 以及两个围栏路径是否零写入停止.
4. 构造强反例, 只改变与任务无关的 `note`, 让全局 revision 推进但相关 generation 保持不变, 比较 global-revision 与 projection-effect.
5. 模拟 unknown result, 在写入 effect 后但 completion 保存前中断, 随后让同一任务重新经过原生产入口.
6. 记录各路径新增写入数和 producer 内部操作计数, 判断为了减少检查而牺牲正确性的路径是否真的更优.
7. 正常完成后再次重放三条生产入口, 检查已完成任务是否新增写入.
8. producer 输出固定 12 列 TSV, 不向 verifier 输出内部期望布尔值.
9. 独立 Python verifier 只从 TSV 场景、路径、结果、写入数、最终值和状态字段重建判定.
10. awk 第二实现独立解析同一 TSV, 复核迟到覆盖、强反例和 unknown-result replay.
11. 完整 producer 运行三次并比较轨迹 SHA-256.

## 原始观测

三次完整生产轨迹均包含 15 个数据行, SHA-256 均为 `a23458a9fe2db92e669b90727eb24031b6861881768ab50a404f9c04088f21bf`.

三次 producer 有效耗时分别为 0.037426 毫秒、0.036915 毫秒和 0.035813 毫秒. 这些数字只描述本轮单机确定性夹具, 不用于推断真实分布式系统性能.

迟到故障中 id-only 以最少操作数返回 applied, 但把 `current-new` 覆盖为 `late-old`. 两条围栏路径都保持零写入并保留 `current-new`.

global-revision 在只有无关 `note` 变化时也拒绝任务, 说明整个对象 revision 能阻止 stale overwrite, 但会把与本任务语义无关的变化一起纳入失败条件.

projection-effect 在无关变化强反例中仍正常写入一次, 因为它只比较相关 generation.

unknown-result 故障中 id-only 与 global-revision 都在恢复后再次写入, 总写入数为 2. projection-effect 第二次进入生产入口时识别已经存在的 `task-42` effect identity, 返回 `effect_already_applied`, 总写入数保持 1, 并补全 task completion.

已正常完成后的同输入重放中三条路径都返回 `already_completed`, 总写入数保持 1. 因此本轮区分了“completed replay”与“effect 已发生但 completion 未保存”的未知结果恢复, 后者才暴露仅 completion 去重的缺口.

## 独立验证

producer 与 verifier 是两个独立 Python 文件, verifier 不导入 producer.

独立 verifier 从 TSV 重新检查:

- 三条正常基线都恰好写入一次并完成.
- 迟到相关状态变化时 id-only 实际覆盖 `current-new`, 两个围栏路径零写入.
- 仅无关 metadata 变化时 global-revision 拒绝, projection-effect 正常执行.
- unknown-result replay 中 id-only 与 global-revision 各产生两次写入, projection-effect 只产生一次并恢复 completion.
- completed replay 中三条路径都没有第二次写入.

三次独立 Python verifier 均返回 `PY_VERIFIER_PASS`.

第二验证器使用 awk 独立解析相同 TSV, 对迟到覆盖、相关 generation 拒绝、无关状态强反例和 unknown-result replay 返回 `PASS`.

producer 与 verifier 均通过 `py_compile`. 两个验证器仍共享 TSV 字段命名和场景标签, 也没有访问真实 Pub/Sub、Kubernetes、S3 或外部 side-effect sink, 因而不是完全外部独立验证.

## 强反例

第一, 把整个对象 revision 作为围栏并不是“越严格越好”. 当只有与本任务无关的 `note` 从 n0 改为 n1 时, global-revision 因 revision 从 1 变为 2 而拒绝, 但相关 generation、当前业务值和任务意图都没有变化. projection-effect 仍能正常执行, 说明应尽量围栏真正影响当前副作用语义的状态投影.

第二, task completion 去重不能覆盖 unknown outcome. id-only 与 global-revision 在第一次副作用已经写入但 completion 尚未持久化时, 重放生产入口都会再写一次. 这说明“没有 completed 记录”无法区分“尚未执行”与“已经执行但确认丢失”.

第三, 已完成任务重放没有暴露上述问题. 三条路径对 completed replay 都没有第二次写入. 因此如果测试只覆盖“完成后再读 completed 标记”, 会错过真正更危险的 effect-completion 间隙.

## 路径比较

| 路径 | 相关状态变化 | 无关状态变化 | unknown-result replay | 正常完成后 replay | 基线操作数 |
| --- | --- | --- | --- | --- | ---: |
| id-only | 错误覆盖 | 执行 | 重复写入 | 零新增写入 | 2 |
| global-revision | 拒绝 | 过度拒绝 | 重复写入 | 零新增写入 | 3 |
| projection-effect | 拒绝 | 执行 | 单次写入并恢复完成 | 零新增写入 | 4 |

id-only 的正常路径操作最少, 但在迟到状态推进和 unknown outcome 两类故障中都产生错误副作用.

global-revision 增加一次全局 revision 比较, 能阻止 stale overwrite, 但不能判断已发生但未确认的 effect, 并对无关状态变化过度保守.

projection-effect 在基线中比 id-only 多两次检查, unknown-result replay 总操作数也更高, 但它同时保持当前状态不被旧任务覆盖、无关变化不被误拒绝, 并避免未知结果恢复中的重复副作用. 本轮有效速度来自减少错误写入和补偿风险, 不是减少检查次数.

## 暂时结论

本轮单次受控实验支持 H3, 证据等级为观察.

迟到恢复至少需要重新验证当前任务真正依赖的相关权威状态, 而不是只看 task ID 或把任意对象变化都等价为任务失效. 当副作用和 completion 记录之间存在中断窗口时, 还需要能由接收端或独立权威存储确认的 effect identity, 否则重放生产入口仍可能产生重复副作用.

这不是对 exactly-once 的一般证明. effect identity 的原子写入、保留期限、跨区域一致性和业务副作用是否允许查询, 都可能改变结论.

## 复验条件

以下任一条件出现时复验:

- effect identity 与真实副作用不能原子提交, 可能出现 marker 已写但 effect 未写或反向顺序.
- effect identity 有 TTL 或保留窗口, 迟到重放可能发生在记录过期后.
- 一个 task 对应多个部分副作用, 单个 task ID 无法表达逐项完成.
- 相关状态投影定义变化, 旧任务保存的 generation 不再覆盖全部业务前提.
- 多区域或多主 sink 无法提供单一最新 effect identity 视图.
- unknown outcome 来自客户端超时而不是进程中断, 需要远端 read-back 才能区分已生效与未生效.

## 体系增量

- 将迟到恢复拆为两个独立问题: 当前执行权限是否仍新鲜, 以及上一次未知结果是否已经产生副作用.
- 增加 `relevant state fence + effect identity` 组合观察, 前者防 stale overwrite, 后者防 effect-completion 间隙重放.
- 明确 global revision 只是保守围栏的一种实现, 强反例显示它可能把无关变化误当作任务失效.
- 明确 completed replay 不能替代 unknown-result replay, 后者必须让任务重新经过生产入口并检查真实副作用计数.
- 本轮不修改 METHOD.md、CASES.md、README.md 或 NOTES.md. 单次观察尚不足以改变稳定方法或发现等级.

## 事实分层

### 已验证事实

- 本轮受控夹具中, id-only 在相关 generation 已推进后仍写入旧 payload 并覆盖当前值.
- global-revision 与 projection-effect 在相关 generation 推进场景中均零写入.
- 只有无关 metadata 变化时, global-revision 拒绝而 projection-effect 正常执行.
- effect 已发生但 completion 丢失后重放原生产入口, id-only 与 global-revision 各产生 2 次总写入, projection-effect 保持 1 次总写入并恢复 completion.
- 三次轨迹 SHA-256 一致, Python verifier 与 awk verifier 均通过, producer 和 verifier 均通过 `py_compile`.

### 基于证据的推断

- 迟到任务的执行权限更适合绑定到实际影响副作用语义的状态投影, 而不是 task identity 或无差别全局 revision.
- unknown outcome 的安全恢复需要独立于 task completion 的 effect evidence, 否则“未完成”与“已生效但确认丢失”不可区分.
- 为减少操作数而删除相关状态检查或 effect 回读会降低验证后有效质量, 即使正常路径更快.

### 未验证事项

- 真实消息系统、API server、对象存储或外部 SaaS 是否能够提供与本夹具相同的 effect identity 原子性.
- effect marker 与业务副作用跨资源提交时的 crash consistency.
- effect identity 的长期保留、压缩、迁移和跨区域一致性.
- 多部分副作用、补偿事务和不可查询副作用中的等价恢复策略.
