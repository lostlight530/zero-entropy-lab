## 研究摘要

This Daily tests whether target preconditions can be mistaken for a complete action-integrity gate.

Kubernetes exposes UID and resourceVersion preconditions for operations. They can protect target identity or revision, but they do not collapse current authorization, historical occurrence, historical authorization, membership completeness or current completion into one proof.

No live state-changing API request is executed.

## 研究问题

Can UID or resourceVersion preconditions make a state-changing retry safe when target reincarnation, authority drift and completion are separate uncertainties.

## 来源依据

Checked 2026-10-05 against current Kubernetes documentation.

[Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) documents object identity, UID generation, resourceVersion semantics and dry-run boundaries.

[Kubernetes Preconditions](https://kubernetes.io/docs/reference/kubernetes-api/definitions/preconditions-v1-meta/) defines UID and resourceVersion as preconditions that must be fulfilled before an operation is carried out.

The API Concepts documentation also states that dry-run and non-dry-run authorization are identical, while generated UID and resourceVersion values from dry-run must not be relied on as persisted values.

These sources constrain Kubernetes API semantics only. They do not prove this fixture.

## 可证伪假设

H1 name equality alone is sufficient to bind a retry to the originally intended object.

H2 matching UID precondition is sufficient to establish valid completion.

H3 matching resourceVersion or UID precondition is sufficient to establish current execution permission.

H4 a separated gate requiring current permission, intended incarnation identity, prior-effect evidence and post-effect task-state verification avoids the modeled false actions and false completions.

Four paths are name-only, precondition-only, permission-plus-precondition and full-integrity.

## 强反例

same-name-recreated-object defeats H1 because an API address can be reused while persisted incarnation changes.

uid-match-required-member-pending defeats H2 because correct target identity does not prove the task-defined completion set.

uid-match-current-permission-revoked defeats H3 because identity protection and authorization answer different questions.

prior-effect-unknown shows that a valid current precondition does not erase ambiguity about whether a previous effect already occurred.

## 路径比较

name-only confuses logical address with incarnation identity.

precondition-only correctly rejects wrong UID and stale revision but still confuses identity protection with authorization and completion.

permission-plus-precondition protects the immediate effect boundary better but still false-completes when the task-defined completion set is incomplete and still retries an unknown prior effect.

full-integrity has zero disagreement in this bounded fixture because it keeps current permission, target incarnation, prior occurrence and post-effect completion evidence separate.

## 暂时结论

UID and resourceVersion preconditions are valuable effect-boundary guards, not universal completion receipts.

Correct target identity does not imply current permission.

Successful precondition matching does not prove the requested task state is complete.

A prior unknown non-idempotent effect remains UNKNOWN until authoritative occurrence evidence resolves it.

H4 is supported only by this bounded model.

## AGI-scale action-integrity relevance

Long-running agents can revisit state-changing plans after object recreation, authority changes or partial completion.

A protected effect should bind intended incarnation and current authority at the effect boundary, while completion is reconstructed afterward from task-defined state.
