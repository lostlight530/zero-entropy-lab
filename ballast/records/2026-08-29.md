## 研究问题

当 multi-resource persistent-state task 已经分别读取 A 与 B 都满足 current postcondition, 并准备在 completion commit 时原子比较两个 target 的 local revision, 如果其中任意一个 target 在读取后被删除重建且新实体复用相同 logical name、value 与 local revision, pair revision compare 是否仍会把新的 identity set 误当成旧 observation set 的延续

本轮组合 8 月 26 日的 multi-resource completion compare 与 8 月 28 日的 incarnation-aware compare, 改变的故障位置是多资源 compare set 中只遗漏一个 target 的 incarnation identity

关键窗口为 `READ A uid-A1 r1 + READ B uid-B1 r1 -> RECREATE B as uid-B2 r1 -> atomic pair revision compare -> completion commit`

## 来源依据

查询日期为 2026-08-29

- [Kubernetes Object Names and IDs](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/) 说明对象删除后可以重新创建同名对象, 每个新对象具有不同 UID, UID 用于区分相似实体的不同历史实例. 适用边界是 Kubernetes object identity, 不直接证明任意 Agent state store 都有同样 UID 合同
- [etcd API](https://etcd.io/docs/v3.6/learning/api/) 说明 transaction 是 atomic If/Then/Else, 一个 transaction 可以对相同或不同 key 的多个 comparison 做 conjunction, 所有 comparison 原子应用后再选择 success 或 failure 分支. 适用边界是 etcd key-value transaction, 不自动提供业务层 target identity 或 task semantics

两个独立官方来源支持一个有限设计前提: 多 key 原子 compare 能保证实际 comparison set 的并发一致性, 但一个逻辑名称下的新历史实体是否应被视为同一 completion target 必须由任务语义与 identity contract 显式决定

本轮只在标准库受控夹具中检验 multi-resource pair revision compare 遗漏单个 target incarnation identity 时是否仍会 false complete

## 可证伪假设

- H1: multi-resource completion 只要在 commit 时原子比较每个 target 的 local revision, 就足以绑定此前的全部 observations
- H2: 对 concrete-pair contract, complete compare set 必须同时绑定 A 与 B 的 target incarnation identity 以及各自 incarnation 内 revision
- H3: identity-set 规则必须服从 task semantics, selector-pair contract 如果接受任何当前 job-a 与 job-b 且两者都满足 marked, 单个 UID 变化本身不应机械导致失败
- H4: completed replay 不能替代 target replacement before completion 的真实 production-entry 窗口

H1 的反证条件是 A 与 B 的 revision 都仍等于读取值, pair revision compare 原子成功, 但 B 或 A 已经是新 incarnation 且 concrete-pair 任务仍保存 completion

H2 的反证条件是任一 target UID 变化后 UID+revision pair compare 仍允许 concrete-pair completion, 或同一 pair 只发生正常 revision drift 时不能识别 conflict

H3 的反方向强反例使用 selector-pair contract, B 重建后同名且仍满足 marked, contract-aware path 应允许 completion

## 控制条件

- historical effect evidence 固定为 hit, 本轮只研究 current multi-resource completion evidence
- current execution permission 的 relevant world state、intent、holder、valid_until、task status、credential capability 与 approval binding 固定有效, 只有 concrete-pair target 被重建时 identity-bound permission 变为无效
- concrete-pair contract 明确要求当前仍是 uid-A1 与 uid-B1
- selector-pair contract 只要求当前 job-a 与 job-b 两个 logical targets 都存在且 value=marked
- 初始 A 为 name=job-a, uid=uid-A1, value=marked, local revision 1
- 初始 B 为 name=job-b, uid=uid-B1, value=marked, local revision 1
- 单目标重建后新实体保持同 logical name 与 value=marked, local revision 重新从 1 开始
- no-compare 读取两个目标后直接保存 completion
- pair-revision-compare 在 completion commit 时原子比较 A revision 与 B revision, 但不比较 UID
- contract-aware-pair-compare 对 concrete-pair 原子比较 A UID+revision 与 B UID+revision, 对 selector-pair 比较当前 logical pair 与 predicate
- same-incarnation reversal 只把 B1 改为 clean 并推进 revision, compare conflict 后 strong path 重新读取 current state, 重新执行 effect 前重新确认 current execution permission
- unrelated metadata 只改变 A note, 不改变 UID、value 或 local revision
- completed replay 让已完成任务重新进入同一 production entry 并经过 completed short circuit
- 实验只使用 Python 标准库与系统 awk, 不访问真实 Kubernetes、etcd 或外部 effect sink

## 实验设计

1. 三条路径运行 normal baseline, 验证 pair identity 与状态不变时都能完成
2. 注入 same-incarnation-reversal-b, 读取后把 B1 改为 clean 并推进 revision, 检查两条 compare path 是否识别 conflict 并在 recovery effect 前重新确认 permission
3. 注入 recreate-b-revision-reuse, 读取 pair 后只重建 B 为 uid-B2 r1 marked, 检查 pair revision compare 是否错误成功
4. 注入 recreate-a-revision-reuse, 对称地只重建 A 为 uid-A2 r1 marked, 检查问题是否不依赖具体 target 位置

两个 local revision 都与旧 observations 相等, CAS 自身也完全原子, 但 current concrete target set 已从 `{uid-A1, uid-B1}` 变成 `{uid-A1, uid-B2}`

## 强反例

第一强反例是 multi-resource pair 中只重建 B

A 仍是 uid-A1 r1, B 从 uid-B1 r1 重建为 uid-B2 r1, 因此 pair revision comparison `(A r1, B r1)` 仍全部为真并原子成功

该结果直接推翻 H1: 比较全部 local revisions 仍不等于比较完整 relevant identity set

第二个对称反例只重建 A, 得到相同结论, 排除单个资源位置或处理顺序造成的解释

第三个反方向强反例是 selector-recreate-b

当任务语义只要求当前 job-a 与 job-b 都满足 marked, 新 B2 仍满足 selector contract, contract-aware path 应并且确实允许 completion

因此 H2 的适用边界只覆盖 concrete-incarnation completion, 不能机械把每个 UID 变化解释为失败

unrelated-metadata 同样不触发 strong path conflict, 说明 compare set 没有退化成 whole-object fencing

completed replay 全部安全, 仍不能替代 replacement-before-completion 窗口

## 暂时结论

本轮推翻 H1, 支持有边界的 H2 与 H3, 并再次支持 H4

对于 concrete multi-resource completion contract, complete atomic compare set 需要覆盖每个 relevant target 的 incarnation identity 与 incarnation 内 freshness evidence

逐资源 revision compare 只有在已经证明每个 observation 仍对应同一 incarnation 时才能解释为 freshness guarantee

因此 multi-resource completion 的可靠判断可以进一步写成 `task semantics -> complete target identity set -> per-target freshness -> atomic compare-and-protected-completion`

该表达没有改变现行 METHOD 的稳定规则, 本轮价值是对其 multi-resource + reincarnation 组合窗口做独立受控复验

## 事实分层

### 已验证事实

- pair-revision-compare 在任一单 target 被同名重建且 local revision 复用时仍原子成功并 completed=1
- 两个 concrete recreate 场景都没有新增 effect, 因而属于零写入错误继承 completion, 不是重复副作用
- contract-aware-pair-compare 在任一 concrete target UID 变化时拒绝旧 completion 并安全停止, 没有把旧任务自动作用于新实体
- same-incarnation reversal 中 compare path 能识别 revision drift, recovery effect 前重新确认 current permission
- selector-recreate-b 与 unrelated-metadata 均未被 contract-aware path 过度拒绝
- completed replay 三条路径新增 effect 均为 0
- 三次 producer 轨迹 SHA-256 完全一致, Python verifier 3/3 PASS, awk verifier PASS, producer 与 verifier py_compile PASS

### 基于证据的推断

- 对 concrete multi-resource task, local revision equality 的解释前提是完整 target identity set 没有变化
- multi-key transaction 的原子性不能弥补 comparison set 对业务 identity dependency 的遗漏
- contract-aware identity predicate 应由 task semantics 决定, concrete target set 与 selector-bound set 需要不同 completion contract

### 未验证事项

- 尚未把真实 Kubernetes、etcd 或其他 multi-key transactional store 作为实验目标
- 尚未验证多个 target 同时或先后 reincarnate、stale UID read、动态 selector membership 与跨服务 completion store
- 尚未证明受控 pair model 可以直接外推到任意 N-resource Agent workflow
- verifier 仍共享事件标签与字段语义, 不能排除共同建模错误
