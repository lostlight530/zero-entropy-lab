# Ballast 日记录 2026-08-14

类型: 每日专题
主题: 批准恢复中的动作与相关状态绑定

## 研究问题

Agent 因敏感工具调用暂停并等待人工批准后, 如果恢复前具体动作参数或与动作相关的权威状态已经变化, 仅保存工具级批准、绑定具体 action/call 的批准、以及同时绑定 action 与相关状态投影的批准, 哪一种能够避免把旧批准误用于已经变化的副作用.

本题承接 2026-08-13 的任务授权边界, 但不重复 credential 状态. 今天只攻击 human approval 在暂停与恢复之间的陈旧化: 人曾经真实批准过, 但批准对象或批准时所依据的相关状态可能已经变化.

## 来源依据

查询日期为 2026-08-14.

- [OpenAI Agents SDK: Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/) 访问于 2026-08-14. 文档说明敏感 tool call 可以暂停执行并通过 `ToolApprovalItem` 交由人工批准, 默认批准按具体 call ID 保存, interruption 同时暴露 tool name 与 arguments, `RunState` 可以序列化后长期恢复. 文档也说明 `always_approve=True` 可以把决定扩展到同一 run 后续该工具调用. 适用边界是 OpenAI Agents SDK 的批准状态合同, 不证明应用层权威状态在等待期间保持不变.
- [OpenAI Agents SDK: Guardrails](https://openai.github.io/openai-agents-python/guardrails/) 访问于 2026-08-14. 文档说明 tool input guardrails 在需要批准时通常会在批准后、真正执行之前再次运行, 即使配置为批准前先检查, 执行前仍会再次检查. 这支持把批准与最终执行前的当前输入验证区分开, 但 guardrail 本身检查什么仍由应用定义.
- [Google Gemini API: Computer Use](https://ai.google.dev/gemini-api/docs/computer-use) 访问于 2026-08-14. Google 将 UI action 作为具体 `function_call` 返回, `safety_decision=require_confirmation` 时客户端需要征求用户确认后再执行. Safety best practices 进一步建议用户确认后在继续动作前获取最新屏幕, 将确认与当前环境状态重新读取分开. 适用边界是 Gemini Computer Use 的客户端执行循环, 不证明任意 API 副作用都自动具有状态绑定批准.

OpenAI 与 Google 来自两个独立实现体系. 两者都把批准放在具体动作执行路径中, 并保留批准后再次检查输入或环境状态的工程位置. 这些公开合同支持本日实验设计, 不直接证明本轮受控夹具结果.

## 可证伪假设

- H1: 人只要在当前 run 中批准过某个工具, 后续同工具调用都可以复用该批准, 即使具体参数变化.
- H2: 批准绑定具体 call ID 与 action digest 已经足够, 只要动作字节没有变化, 恢复时就可以执行.
- H3: 批准至少需要绑定具体 action 与本次副作用真正相关的权威状态投影. 动作变化或相关状态变化都使旧批准失效, 但与本动作无关的状态变化不应自动使批准失效.

如果工具级批准在参数改变后不执行新动作, H1 的风险解释被削弱.

如果 action-bound 路径在相关权威状态改变后能够拒绝旧批准, H2 的不足解释被削弱.

如果相关状态投影路径在相关状态改变后仍执行, 或仅有无关 metadata 改变时也无条件拒绝, H3 被推翻或证明过度围栏.

## 控制条件

- 工具固定为 `publish`, 目标固定为 `doc-7`.
- 初始 action 为 call ID `call-42`, payload `alpha`.
- 初始相关权威状态为 `target_status=ACTIVE`, `owner=alice`.
- 无关 metadata 字段为 `note=n0`.
- 工具级路径只保存 `publish` 已批准.
- action-bound 路径保存 `call-42` 与规范化 action SHA-256.
- state-bound 路径额外保存由 `target_status` 与 `owner` 组成的相关状态投影 SHA-256.
- 故障一在批准后把 payload 从 `alpha` 改为 `beta`, call ID 与工具名保持不变.
- 故障二保持 action 完全不变, 但把 `target_status` 从 `ACTIVE` 改为 `LOCKED`.
- 强反例只把无关字段 `note` 从 `n0` 改为 `n1`, action 与相关权威状态保持不变.
- 完成后的同输入重放继续使用同一生产入口, 通过 `call-42` 的完成集合检查第二次副作用.
- 实验只使用 Python 标准库、系统已有 awk 与系统临时目录, 文本显式使用 UTF-8.

## 实验设计

1. 正常基线中批准 `publish doc-7 alpha`, 不改变 action 或相关状态, 比较三条路径是否各执行 1 次.
2. 故障一在批准后把 payload 改为 `beta`, 再让相同 call ID 经过三条生产入口.
3. 记录工具级路径是否把旧批准扩展到新参数, 以及 action-bound 与 state-bound 是否识别 action digest 变化.
4. 故障二重新从原始批准开始, 保持 action digest 不变, 仅把相关状态改为 `LOCKED`.
5. 比较 action-bound 是否仍执行, 以及 state-bound 是否因相关 authority state 改变而零写入停止.
6. 构造强反例, 只改变与本动作无关的 `note`, 检查 state-bound 是否仍允许原 action, 用于反证把所有 revision 或所有字段变化都视为批准失效的过度围栏.
7. 正常完成后让同一 `call-42` 再次经过 state-bound 生产入口, 检查是否新增第二次写入.
8. producer 输出固定九列 UTF-8 TSV, 不向独立验证器输出内部期望布尔值.
9. 独立 Python verifier 只读取 TSV, 根据场景、路径、结果、写入数和最终值重新判断反例.
10. 使用 awk 第二实现再次解析相同 TSV, 独立复核动作变化、相关状态变化、无关状态变化和完成后重放.
11. 完整生产夹具运行三次, 比较事件摘要与验证结果.

## 原始观测

三次完整生产轨迹均包含 13 个数据行, SHA-256 均为 `2d9c382f3e2c3c1f6cf690a426754b9178b9b551eebd8a9ec7f902292f52ac0b`.

三次首轮 producer 加内置断言的有效耗时分别为 0.501355 毫秒、0.275795 毫秒和 0.720173 毫秒. 这些数字只描述本轮单机确定性夹具, 不用于推断真实 HITL 系统延迟.

| 场景 | 路径 | 结果 | 新增写入 | 最终值 | 相关状态 |
| --- | --- | --- | ---: | --- | --- |
| 正常基线 | tool-wide | applied | 1 | alpha | ACTIVE |
| 正常基线 | action-bound | applied | 1 | alpha | ACTIVE |
| 正常基线 | state-bound | applied | 1 | alpha | ACTIVE |
| 批准后 action 改变 | tool-wide | applied | 1 | beta | ACTIVE |
| 批准后 action 改变 | action-bound | action_changed | 0 | initial | ACTIVE |
| 批准后 action 改变 | state-bound | action_changed | 0 | initial | ACTIVE |
| 批准后相关状态改变 | tool-wide | applied | 1 | alpha | LOCKED |
| 批准后相关状态改变 | action-bound | applied | 1 | alpha | LOCKED |
| 批准后相关状态改变 | state-bound | authority_state_changed | 0 | initial | LOCKED |
| 仅无关 metadata 改变 | tool-wide | applied | 1 | alpha | ACTIVE |
| 仅无关 metadata 改变 | action-bound | applied | 1 | alpha | ACTIVE |
| 仅无关 metadata 改变 | state-bound | applied | 1 | alpha | ACTIVE |
| state-bound 完成后重放 | state-bound | applied -> already_applied | 0 | alpha | ACTIVE |

工具级路径在批准后 payload 从 `alpha` 改为 `beta` 时仍写入 `beta`, 证明工具名级批准可以跨越具体动作变化.

action-bound 路径能够拒绝参数变化, 但相关状态从 ACTIVE 变为 LOCKED 而 action 字节保持不变时仍执行 1 次. 因此具体 call/action 身份解决了批准对象漂移, 仍没有解决批准依据的相关状态漂移.

state-bound 路径在 action 变化时返回 `action_changed`, 在相关状态变化时返回 `authority_state_changed`, 两种场景均零写入.

强反例中只改变无关 `note`, state-bound 仍执行原 action. 因此本轮首选路径绑定的是明确相关状态投影, 不是把整个世界状态或任意 metadata revision 都粗暴地纳入批准身份.

完成后的同一 `call-42` 再次经过 state-bound 生产入口返回 `already_applied`, 新增写入为 0.

## 独立验证

第二轮正式验证把 producer 与 verifier 拆为两个独立 Python 文件.

producer 只负责根据路径规则生成固定九列 TSV. 独立 verifier 不导入 producer, 只用 `csv` 读取场景、路径、结果、写入增量、写入总数、最终值和状态, 重新检查:

- 三条正常基线都恰好写入一次 `alpha`.
- action mutation 中 tool-wide 实际写入 `beta`, 两条 action digest 路径零写入拒绝.
- authority-state mutation 中 tool-wide 与 action-bound 各写入一次, state-bound 零写入拒绝.
- irrelevant-state mutation 中 state-bound 仍执行一次, 没有把无关 metadata 变化误判为批准失效.
- completed replay 中 state-bound 第二次进入生产入口新增写入为 0.

三次 producer 输出 SHA-256 完全一致, 独立 Python verifier 3/3 返回 `PY_VERIFIER_PASS`.

第二验证器使用 awk 独立解析同一 TSV, 不复用 Python 对象模型或 JSON 摘要实现, 对上述关键分类返回 `AWK_VERIFIER_PASS`.

producer 与 Python verifier 均通过 `py_compile`. 两个验证器仍共享场景命名、TSV 字段语义和 producer 生成的观测, 没有访问真实 OpenAI、Google 或其他 HITL 服务, 因此不构成完全外部独立验证.

## 强反例

本日有两个方向相反的强反例.

第一, 只把批准绑定具体 action 仍不足够. `call-42`、tool、target 与 payload 全部保持不变时, action digest 没有变化, 但相关权威状态已经从 ACTIVE 变为 LOCKED. action-bound 路径仍返回 `applied` 并写入一次, 说明“人批准的还是同一个动作”不能证明批准时的执行前提仍成立.

第二, 把整个可观察状态的任意变化都视为批准失效又可能过度保守. 只把无关 `note` 从 n0 改为 n1 时, 与本动作有关的 `target_status` 与 `owner` 均未变化. state-bound 路径只比较相关状态投影, 因而仍能执行原批准动作.

这两个反例共同限制结论: 需要绑定的是影响本次副作用授权和语义的相关状态, 不是永久工具许可, 也不是无差别的全世界 revision.

## 路径比较

| 路径 | 绑定工具 | 绑定具体 action | 绑定相关状态 | action 改变 | 相关状态改变 | 无关状态改变 | 完成后重放 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| tool-wide | 是 | 否 | 否 | 错误执行 | 错误执行 | 执行 | 本轮不作为首选 |
| action-bound | 是 | 是 | 否 | 拒绝 | 错误执行 | 执行 | 可结合完成记录 |
| state-bound | 是 | 是 | 是 | 拒绝 | 拒绝 | 执行 | 零新增写入 |

工具级路径状态检查最少, 但在两类故障中各产生一次错误副作用.

action-bound 增加 action digest 比较, 消除参数漂移, 但对批准依据的相关状态变化失明.

state-bound 再增加一次相关状态投影比较, 在本轮两类真实漂移中都零写入停止, 同时没有因无关 metadata 改变而拒绝. 改进来自更精确的批准合同, 不是更少操作.

## 暂时结论

状态为观察.

本次受控实验中, human approval 不是可以脱离批准对象和批准依据永久保存的布尔值.

工具级批准会跨越具体 action 参数变化. 具体 call/action 绑定能够解决这一问题, 但如果批准后与动作相关的权威状态发生变化, 旧批准仍可能在 action 字节完全相同时产生错误副作用.

本轮最强路径把批准绑定到具体 action digest 与明确相关的 authority-state projection, 在 action 或相关状态变化时零写入停止, 在无关 metadata 变化时仍允许执行. 该结果与 OpenAI 的 per-call approval 和执行前 guardrail 位置, 以及 Google 在确认后重新获取最新 screen 的建议方向一致, 但不证明这些产品内部自动实现本轮同样的状态投影语义.

今天只有一个新的受控研究单元, 三次同条件重复不计为三个独立实验, 不提升为候选或发现.

## 事实分层

### 已验证事实

- 三次生产轨迹各含 13 个数据行且 SHA-256 完全一致.
- 工具级批准在 payload 改为 beta 后仍执行一次并写入 beta.
- action-bound 与 state-bound 在 action digest 变化后都零写入拒绝.
- 相关状态从 ACTIVE 变为 LOCKED 后, tool-wide 与 action-bound 各执行一次, state-bound 零写入拒绝.
- 仅无关 note 变化时, state-bound 仍执行一次原 action.
- state-bound 已完成 intent 再次经过同一生产入口后新增写入为 0.
- 独立 Python verifier 3/3 通过, awk 第二实现通过, producer 与 verifier 编译检查通过.

### 基于证据的推断

- 批准身份至少需要回答两个问题: 人批准的是否仍是同一个动作, 以及批准时影响该动作合法性的相关状态是否仍成立.
- per-call approval 能显著缩小批准复用范围, 但无法单独覆盖外部权威状态在等待期间的变化.
- 相关状态投影比全局 revision 更精确, 因为无关 metadata 改变不必自动撤销批准.
- 对长时 Agent, approval 更适合视为带对象和前提的 capability, 而不是工具级永久布尔值.

### 未验证事项

- OpenAI、Google 或其他真实 Agent runtime 在批准恢复时具体如何处理外部资源版本变化.
- 哪些字段构成最小充分的相关状态投影, 以及状态服务与副作用 sink 不同一致性级别下的 TOCTOU 风险.
- `always_approve` 或同类持久权限在跨动作、跨 handoff、跨 resume 时的实际作用域与撤销语义.
- 人工确认后到真实不可逆提交之间仍可能发生的最后窗口.
