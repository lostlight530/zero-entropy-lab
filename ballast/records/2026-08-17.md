# Ballast 日记录 2026-08-17

类型: 每日专题
主题: effect receipt 与副作用持久化顺序的幽灵完成和重复执行

## 研究问题

Agent 在 unknown outcome 恢复中已经拥有正确的 effect identity 与当前执行权限时, receipt 自身的持久化顺序是否足以决定恢复安全性. 比较先写 receipt 再执行 effect、先执行 effect 再写 receipt、以及 effect 与 receipt 作为同一原子提交边界三条路径, 检查中断后重放是否出现幽灵完成或重复副作用.

本题承接 2026-08-15 至 2026-08-16 对 authoritative effect identity 的研究, 但不再改变 action、target incarnation 或当前执行权限. 本轮只攻击一个更底层前提: 一份身份完全正确的 receipt, 如果与真实副作用之间存在可观察的持久化间隙, 是否仍足以作为完成证据.

## 来源依据

查询日期为 2026-08-17.

- [PostgreSQL Documentation: Transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html) 访问于 2026-08-17. 文档把 transaction 描述为把多个步骤组合为 all-or-nothing operation, 未完成的中间状态对并发事务不可见, 失败时步骤不会部分生效. 适用边界是事务数据库中的原子提交, 不直接覆盖跨服务不可回滚副作用.
- [AWS Prescriptive Guidance: Transactional outbox pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) 访问于 2026-08-17. 文档明确指出双写中的任一操作失败都可能造成不一致, 并要求数据库更新与 outbox 记录在同一 transaction 中更新, 失败时整体回滚. 文档也提醒后续消息传递仍可能重复, 消费侧仍需幂等. 适用边界是数据库与事件通知的 dual-write 问题, 不能证明所有外部 sink 都能提供同一原子边界.
- [Stripe API Reference: Idempotent requests](https://docs.stripe.com/api/idempotent_requests) 访问于 2026-08-17. Stripe 说明同一 idempotency key 会保存首次请求结果并在重试时复用, 且只有 endpoint execution 开始后才保存 idempotent result. 适用边界是 Stripe 自身的服务器幂等合同, 不公开其内部 effect 与结果缓存的完整原子实现.

PostgreSQL 与 AWS 独立支持“两个需要共同成立的持久化事实之间存在中间故障窗口时, 单纯的先后双写不能自动提供原子完成语义”. Stripe 则提供实际幂等服务中“result evidence 不是在执行开始前无条件预写”的公开边界. 本轮实验只把这些原则转化为受控状态机, 不把任何服务合同外推为通用 exactly-once 证明.

## 可证伪假设

- H1: receipt-first 足够安全. 只要 receipt 已持久化, 即使 effect 尚未执行, 恢复也可以把 receipt 当作 authoritative effect evidence.
- H2: effect-first 足够安全. 只要先确保真实 effect 发生, receipt 稍后补写不会在重放时产生第二次副作用.
- H3: 对本轮单目标受控模型, effect 与 receipt 需要共享不可观察的原子提交边界, 才能同时排除 receipt 已有但 effect 未发生的幽灵完成, 以及 effect 已发生但 receipt 缺失导致的重复执行.

如果 receipt-first 在 receipt 已写入而 effect 未执行的中断后不会错误恢复 completed, H1 的风险解释被削弱.

如果 effect-first 在 effect 已发生而 receipt 未写入的中断后重放仍保持单次 effect, H2 的风险解释被削弱.

如果 atomic-bundle 在中断重放后出现 effect 与 receipt 分裂、重复 effect 或错误 completion, H3 被推翻.

## 控制条件

- 当前执行权限始终有效, 不改变 world state、intent、ownership、valid_until、task status、credential、approval 或 target incarnation.
- effect identity 始终正确且唯一, 不测试 key collision、action drift 或同名目标重建.
- 业务 effect 为把目标从 `clean` 写为 `marked`, 同时以 effect 计数记录每次真实副作用.
- receipt 为同一 effect identity 的持久化证据位, completion 与 receipt 分开保存.
- `receipt-first` 先提交 receipt, 后提交 effect.
- `effect-first` 先提交 effect, 后提交 receipt.
- `atomic-bundle` 在模型中只有一个不可分割状态转换同时提交 effect 与 receipt, 不暴露只提交其中之一的中间状态.
- crash-window 对三条路径都在首次 production entry 的第一个可中断持久化边界注入中断, 随后重新进入同一 production entry.
- completed replay 先正常完成, 再重新进入同一 production entry.
- 受控夹具使用 Python 标准库与系统 awk, 不使用数据库、缓存、外部依赖或网络写入.

## 实验设计

1. 正常基线分别执行三条 production path, 检查 effect、receipt 与 completion 是否都形成一次有效完成.
2. receipt-first 在 receipt committed 后、effect committed 前注入中断, 随后重新进入同一 production entry.
3. effect-first 在 effect committed 后、receipt committed 前注入中断, 随后重新进入同一 production entry.
4. atomic-bundle 不允许 effect 与 receipt 分裂, 在原子提交前注入中断, 随后重新进入同一 production entry.
5. 三条路径都执行 completed replay 强反例, 验证正常完成后的零新增副作用不能替代真正 crash-window 测试.
6. producer 输出固定 10 列 TSV, 包含首次结果、重放结果、effect 数、receipt 状态、completion、目标值、操作数与 event order, 不输出预设通过布尔值.
7. event order 保留 `receipt_committed`、`effect_committed`、`effect_receipt_atomic_commit`、`interrupt` 与 `replay_entry` 的先后关系, 使 verifier 能区分收敛到同一最终 completed 状态的不同历史.
8. 独立 Python verifier 不导入 producer, 从 TSV 的最终权威状态与 event order 重建三条 crash-window 的期望.
9. awk 第二实现只复核 crash-window 三条路径的 effect 计数、completion 与最终目标值.
10. producer 完整运行三次并比较轨迹 SHA-256, producer 与 verifier 额外执行 Python 语法编译检查.

## 原始观测

三次完整生产轨迹都包含 9 个数据行, SHA-256 均为 `2c29bef4baff12a12f3e6e403ee0dfdf2ce5ee07653bee0f5b4512e0f78d5cde`.

三次 producer 进程内记录的夹具执行耗时分别约为 0.039 毫秒、0.041 毫秒与 0.041 毫秒. 这些数字不包含完整解释器启动时间, 只用于确认本轮模型没有明显异常停顿, 不用于推断真实系统性能.

| 场景 | 路径 | 首次结果 | 重放结果 | effect 数 | receipt | completed | 最终值 | 操作数 |
| --- | --- | --- | --- | ---: | ---: | ---: | --- | ---: |
| 正常基线 | receipt-first | applied | - | 1 | 1 | 1 | marked | 5 |
| 正常基线 | effect-first | applied | - | 1 | 1 | 1 | marked | 5 |
| 正常基线 | atomic-bundle | applied | - | 1 | 1 | 1 | marked | 4 |
| crash-window | receipt-first | interrupted_after_receipt | effect_already_applied | 0 | 1 | 1 | clean | 6 |
| crash-window | effect-first | interrupted_after_effect | applied | 2 | 1 | 1 | marked | 8 |
| crash-window | atomic-bundle | interrupted_before_atomic_commit | applied | 1 | 1 | 1 | marked | 6 |
| completed replay | receipt-first | applied | already_completed | 1 | 1 | 1 | marked | 7 |
| completed replay | effect-first | applied | already_completed | 1 | 1 | 1 | marked | 7 |
| completed replay | atomic-bundle | applied | already_completed | 1 | 1 | 1 | marked | 6 |

receipt-first 的关键 event order 为 `permission_checked>receipt_committed>interrupt>replay_entry>permission_checked>receipt_seen>completion_saved`. 重放看到 receipt 后直接恢复 completion, 但 effect 数仍为 0, 最终目标仍为 clean. 这是“证据存在但被证明对象不存在”的幽灵完成.

effect-first 的关键 event order 先出现 `effect_committed>interrupt`, 重放时因为 receipt 尚不存在再次执行 effect, 最终 effect 数为 2. 最终值虽然仍为 marked 且 completion 为 1, 但历史已经发生重复副作用, 单看最终值无法识别该错误.

atomic-bundle 在首次进入时中断于原子提交之前, 没有形成 receipt-only 或 effect-only 中间状态. 重放后通过 `effect_receipt_atomic_commit` 一次形成 effect 与 receipt, 最终 effect 数为 1 并完成.

completed replay 中三条路径全部保持 effect 数 1. 因此“完成后再跑一次没有新增写入”是必要但不充分证据, 它无法暴露 effect 与 receipt 之间的未知结果窗口.

## 独立验证

producer 与 Python verifier 为两个独立文件, verifier 不导入 producer, 不读取 producer 内部成功布尔值或保存的期望对象.

Python verifier 独立检查:

- 三条正常基线都恰好形成 1 次 effect、1 份 receipt 与 completed.
- 三条 completed replay 都保持 1 次 effect 并返回 already_completed.
- receipt-first crash-window 的 receipt 为 1、completed 为 1, 但 effect 为 0 且最终值为 clean, event order 明确保存 receipt 在 interrupt 前而 effect 从未提交.
- effect-first crash-window 的最终 effect 数为 2, event order 明确保存第一次 effect 在 interrupt 前发生, 重放后又执行第二次 effect.
- atomic-bundle crash-window 在 interrupt 前没有 receipt-only 或 effect-only 提交, 重放后 effect 数恰好为 1.

三次独立 Python verifier 均返回 `PY_VERIFIER_PASS`.

第二验证器使用 awk 独立解析同一 TSV, 只依据 crash-window 的 path、effect 数、completed 与最终值返回 `AWK_PASS`.

producer 与 verifier 均通过 `py_compile`. 两个 verifier 仍共享 TSV 字段语义、相同原始轨迹与系统文件环境. atomic-bundle 是受控状态机中的单步提交模型, 本轮没有用真实事务数据库或外部 sink 制造进程级断电, 因而不能声称已验证任何具体存储系统的物理原子性.

## 强反例

第一, receipt 身份正确不等于 receipt 事实正确. receipt-first 没有 key collision、action drift 或 target alias, 但 receipt 在 effect 前先落地, 中断后仍会让恢复逻辑把不存在的 effect 当成已发生.

第二, effect-first 解决 ghost receipt 但没有解决 unknown outcome. effect 已经真实发生而 receipt 尚未落地时, completion 缺失与 receipt 缺失会把重放重新导向 effect, 最终状态仍正确却留下 effect 数 2 的历史重复.

第三, completed replay 会给出误导性的安全信号. 三条路径在完成后重放都没有新增 effect, 如果只测试 completed replay, receipt-first 与 effect-first 都会被错误评为幂等安全.

第四, 本轮并不证明“任何两个外部系统都能原子提交”. atomic-bundle 只是验证如果 effect 与 receipt 之间不存在可观察分裂状态, 受控模型能够同时避开两类窗口. 跨服务场景仍可能需要 sink 原生幂等、事务 outbox、可查询 authoritative receipt、补偿协议或安全停止.

## 路径比较

| 路径 | 正常基线 | crash-window | completed replay | 主要失败 | 基线操作数 |
| --- | --- | --- | --- | --- | ---: |
| receipt-first | 正确 | effect 0 但 completed 1 | 单次 effect | ghost receipt 导致零写入假完成 | 5 |
| effect-first | 正确 | effect 2 | 单次 effect | effect 已发生但 receipt 缺失导致重复执行 | 5 |
| atomic-bundle | 正确 | 单次 effect | 单次 effect | 本轮受控模型未观察到分裂窗口 | 4 |

操作数不是本轮主因. receipt-first 与 effect-first 正常基线操作数相同却在相反方向失败. atomic-bundle 的单步提交在模型中操作数更少, 但不能据此推断真实系统更快或更便宜, 因为真实事务协调可能引入额外成本.

## 暂时结论

本轮支持把 `authoritative effect identity` 再细分为两项要求: identity 必须正确绑定 action 与真实 target, 同时 receipt 的形成必须与被证明的 effect 存在可信的提交关系. 仅有一份身份正确但提前写入的 receipt 会造成 ghost completion, 仅在 effect 后补写 receipt 又会留下 unknown outcome 重复窗口.

对能够共享事务边界的本地 effect 与 receipt, 原子提交可以消除这两个可观察中间状态. 对不能共享事务边界的外部副作用, 本轮不支持假装拥有原子性, 恢复逻辑仍需查询 sink 的 authoritative effect evidence、使用 sink 原生 idempotency、事务 outbox 或在证据不足时安全停止.

该结论仅为单日观察, 不升级为新的 NOTES 发现.

- 使用不能共享事务边界的两个独立 sink, 检查 outbox 或 sink 原生幂等能否把重复窗口转化为可验证恢复.
- 加入 target incarnation 与 action identity 变化, 检查 atomic receipt 是否仍正确绑定被证明实体, 避免“原子但身份错误”.
- 加入 receipt 保留期与清理, 检查历史 effect 仍存在但 receipt 已过期时是否安全停止或重新查询权威状态.
- 用独立进程或不同语言 verifier 复核 event order, 降低共享 Python 语义合同风险.

## 体系增量

- 在 Unknown outcome 恢复门中增加 receipt provenance 检查: receipt 不只要有正确 identity, 还要能证明它与实际 effect 的提交关系.
- 将 `receipt exists` 明确降级为候选证据. 如果 receipt 可能先于 effect 独立提交, 不得直接据此恢复 completion.
- 将 `effect committed -> receipt missing -> replay` 与 `receipt committed -> effect missing -> replay` 作为一对对称故障窗口测试, completed replay 不能替代.
- 对能够共享单一事务的本地状态, 要求 effect 与 receipt 共同提交或共同回滚. 对跨服务副作用, 明确披露无法原子化的边界并依赖远端权威 evidence 或安全停止.
- 时序验证必须保留 receipt、effect、interrupt 与 replay 的 event order, 因为 receipt-first ghost completion 与正常 completed replay 都可能最终显示 completed=1.

## 事实分层

### 已验证事实

- receipt-first 在 receipt 已提交而 effect 未提交的中断后, 重放产生 effect 数 0、receipt 1、completed 1、最终值 clean 的错误完成.
- effect-first 在 effect 已提交而 receipt 未提交的中断后, 重放产生 effect 数 2, 虽然最终值与 completion 正确, 历史仍存在重复副作用.
- atomic-bundle 受控模型在原子提交前中断并重放后只产生 1 次 effect, 没有观察到 receipt-only 或 effect-only 中间状态.
- 三条 completed replay 都保持 effect 数 1, 因此 completed replay 单独无法区分两条弱路径.
- 三次轨迹 SHA-256 一致, Python verifier 3 次通过, awk 第二验证器通过, producer 与 verifier 均通过语法编译.

### 基于证据的推断

- effect receipt 的权威性不仅取决于 identity 绑定范围, 还取决于 receipt 与实际 effect 之间是否存在可信的提交关系.
- 在不能共享原子提交边界的跨服务副作用中, 本地 receipt 不应被自动视为远端 effect 已发生的充分证明.
- “先证明再执行”和“先执行再证明”分别暴露 ghost completion 与 duplicate effect 的对称窗口, 需要额外协议来封闭.

### 未验证事项

- 未验证 PostgreSQL、Stripe、AWS 或其他真实服务在本轮具体状态机下的物理崩溃恢复行为.
- 未验证真实数据库 transaction、fsync、multi-region replication 或 power loss 下的 durable atomicity.
- 未验证跨服务 two-phase commit、transactional outbox 实现、CDC、消息代理 redelivery 或补偿事务.
- 未验证 receipt TTL、清理、重建、跨账户 scope 与 target migration.
- 未证明 atomic-bundle 在不可回滚外部副作用中可直接实现.
