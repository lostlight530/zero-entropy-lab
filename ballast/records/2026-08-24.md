# Ballast 日记录 2026-08-24

类型: 每日专题
主题: 当前后置条件滞后读取造成的补偿后假完成

## 研究问题

当 unknown outcome 的历史 effect receipt 已经真实存在, 任务完成语义又要求当前 stateful postcondition 仍成立时, 恢复流程虽然重新读取 current postcondition, 但如果该读取来自滞后副本, 是否仍可能把已经被合法反转的 effect 错误判为当前完成

本轮改变故障位置: 不攻击 receipt 查询, receipt retention 或 receipt provenance, 而攻击 `receipt hit -> current postcondition read` 这一正向完成证据的 freshness

关键窗口为 `effect + receipt committed -> completion missing -> authoritative state reversed -> replica still shows old satisfied state -> replay`

## 来源依据

查询日期为 2026-08-24

- [Amazon DynamoDB read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html) 明确说明 eventually consistent read 可能暂时不反映已经成功完成的近期写入, strongly consistent read 则反映此前已成功的更新. 适用边界是 DynamoDB 读取一致性, 不直接证明 Ballast 受控夹具的 Agent 恢复语义
- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) 区分 `Any`, `Most recent`, `Not older than` 与 `Exact` 等读取语义, 并明确指出不要求强一致性的读取可能返回客户端已经见过的更旧 resource version. 适用边界是 Kubernetes API 读取版本语义, 不直接等价于任意 effect sink

两个独立官方来源共同支持一个设计前提: 查询成功不等价于读取足够新, current state verification 也需要说明 freshness 或 version boundary

把这个边界用于历史 receipt 已命中后的 current completion postcondition 属于本轮待证伪假设

## 可证伪假设

- H1: exact receipt hit 后重新读取 postcondition 就足够, 不需要额外 freshness 证明
- H2: 要求 postcondition read 至少覆盖当前 authoritative global revision 可以阻止滞后正向命中
- H3: 如果授权和完成语义只依赖目标 state projection, 使用 target-state revision 而不是 whole-store global revision 可以同时阻止 stale positive read 并减少无关状态造成的 over-fencing
- H4: linearizable current read 可以在本轮受控模型中直接区分被反转后的 `clean` 与副本旧值 `marked`
- H5: completed replay 不能替代 receipt hit 后 current postcondition stale-read 窗口

H1 的反证条件是 authoritative state 已经为 `clean`, replica 仍返回旧 `marked`, 路径据此直接保存 completion

H2 的强反例是只发生无关 global revision 变化, target-state revision 与 value 均未变化时, global fence 仍等待

H3 的反证条件是 target state 已经改变而 target-state fence 仍接受旧副本, 或只发生无关 global 变化时 target-state fence 也等待

H4 的反证条件是 authoritative state 已经被反转时 primary read 仍返回 `marked`

H5 的反证条件是 completed replay 能暴露上述 stale positive postcondition

## 控制条件

- task, normalized action, target incarnation 与 exact receipt identity 固定
- receipt 只在真实 forward effect commit 后保存, 因而本轮不攻击 receipt provenance
- replay 时 task status, intent, ownership, valid_until, credential 与 approval binding 保持有效
- 每次 B 侧真实 forward effect commit 前重新记录 `B:permission_valid`
- completion contract 固定要求当前 authoritative target value 为 `marked`
- relevant state projection 只包含 target state value 对应的 `target_state_rev`; 无关对象变化只推进 `global_rev`, 不推进 `target_state_rev`
- `eventual-postcondition` 在 receipt hit 后直接使用 replica 当前可见 value
- `global-revision-fence` 要求 replica global revision 不旧于当前 permission snapshot 的 global revision, 不满足时等待追平后再读 postcondition
- `target-state-fence` 要求 replica target-state revision 不旧于当前 permission snapshot 的 target-state revision, 不满足时只等待相关目标状态追平
- `linearizable-postcondition` 直接读取 authoritative current target state
- `reversal-lag-after-receipt` 在 A effect 与 receipt 后中断, 随后 authoritative target 从 `marked` 合法反转为 `clean`, replica 保持反转前状态
- `unrelated-global-lag` 保持 target 为 `marked`, 只让无关对象推进 global revision, replica target state 没有语义滞后
- completed replay 固定在 completion 已保存后重新进入同一 production entry
- 夹具只使用 Python 标准库与系统 awk, 不访问真实 DynamoDB, Kubernetes 或外部 effect sink

## 实验设计

1. 四条路径执行 normal-no-prior, 没有历史 receipt, 检查是否都执行一次必要 effect 并达到 `marked`
2. 四条路径执行 reversal-lag-after-receipt, A 提交 effect 与 receipt 后在 completion 前中断, authoritative target 被反转为 `clean`, replica 仍为旧 `marked`, B 从同一 production entry 恢复
3. 四条路径执行 unrelated-global-lag, target value 与 target-state revision 不变, 只推进 unrelated global revision, 检查 global fence 是否产生 over-fencing
4. 四条路径执行 completed-replay, completion 已存在后重新进入同一 production entry
5. producer 输出 scenario, path, effect_count, completed, authoritative value, result, ops 与 event_order, 完整运行三次并比较 stdout TSV SHA-256
6. 独立 Python verifier 不导入 producer, 从 event_order 重建真实 forward effect commit 数, 检查每个 B effect 前存在 current permission evidence, 并复核 stale positive 与 over-fencing 强反例
7. awk 第二验证实现独立复核 reversal-lag 与 unrelated-global-lag 的决定性结果
8. producer 与 verifier 执行 `py_compile`

## 独立验证

Python verifier 与 producer 为两个独立文件

verifier 不导入 producer, 不读取 producer 内部成功布尔值或保存的期望对象

Python verifier 独立检查

- 16 个 scenario/path 组合完整且唯一
- event_order 中真实 forward effect commit 数与输出 effect_count 一致
- 每个 B 侧 effect commit 前都存在 `B:permission_valid`
- normal-no-prior 四条路径均 effect 1, completed 1, authoritative value `marked`
- reversal-lag-after-receipt 的 eventual-postcondition 为 effect 1, completed 1, authoritative value `clean`
- 相同反转场景的 global-revision-fence, target-state-fence 与 linearizable-postcondition 均为 effect 2, completed 1, authoritative value `marked`
- eventual-postcondition 的 event_order 同时包含 authoritative reversal 与随后 stale replica `marked` 读取, 因而 verifier 能区分两个收敛到 completed 的不同历史
- unrelated-global-lag 的 global-revision-fence 存在 `B:wait_global_catchup`
- unrelated-global-lag 的 target-state-fence 不存在 `B:wait_target_catchup`
- completed-replay 四条路径均 effect 1, authoritative value `marked`, 且确实经过 `B:completed_short_circuit`

三次 Python verifier 均返回 `PY_VERIFIER_PASS`

awk 第二验证实现返回 `AWK_PASS`

producer 与 verifier 均通过 `py_compile`

两个 verifier 仍共享 TSV 字段语义, event label 约定与同一系统运行环境

因此本轮不是对真实数据库 replica, watch cache 或跨区域状态存储的端到端验证

## 强反例

- reversal-lag-after-receipt 直接推翻 H1: exact receipt 为真且恢复流程确实重新读取 postcondition, 但 stale positive `marked` 仍让已经被反转到 `clean` 的 authoritative state 错误 completed
- unrelated-global-lag 限制 H2: whole-store global freshness 虽能阻止本轮 stale positive, 但只发生无关状态变化时仍额外等待, 说明安全围栏可以过宽
- target-state-fence 在 reversal-lag 中等待并恢复 `marked`, 在 unrelated-global-lag 中不等待, 支持 H3 的受控相关投影价值; 该结论依赖 `target_state_rev` 确实保守覆盖所有会改变完成语义的目标状态
- linearizable-postcondition 在反转场景直接看到 `clean`, 支持 H4, 但不证明真实系统一定提供同等读取合同
- completed replay 四条路径全部安全, 因为 completion 已存在时不会进入 receipt 后 postcondition freshness 判断, 因而不能替代本轮 crash-window

linearizable-postcondition 在本地夹具操作数更少, 但这不是实际远端延迟或成本测量, 不用于推断真实基础设施性能

## 暂时结论

状态保持观察

本轮支持把 `current completion postcondition` 自身也纳入 freshness 合同: exact receipt 能证明历史 occurrence, 重新读取 postcondition 能检查当前完成语义, 但 postcondition read 若不能证明足够新, 仍可能把已经失效的旧 satisfied state 当成当前事实

因此对要求当前状态持续成立的可逆 effect, 恢复判断至少需要区分 `historical effect evidence` 与 `fresh current postcondition evidence`

whole-store global revision 可以作为保守围栏, 但可能因无关变化 over-fence. relevant target-state projection 可以减少这种无关等待, 前提是依赖字段确实完整覆盖完成语义; 无法证明 projection 完整时仍应使用更强读取或安全停止

本轮不升级 METHOD, CASES 或 NOTES. 这是 current postcondition freshness 的首个独立日实验, 与 8 月 20 日 stale receipt miss 的故障位置不同

## 复验条件

- 在真实提供 eventual 与 strong read 的存储上复验 receipt hit 后 current postcondition stale positive
- 加入 postcondition read 后到 completion commit 前再次变化的窗口, 检验 read freshness 与 decision-time binding 是否需要二次 revision compare
- 加入 target metadata 变化但完成语义不变的反例, 检查 target-state projection 是否仍可能 over-fence
- 改变任一真实相关字段, 检查 projection 是否会 under-fence
- 加入 postcondition read 不可用与 stale cache fallback, 检验 `hit / miss / unknown` 分类能否复用到正向完成证据
- 加入多目标 postcondition, 检查单一 target revision 是否足够表达跨对象完成语义

## 体系增量

- 把恢复模型细化为 `current execution permission + historical effect evidence + fresh current completion postcondition`
- current postcondition 的“查询成功”不能单独证明当前性, 还需要读取 consistency, revision 或等价 freshness boundary
- relevant state projection 不只用于执行权限和 approval freshness, 也可用于限制 current postcondition 的 over-fencing, 但必须保守覆盖完整完成语义
- completed replay 继续保持独立测试, 不能替代 receipt hit 后 postcondition stale-read 的真实 production-entry replay
- 任何因为 stale postcondition 失效而重新执行的 effect, 仍必须在副作用前重新确认 current execution permission

## 事实分层

### 已验证事实

- 受控夹具中 reversal 已经把 authoritative value 从 `marked` 变成 `clean`, replica 仍停在旧 target-state revision 2 并返回 `marked`
- eventual-postcondition 在该 stale positive 上保存 completion, 最终为 effect 1, completed 1, authoritative value `clean`
- global-revision-fence, target-state-fence 与 linearizable-postcondition 都恢复到 authoritative value `marked`, forward effect 总数为 2
- unrelated-global-lag 中 global-revision-fence 额外等待, target-state-fence 不等待且正确确认目标仍为 `marked`
- 四条 completed replay 均保持 forward effect 1
- 三次 producer 轨迹哈希完全一致, Python verifier 3 次通过, awk verifier 通过, producer 与 verifier 均通过 `py_compile`

### 基于证据的推断

- positive current postcondition evidence 与 negative prior-effect evidence 一样存在 freshness 边界, stale positive 也可以形成假完成
- global revision freshness 可以保守覆盖本轮 stale read, 但 relevant target-state revision 在依赖投影完整时更精确
- historical occurrence 与 current completion 的分离需要继续加入 `current evidence freshness`, 不能只写成“重新读一次当前状态”

### 未验证事项

- 未把真实 DynamoDB, Kubernetes, etcd 或其他远端存储作为实验目标
- 未验证跨区域复制, cache eviction, quorum 故障, watch progress, read-after-write 延迟分布或真实 linearizable read 成本
- 未证明 `target_state_rev` 在真实复杂任务中足以覆盖全部完成语义依赖
- 未测试 postcondition read 与 completion commit 之间再次变化的 TOCTOU 窗口
- 未测试多目标或不可逆 occurrence-only effect 的完成合同
