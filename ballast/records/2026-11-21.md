## 研究问题

Can a delivered webhook ID, event ID, or object/type pair establish whether an exact downstream non-idempotent operation occurred, was authorized at effect time, and remains currently complete after event replay

## 来源依据

- [Stripe webhook official documentation](https://docs.stripe.com/webhooks) accessed 2026-11-21, distinguishes redelivery of one Event and separate Event objects with the same data.object identity and event.type, and explicitly warns that event delivery order is not guaranteed
- [Stripe idempotent request documentation](https://docs.stripe.com/api/idempotent_requests) accessed 2026-11-21, documents request-side key retention and same-request semantics, not eternal dedup of downstream webhook side effects
- [GitHub official webhook redelivery example](https://docs.github.com/en/webhooks/using-webhooks/automatically-redelivering-failed-deliveries-for-a-repository-webhook) accessed 2026-11-21, identifies a stable GUID across attempts of the same GitHub webhook delivery, distinct publisher and event contract from Stripe
- Stripe and GitHub are separate publishers, not independent witnesses for the authored fixture, external authorization, or a live effect sink, and their different ID namespaces must not be silently merged

## 可证伪假设

H1 an Event-ID-only weak handler may PROCESS when a separately generated Event has a new ID despite the same business effect having a prior positive receipt
H2 object/type dedup suppresses one class of vendor duplicate, but cannot by itself prove task-defined operation, current incarnation, historical effect-time authority or exact effect-set completion
H3 the bounded reference and separately implemented tuple reconstruction should reject duplicate/extraneous receipt identities, conflicting positive/MISS, incomplete authoritative query coverage and TOCTOU
Falsifiers include any counterexample that causes the reference to emit MODEL_DONE or MODEL_RETRY_GATED without its authored preconditions, model/verifier disagreement, or an actual trusted sink result that refutes the modeled authority assumptions

## Action-integrity state

Current permission is a synthetic at-commit gate for new effects, never historical authorization for old effects
Historical occurrence is only represented by authored receipts with nonempty ID plus run/attempt, task, operation, intent, tenant, publisher and incarnation fields, still no real sink authority

Event creation time and delivery ID are not authoritative effect ordering or sink occurrence proofs
