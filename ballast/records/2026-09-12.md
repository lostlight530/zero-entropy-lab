## 研究问题

暂停后的任务在恢复时检查旧批准仍有效, 但真正副作用到达线性化点时已经越过 approval valid_until, 仅依赖恢复时 freshness check 是否会产生 stale unauthorized effect

本轮攻击窗口为 `RESUME approval valid -> time advances past approval valid_until -> EFFECT`

核心区分是批准在恢复时点有效, 与批准在 effect commit 时点仍有效是否属于同一个证明义务

## 来源依据

查询日期为 2026-09-12

- [RFC 7519 JSON Web Token](https://www.rfc-editor.org/rfc/rfc7519.html) 的 `exp` 规则要求当前时间必须早于 expiration time, 到达或超过 expiration 后 token 不应继续被接受. 本轮只采用有限命题: 带时间边界的授权材料不能因为更早时点曾有效就被外推为永久有效, 不把 JWT 语义直接等同于人工批准
- [AWS IAM security credentials](https://docs.aws.amazon.com/IAM/latest/UserGuide/security-creds.html) 说明 temporary security credentials 具有有限生命周期, 到期后 AWS 不再认可其 API 访问能力. 本轮只采用有限命题: 授权能力的时间有效性需要在实际使用时保持成立, 不把 AWS credential 直接等同于 Ballast approval

两个独立权威来源共同支持有限设计前提: temporal authorization evidence 具有真实有效期边界, 先前有效不能自动证明更晚执行点仍获授权

外部来源不证明本地 effect_count、event_order 或 PASS

## 可证伪假设

- H1: 只要 approval action identity 与当前 action 一致, 恢复后就可以继续执行, 不需要重新检查 approval valid_until
- H2: 在 resume 时检查 approval 未过期已经足够, 即使 effect commit 发生在更晚时刻
- H3: approval relevant projection 至少包含 action identity 与 valid_until, 并在 effect 受保护边界重新评价时间条件, 可以拒绝跨过 deadline 的 stale effect
- H4: whole-global revision 也可以保守阻止 relevant drift, 但无关 metadata 变化可能产生额外 over-fencing
- H5: current execution permission 仍是独立门, approval freshness 不能替代 cancellation 等任务级权限
- H6: completed replay 必须从 production entry 重入且保持零新增 effect

H1 与 H2 的反证条件是 `expires-after-resume`: resume_time=99 小于 approval_until=100, 但 effect_time=101 已不再处于批准窗口, 弱路径仍 effect_count=1

H3 的反证条件是 approval-bound-effect 在相同场景仍执行 effect, 或在只改变无关 metadata 时错误停止

## 控制条件

- action identity 固定为 `action-42`, effect identity 固定为 `op-112`
- approval valid_until 固定为逻辑时刻 100
- normal-valid 使用 resume_time=90、effect_time=95
- expires-after-resume 使用 resume_time=99、effect_time=101, 专门制造恢复检查与 effect commit 之间跨过 deadline
- already-expired 使用 resume_time=101、effect_time=102, 作为明显过期控制
- unrelated-metadata 保持 approval 与 permission 不变, 只推进无关 global revision
- permission-cancelled 保持 approval 时间有效但 current permission=0
- completed-replay 已有 completion, 从相同 production entry 重入
- action-only 只核对 action identity
- resume-time-check 在 resume 时评价 valid_until, 之后不再绑定时间边界
- approval-bound-effect 在 effect 边界评价 action + valid_until, 并独立检查 current permission
- global-revision-effect 使用 whole-global revision 保护变化, 同时在 effect 边界评价 approval 时间
- fixture 只使用 Python 标准库与系统 awk

already-expired 中 resume-time-check 与 approval-bound-effect 都 effect_count=0, 排除强路径只是特殊识别跨窗口场景而不能处理普通过期的解释

## 强反例

第一强反例攻击 resume-time approval check 足够

expires-after-resume 中 t=99 的检查完全正确返回 valid, 只有随后时间推进到 t=101. resume-time-check 仍执行 effect, 证明正确的旧时点判断不能自动续期到更晚的 commit 点

第二强反例攻击 action identity 一致即可继续

action-only 的 action identity 从未改变, 但 effect 发生时 approval 已过期, 仍产生 effect_count=1. 因而 action binding 与 temporal freshness 是两个不同字段

反方向强反例只改变无关 metadata

approval-bound-effect 在 metadata-only 场景正常执行, global revision 则额外冲突, 说明把 valid_until 纳入 relevant projection 不要求 whole-world revision 过度围栏

permission-cancelled 进一步表明 approval 仍有效也不能替代 current task permission

## 路径比较

- action-only 操作少, 但完全漏掉 temporal expiry
- resume-time-check 能拒绝已经过期的批准, 但 read 与 effect 分离时仍存在时间 TOCTOU
- approval-bound-effect 增加 effect-time 条件评价, 在跨 deadline 场景零写入停止, metadata-only 场景保持一次合法 effect
- global-revision-effect 对 expiry 同样保守安全, 但无关 metadata 变化时额外停止
- 结果质量优先于少一次时间检查; stale unauthorized effect 不能因为路径更短而计为有效优化
- 本地逻辑时钟与 Python 运行耗时不外推真实批准系统性能

## 暂时结论

证据状态为观察

本轮支持 H3 与 H5, 推翻 H1 与 H2

approval freshness 的 temporal dependency 不能只在恢复时检查. 当副作用发生时点可能越过 valid_until, 时间边界必须参与受保护 effect decision, 或使用能够提供等价保证的服务端条件

`resume approval valid` 是 point-in-time observation, 不是任务级授权续期信号

relevant approval projection 可以显式绑定 action identity 与 valid_until, 同时避免 unrelated metadata 引起的 whole-global over-fencing
