# Ballast 日记录 2026-08-09

类型: 每日专题
主题: 迟到重试中的基准漂移与条件围栏

## 研究问题

任务第一次执行后响应丢失, 随后权威状态被其他操作推进, 原任务迟到重试时, 无条件重放、严格代际围栏和代际围栏加目标后置条件三条路径中, 哪一种能同时避免覆盖较新状态并避免把已经实现的目标误判为失败

## 来源依据

查询日期为 2026-08-09

- [RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html) 发布于 2022-06, Section 13 规定条件请求, `If-Match` 常用于状态变更方法以防止 lost update, 条件不满足时不得执行原方法, 支持在应用旧写入前核对客户端已知状态与当前表示是否仍一致
- [Google Cloud Storage Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions) 访问于 2026-08-09, generation-match precondition 只在对象 generation 与预期一致时执行, 文档明确用迟到删除请求覆盖新对象的竞态说明条件写入可阻止旧操作作用于新代际
- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) 访问于 2026-08-09, 当客户端携带的 `resourceVersion` 已过时时 API server 返回 `409 Conflict`, 文档建议需要检测 lost update 的客户端让更新依赖现有 `resourceVersion` 并在冲突后重新处理

RFC Editor, Google Cloud 与 Kubernetes 来自不同标准或实现体系, 都支持状态变更前检查当前版本或代际, 但这些来源不证明所有业务目标都能仅由版本冲突判断完成, 也不证明版本变化必然意味着目标未实现

## 可证伪假设

- H1: 迟到任务只要再次经过原生产入口并成功返回, 就可以覆盖当前状态, 因为它代表同一任务的合法恢复
- H2: 迟到任务必须先核对读取时的基准代际, 如果当前代际已变化就停止写入, 这样可以避免旧任务覆盖较新状态
- H3: 代际变化后还应独立检查目标后置条件, 如果新状态已经满足原目标则返回 `already_satisfied`, 只有目标不满足时才返回 `generation_conflict`

如果无条件重放在基准变化后仍能保留较新状态, H1 的风险解释被削弱

如果严格代际围栏会错误修改较新状态, H2 被推翻

如果目标后置条件检查在代际变化但目标已满足时仍无法区分已完成与冲突, H3 被推翻

## 控制条件

- 初始权威状态为 generation 1, value 10
- 原任务身份为 `late-7`, 读取 generation 1 后目标为 value 20
- 第一次生产入口调用把 value 写为 20 并推进 generation
- 注入响应丢失, 调用方不知道第一次调用结果
- 在迟到重试到达前, 独立操作把权威状态推进到 value 30 和更高 generation
- 弱路径不检查 generation, 每次调用都写入目标 value 20
- 严格路径要求当前 generation 等于任务读取时的 generation 1
- 目标感知路径先检查 generation, 失配后再从当前权威状态直接检查 value 是否已经等于目标
- 强反例把当前状态推进到更高 generation 但 value 恰好已经为 20
- 实验仅使用 Python 标准库和系统临时目录, 文本显式 UTF-8, 每轮结束后清理临时目录

## 实验设计

1. 为三条生产路径分别初始化 generation 1, value 10
2. 让同一任务经过各自生产入口一次, 模拟原始操作已经执行但响应丢失
3. 由独立状态变化把当前权威值推进为 30 并增加 generation
4. 记录迟到重试前的当前 generation 与副作用写入计数
5. 让迟到任务重新经过同一生产入口, 记录状态码, 写入增量和最终值
6. 对严格路径和目标感知路径构造强反例, 当前 generation 已变化但 value 已由其他操作达到 20
7. 再让同一迟到任务经过原生产入口, 比较 `generation_conflict` 与 `already_satisfied`
8. 独立验证逻辑从初始夹具、目标值、并发目标和最终原始观测重新推导期望条件, 不读取生产路径内部成功布尔值
9. 同一控制条件完整运行三次, 比较结果质量, 写入数量和验证后有效耗时

## 原始观测

三次完整运行得到一致观测摘要 `566a82ce8a43fb438bc231586f51c961e77d3d4686ad8306d28195a017dd4d89`

| 路径 | 迟到重试结果 | 重试新增写入 | 最终 generation | 最终 value |
| --- | --- | ---: | ---: | ---: |
| 无条件重放 | applied | 1 | 4 | 20 |
| 严格代际围栏 | generation_conflict | 0 | 3 | 30 |
| 代际围栏加目标检查 | generation_conflict | 0 | 3 | 30 |

弱路径的迟到重试再次成功执行, 但把更新后的 value 30 覆盖回旧目标 20, 因此命令成功与生产入口成功都没有证明恢复正确

严格路径和目标感知路径都在 generation 已变化时拒绝旧写入, 保留 value 30, 迟到重试新增写入为 0

强反例中当前状态为 generation 2, value 20

| 路径 | 强反例结果 | 新增写入 | 最终 value |
| --- | --- | ---: | ---: |
| 严格代际围栏 | generation_conflict | 0 | 20 |
| 代际围栏加目标检查 | already_satisfied | 0 | 20 |

三次完整运行的验证后有效耗时分别为 8.440 毫秒, 3.624 毫秒和 3.076 毫秒, 仅用于记录本机受控样本成本, 不用于推断真实服务性能

## 独立验证

验证逻辑没有复用生产入口的分支判断结果作为期望值, 而是从控制夹具重新推导

- 旧任务目标为 value 20
- 并发推进后的权威目标为 value 30
- 基准变化后无条件重放若写回 20, 就违反保留较新状态的后置条件
- 基准变化后严格路径和目标感知路径都必须保持 value 30 且重试写入增量为 0
- 强反例中较新 generation 的当前 value 已经等于 20, 因此目标感知路径应能在不写入的情况下识别目标已满足

三次验证均无错误

本轮独立验证与生产路径仍共享同一 Python 运行时, JSON 解析语义和文件系统, 没有通过独立 Python 进程运行, 原因是当前环境中子进程版受控实验两次超时且没有形成有效观测

因此本轮验证在期望推导和代码分支上独立, 但不是进程级独立, 该限制保留为未验证边界

## 强反例

仅使用 generation 冲突作为最终执行判断会把所有基准变化都归类为失败

当其他操作已经把当前状态推进到更高 generation, 但最终 value 恰好已经满足原任务目标 20 时, 严格路径返回 `generation_conflict`

这个结果没有破坏数据, 但它说明版本失配只能证明原任务不能直接按旧基准写入, 不能单独证明目标尚未完成

目标感知路径在相同强反例中读取当前权威状态, 确认 value 已经为 20, 返回 `already_satisfied` 且新增写入为 0

因此首选解释不是所有迟到任务都应简单因版本变化失败, 而是版本变化先关闭旧写入权限, 随后由当前后置条件决定是已完成还是需要重新规划

## 路径比较

| 路径 | 基准检查 | 当前目标检查 | 覆盖较新状态 | 强反例识别 | 迟到重试写入 |
| --- | --- | --- | --- | --- | ---: |
| 无条件重放 | 否 | 否 | 是 | 不适用 | 1 |
| 严格代际围栏 | 是 | 否 | 否 | 误判为冲突 | 0 |
| 代际围栏加目标检查 | 是 | 是 | 否 | already_satisfied | 0 |

弱路径操作最少, 但代价是把成功返回建立在错误状态上

严格围栏增加一次代际检查, 能阻止 lost update, 但没有回答目标是否已经由其他路径实现

目标感知路径在冲突后再增加一次当前后置条件检查, 操作数量更多, 但在不允许旧写入的同时区分安全停止与幂等完成

## 暂时结论

状态为观察

本次受控实验中, 迟到任务重新经过原生产入口并返回 `applied` 仍可能覆盖较新的权威状态, 因此生产入口重放本身不是恢复正确性的充分条件

代际围栏能阻止旧任务在基准变化后继续写入, 与 RFC 9110 条件请求, Cloud Storage generation precondition 和 Kubernetes `resourceVersion` 的公开合同方向一致

强反例同时表明版本冲突不是最终完成判断, 当前状态已经满足目标时, 在保持零新增写入的前提下识别 `already_satisfied` 比统一返回冲突保留了更多真实状态信息

今天仍是单个受控研究单元, 三次同条件重复不计为三个独立实验, 不提升为候选或发现

## 复验条件

使用真实提供 ETag, generation 或 resourceVersion 的服务复验迟到 PUT, DELETE 或更新请求, 记录条件失败后的真实返回语义和重试合同

增加并发窗口, 让当前状态在版本检查与后置条件读取之间再次变化, 检查目标感知路径是否需要同一快照或再次绑定版本

构造部分目标已满足, 多字段目标冲突, 非交换更新和不可逆副作用, 检查单值后置条件是否过弱

## 事实分层

### 已验证事实

- 无条件迟到重试新增写入 1 次并把 value 30 覆盖回 20
- 严格代际围栏在基准变化后返回 `generation_conflict`, 新增写入 0, 最终 value 保持 30
- 目标感知路径在基准变化且目标未满足时同样返回 `generation_conflict`, 新增写入 0, 最终 value 保持 30
- 强反例中严格路径返回 `generation_conflict`, 目标感知路径返回 `already_satisfied`, 两者新增写入都为 0
- 三次单进程完整运行的原始观测摘要一致, 分项验证均无错误
- 每次运行的系统临时目录均已清理

### 基于证据的推断

- 基准代际是迟到任务继续写入权限的围栏, 不是目标完成状态本身
- 条件失败后直接重试旧操作会重新引入覆盖风险, 更安全的恢复顺序是重新读取当前事实源后决定已完成, 冲突停止或生成新意图
- 结果质量需要优先于减少读取次数或操作数量, 因为弱路径虽然少一次验证, 却产生了错误最终状态

### 未验证事项

- 真实远端服务在 ETag, generation 和 resourceVersion 冲突后的具体重试语义
- 版本检查与后置条件读取之间再次发生状态变化时的原子性边界
- 多字段, 部分完成和非交换操作中目标后置条件的最小充分集合
- 进程级独立验证和不同实现验证器的结果
- 完整 `ballast/tools/check.py` 在最终远端树上的结果

## 指标

- 有效完成: 无条件重放为否, 严格围栏为安全停止, 目标感知强反例为幂等完成
- 生产入口重放: 三条路径的迟到任务都重新经过各自原生产入口, 不是重复只读验证
- 重放新增副作用: 无条件路径 1, 两条围栏路径 0

- 执行状态: 幂等完成与安全停止按路径分别记录
