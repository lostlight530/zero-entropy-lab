# Ballast 日记录 2026-08-11

类型: 每日专题
主题: 接收端已见代际围栏的所有权交接盲区

## 研究问题

租约已经从旧执行者切换到新执行者后, 如果目标服务尚未见过新 generation, 接收端仅保存自己见过的最大 generation 是否足以拒绝旧执行者的迟到提交, 还是必须在副作用接受边界核对当前权威 holder 与 generation.

本题不是重复 2026-07-27 的租约隔离实验. 7 月 27 日已经比较缓存租约判断与提交时当前 holder/token 校验. 今天专门攻击一个中间实现: 接收端不查询当前权威租约, 只拒绝低于自身 `max_seen_generation` 的请求.

## 来源依据

查询日期为 2026-08-11.

- [The Chubby lock service for loosely-coupled distributed systems](https://research.google/pubs/the-chubby-lock-service-for-loosely-coupled-distributed-systems/) 发表于 OSDI 2006. 论文描述旧锁持有者请求可能在新持有者动作之后迟到到达, 并给出 lock acquisition count 与 sequencer 机制. 接收端应拒绝较旧 acquisition count, sequencer 包含 lock generation 并应在受保护请求上验证. 适用边界是 Chubby 的锁和 sequencer 设计, 不证明任何仅有 TTL 的租约自动获得同等安全性.
- [Kubernetes Lease API](https://kubernetes.io/docs/reference/kubernetes-api/coordination/lease-v1/) 访问于 2026-08-11. LeaseSpec 明确记录 `holderIdentity`, `renewTime`, `leaseDurationSeconds` 和 `leaseTransitions`, 说明所有权与交接次数是显式状态. 适用边界是 Kubernetes Lease 对象语义, 文档没有声称该对象会自动阻止旧 holder 对外部服务产生副作用.
- [etcd API 3.6](https://etcd.io/docs/v3.6/learning/api/) 访问于 2026-08-11. etcd 将 Lease 定义为检测客户端存活并为键提供 TTL 的机制, 同时 Transaction 可对 value, version 或 revision 执行原子 compare 后再执行请求. 适用边界是 etcd KV 与 Lease API, 本轮没有运行真实 etcd 服务.

三个来源共同区分了存活租约、所有权代际与副作用接受条件. 它们支持研究设计, 但不直接证明本轮三个受控路径的实验结果.

## 可证伪假设

- H1: 旧执行者只要本地缓存的 lease deadline 尚未到期, 就可以继续提交, 即使权威协调器已经完成 holder 交接.
- H2: 接收端只要维护自己见过的最大 generation, 并拒绝更小 generation, 就与查询当前权威 holder/generation 等价.
- H3: 每次副作用提交在接受边界核对当前权威 holder 与 generation, 可以在新 holder 尚未触碰 sink 的窗口中拒绝旧提交.

如果注入交接和本地时钟偏差后 H1 仍不接受过期 holder, H1 的风险解释被削弱.

如果新 holder 尚未向 sink 发送任何 generation 2 请求时, `max_seen_generation` 路径仍能拒绝 generation 1, H2 的风险解释被削弱.

如果提交时权威核对路径在 holder 已变为 W2, generation 已变为 2 后仍接受 W1, generation 1, H3 被推翻.

## 控制条件

- 初始权威 holder 为 W1, generation 为 1, W1 的目标值为 20.
- 所有权交接后 holder 为 W2, generation 为 2, 当前目标值为 30.
- 本地 TTL 路径缓存 deadline 10, 故障注入时权威侧已经发生交接, 但 W1 的本地逻辑时钟仍为 8, 因而错误认为旧租约可用.
- 已见代际路径只维护 sink 已接受请求中的最大 generation, 不主动读取协调器.
- 权威代际路径在每次提交时读取当前 holder 与 generation, 只有 actor 和 generation 同时匹配才允许副作用.
- 三条路径都使用 `(generation, intent_id)` 去重, 用于单独验证完成后同输入重放是否新增写入.
- 实验使用确定性逻辑状态, Python 标准库与系统已有 awk, 样本和验证逻辑只位于本轮系统临时目录.

## 实验设计

1. 正常基线中保持 W1, generation 1, 比较三条路径能否提交 value 20.
2. 第一类故障注入先完成 W1 -> W2 交接, 再让 W2 先提交 generation 2, value 30, 最后重放 W1 的 generation 1 迟到提交.
3. 第二类故障注入作为强反例, 完成交接后不让 W2 先触碰 sink, 直接让 W1 generation 1 迟到提交, 随后才让 W2 generation 2 提交 value 30.
4. 比较最终 value, 接受写入次数, stale generation 是否被接受以及每条路径的校验操作数.
5. 对已经完成的 W2 generation 2, intent `job-b` 重新经过同一提交入口, 检查是否新增写入.
6. 生产夹具输出固定十列 UTF-8 TSV 事件轨迹, 不输出内部期望布尔值给验证器.
7. 独立 Python 进程从 OWNER 与 HANDOFF 事件重建每个场景的当前 generation, 检查 stale accept, 最终值与写入计数.
8. 再使用 awk 独立解析同一 TSV, 重新计算强反例中的 stale accept, 最终值和写入次数.
9. 完整夹具运行三次, 比较轨迹摘要和验证结果.

## 原始观测

三次完整生产轨迹 SHA-256 均为 `d70361dff361a1a2ea3e0d8e2cd50c76d153f2f8cad8205ff41c0efa9f85156c`, 每次 66 个事件行.

三次生产夹具本体耗时分别为 0.047 毫秒, 0.045 毫秒和 0.048 毫秒. 该数字只描述本轮单机确定性夹具, 不用于推断真实分布式服务性能.

| 场景 | 路径 | 提交结果序列 | 最终值 | 写入次数 |
| --- | --- | --- | ---: | ---: |
| 正常基线 | 本地 TTL | applied | 20 | 1 |
| 正常基线 | 已见代际围栏 | applied | 20 | 1 |
| 正常基线 | 权威代际围栏 | applied | 20 | 1 |
| W2 先提交后 W1 迟到 | 本地 TTL | applied, applied | 20 | 2 |
| W2 先提交后 W1 迟到 | 已见代际围栏 | applied, stale_rejected | 30 | 1 |
| W2 先提交后 W1 迟到 | 权威代际围栏 | applied, stale_rejected | 30 | 1 |
| 交接后 W2 尚未触碰 sink | 本地 TTL | applied, applied | 30 | 2 |
| 交接后 W2 尚未触碰 sink | 已见代际围栏 | applied, applied | 30 | 2 |
| 交接后 W2 尚未触碰 sink | 权威代际围栏 | stale_rejected, applied | 30 | 1 |
| W2 完成后同输入重放 | 本地 TTL | applied, already_applied | 30 | 1 |
| W2 完成后同输入重放 | 已见代际围栏 | applied, already_applied | 30 | 1 |
| W2 完成后同输入重放 | 权威代际围栏 | applied, already_applied | 30 | 1 |

第一类故障中, W2 已经先把 generation 2 送到 sink, 因而已见代际围栏和权威代际围栏都能拒绝迟到 generation 1. 本地 TTL 路径因为使用 W1 的旧 deadline 与偏慢逻辑时钟继续写入, 最终把 value 30 覆盖回 20.

强反例中, holder 已经切换到 W2, generation 已经推进到 2, 但 W2 尚未向 sink 发送第一条请求. 此时已见代际围栏的 `max_seen_generation` 仍不足以知道 generation 2 已经存在, 因而和本地 TTL 路径一样接受 W1 generation 1.

随后 W2 正常提交后, 三条路径最终都得到 value 30. 仅检查最终值会把本地 TTL 与已见代际围栏中的 1 次过期写入隐藏起来.

权威代际围栏在相同强反例中先拒绝 W1 generation 1, 再接受 W2 generation 2, 因而只有 1 次有效写入.

## 独立验证

独立 Python 验证器不调用生产提交函数, 只读取 TSV 中的 OWNER, HANDOFF, COMMIT 与 FINAL 事件.

验证器按事件顺序重建当前 generation, 将 `generation < current_generation` 且结果为 `applied` 的提交计为 stale accept, 并从 FINAL 事件核对最终 value 与总写入次数.

三次 Python 独立进程验证均通过. 在强反例中重新得到:

- 本地 TTL stale accept 为 1, 写入 2 次.
- 已见代际围栏 stale accept 为 1, 写入 2 次.
- 权威代际围栏 stale accept 为 0, 写入 1 次.
- 三条路径最终 value 都为 30.
- W2 完成后的同输入重放在三条路径中都没有新增第二次写入.

第二验证器使用 awk 独立解析同一 TSV, 不复用 Python 对象模型与解析器, 对强反例得到相同分类并通过.

本轮验证仍共享同一事件语义合同与生产夹具生成的轨迹, 因此不是完全独立的真实服务验证.

Python 独立进程验证三次的进程级墙钟耗时约为 0.52, 0.53 和 0.55 秒, 包含本轮沙箱 Python 启动开销. awk 验证三次均低于 `/usr/bin/time` 0.01 秒显示分辨率. 这些耗时只用于记录验证成本, 不比较真实服务性能.

## 强反例

强反例不是 W2 已经先写入 generation 2 后再观察 W1. 那种顺序会让 `max_seen_generation` 自然推进到 2, 使已见代际围栏看起来与权威围栏等价.

本轮故意把顺序改为 `权威交接到 W2/generation 2 -> W1/generation 1 迟到提交 -> W2 第一次提交`.

在这个窗口中, 已见代际围栏尚未观察到 generation 2, 所以它接受 generation 1. W2 随后写入 value 30 后最终状态仍然正确, 但总写入数为 2, 证明 stale side effect 已经发生.

因此 `最终值正确 + sink 当前最大已见 generation 为 2` 不能证明交接期间没有执行过旧所有者副作用.

这个反例不推翻 2026-07-27 的当前 holder/token 规则. 相反, 它说明把该规则优化成纯接收端 `max_seen_generation` 会丢失尚未观察到的新交接信息.

## 路径比较

| 路径 | 依赖状态 | 新 holder 未触碰 sink 时拒绝旧提交 | 强反例写入 | 最终质量 | 完成后重放写入 |
| --- | --- | --- | ---: | --- | ---: |
| 本地 TTL | 执行者缓存 deadline 与本地时钟 | 否 | 2 | 最终可被后续修正, 但发生旧副作用 | 0 |
| 已见代际围栏 | sink 已观察到的最大 generation | 否 | 2 | 最终正确, 但发生旧副作用 | 0 |
| 权威代际围栏 | 提交时当前 holder + generation | 是 | 1 | 当前所有者结果且无旧写入 | 0 |

本地 TTL 操作最少, 但在 W2 先提交场景中直接把当前值回滚为 20.

已见代际围栏在已经观察过 generation 2 后能够拒绝 generation 1, 但交接信息传播到 sink 之前存在安全盲区.

权威代际围栏每次提交多一次当前所有权检查, 在本轮强反例中避免 1 次过期副作用. 结果质量优先于减少这一次检查.

## 暂时结论

状态为观察.

本轮在 2026-07-27 当前 holder/token 结论上识别出一个实现边界: `sink 最大已见 generation` 不是 `当前权威 generation` 的等价替代.

如果新 holder 已经接管但尚未与 sink 通信, 纯接收端已见代际围栏仍可能接受旧 holder 的迟到提交. 后续新 holder 可以把最终值修正回来, 因而只看最终状态会漏掉已经发生的重复或过期副作用.

更稳妥的受控顺序是 `所有权交接推进单调 generation -> 副作用接受端在提交边界验证当前 holder/generation 或由交接原子推进其 fence -> 接受当前提交 -> 完成状态绑定当前 generation`.

本轮是一个新的故障位置和执行路径, 但仍是单日受控实验. 它用于复验既有发现的边界, 不单独形成新的候选或发现.

## 复验条件

使用真实多进程协调器和独立 sink, 让 holder 交接与第一条新 generation 请求之间存在真实网络延迟, 检查纯 `max_seen_generation` 是否出现同类盲区.

注入续约确认丢失和真实时钟漂移, 区分客户端认为 lease 仍有效与协调器已经完成接管的状态.

比较三种服务端实现: 每次提交查询当前权威 generation, 所有权交接时主动推进 sink fence, 以及使用单一原子事务同时比较 generation 和写副作用.

加入不可逆副作用, 验证最终状态后来恢复时是否仍能检测并计入已经发生的 stale action.

## 事实分层

### 已验证事实

- 正常基线中三条路径都能完成 W1 generation 1 的一次写入.
- W2 先提交 generation 2 后, 已见代际围栏和权威代际围栏都拒绝 W1 generation 1, 本地 TTL 路径接受并把最终值回滚为 20.
- W2 尚未触碰 sink 的强反例中, 已见代际围栏和本地 TTL 都接受 W1 generation 1, 权威代际围栏拒绝.
- 强反例随后由 W2 写入后, 三条路径最终值都为 30, 但前两条路径有 2 次写入, 权威路径只有 1 次.
- 三次完整生产轨迹摘要一致, Python 独立进程验证三次通过, awk 独立实现再次通过.
- W2 当前完成结果通过同一生产入口重放后, 三条路径新增写入均为 0.

### 基于证据的推断

- TTL 更适合作为存活与接管时机机制, 不能单独充当外部副作用的当前所有权证明.
- sink 只维护已观察到的最大 generation 时, 安全性依赖新 generation 已经传播到 sink, 这引入了交接传播窗口.
- 当前 holder/generation 需要在最终副作用接受边界可核验, 或通过等价原子机制把新的 fence 在交接时推进到接受端.
- 最终状态验证需要同时检查副作用计数或事件身份, 否则后续正确写入可能掩盖先前 stale action.

### 未验证事项

- 真实 Kubernetes Lease, etcd Lease/Txn 或 Chubby 类 sequencer 服务上的实际并发时序.
- 多进程网络延迟, 续约响应丢失与真实时钟漂移.
- sink fence 主动推进与业务写是否能在真实系统中共享原子边界.
- 不可逆外部副作用发生后无法靠后续正确值覆盖时的恢复策略.
- 当前 PR head 对应完整工作树上的 `ballast/tools/check.py` 执行结果.
