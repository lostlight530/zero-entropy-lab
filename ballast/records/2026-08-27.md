# Ballast 日记录 2026-08-27

类型: 每日专题
主题: 同名目标重建后的 current completion incarnation 绑定

## 研究问题

当 unknown outcome 恢复已经命中 historical effect evidence, 当前 completion contract 又要求目标资源仍是任务原本绑定的实体时, 如果同名资源被删除并重建且局部 revision 从相同初值重新开始, 仅核对 value 或 `value + revision` 是否会把新实体误认成旧任务的 current completion

本轮改变故障位置: 8 月 16 日攻击 historical effect receipt 的 target incarnation alias, 本轮攻击 current completion evidence 自身的 target incarnation alias

关键窗口为 `observe old incarnation -> delete and recreate same logical name -> new incarnation reuses visible value and local revision -> completion decision`

## 来源依据

查询日期为 2026-08-27

- [Kubernetes Object Names and IDs](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/) 说明同类资源名称在对象删除后可以再次使用, 而 UID 用于在整个集群中唯一标识对象, 因此同名新对象不是旧对象本身. 适用边界是 Kubernetes 对象身份, 不直接证明任意 Agent 状态源都具有 UID
- [Amazon S3 How S3 Versioning works](https://docs.aws.amazon.com/AmazonS3/latest/userguide/versioning-workflows.html) 说明同一个 object key 可以对应不同 version ID, version ID 用来区分同名对象的不同版本. 适用边界是启用 versioning 的 S3 对象, 不直接等价于 Kubernetes UID 或任意业务实体 incarnation

两个独立官方来源共同支持一个有限设计前提: 逻辑名称和值不足以唯一标识资源实例, 某些系统需要 UID、version ID 或等价不可混淆 identity 才能区分同名历史实体

把该前提用于 Ballast current completion evidence 属于本轮待证伪假设

## 可证伪假设

- H1: 当前同名目标的 value 满足任务后置条件时可以直接恢复 completion, 不需要区分实体 incarnation
- H2: 如果 current value 与局部 revision 都和旧观察一致, 就足以证明还是同一个 completion target
- H3: current completion evidence 同时绑定 target incarnation identity 与 incarnation 内 revision, 可以识别同名重建, 同时不因无关 metadata 变化过度失效
- H4: completed replay 不能替代 target replacement 窗口测试

H1 的反证条件是旧任务明确绑定 `uid-B1`, 当前同名 B 已变成 `uid-B2`, 即使 B2 的 value 也是 `marked`, 旧任务仍不应保存 completion

H2 的强反例让 B1 与 B2 都使用 local revision 1, 删除重建后仅看 revision 无法区分两个实体

H3 的反证条件是 target UID 已变化而 incarnation-bound 路径仍保存旧任务 completion, 或仅改变无关 metadata 时该路径错误停止

## 控制条件

- task identity、normalized action、ownership、valid_until、task status、credential capability 与 approval binding 固定有效
- completion contract 明确绑定目标 A=`uid-A1` 与 B=`uid-B1`, 两个目标值都要求 `marked`
- A 始终为 `uid-A1`, value=`marked`, local revision 1
- B 初始为 `uid-B1`, value=`marked`, local revision 1
- 同名重建把 B 替换为 `uid-B2`, value 仍为 `marked`, local revision 重新从 1 开始
- `value-only` 只读取 A/B 当前 value
- `value-revision` 读取 value 与 local revision, 完成前只复核 revision, 故意不绑定 UID
- `incarnation-bound` 同时读取 UID、value 与 local revision, 并检查 UID 是否仍是任务绑定的 target incarnation
- target incarnation 变化时强路径返回 safe stop / replan required, 不对新实体执行旧任务副作用
- unrelated metadata 场景只记录 note 变化, 不改变 UID、value 或 revision
- completed replay 重新进入同一 production entry 并直接经过 completed short circuit
- 夹具只使用 Python 标准库和系统 awk, 不访问真实 Kubernetes、S3 或外部 effect sink

## 实验设计

1. 三条路径执行 normal, 验证原 incarnation 不变时都能零新增 effect 恢复 completion
2. 三条路径执行 recreate-before-check, 在 production entry 检查前把 B 从 `uid-B1` 重建为同名 `uid-B2`, 检查只看 value 或 revision 是否错误完成
3. 三条路径执行 recreate-after-value-read, 先读取旧 B1 再重建成 B2, 且 B2 复用 local revision 1, 检查 revision-only 是否能够识别 incarnation change
4. 三条路径执行 unrelated-metadata, 检查 incarnation-bound 是否只绑定真实 completion dependency 而不因无关变化过度停止
5. 三条路径执行 completed-replay, 让已完成任务重新进入 production entry, 检查是否新增副作用
6. producer 输出 scenario、path、completed、A/B UID、value、revision、effect_count、ops 与 event order, 完整运行三次并比较 TSV SHA-256
7. 独立 Python verifier 不导入 producer, 从最终权威 UID 与 event order 重建预期, 检查同名重建后弱路径假完成与强路径 safe stop
8. awk 第二验证独立复核 recreate-after-value-read 中 incarnation-bound 必须 completed=0 且 event order 含 `SAFE_STOP`
9. producer 与 verifier 执行 `py_compile`

## 原始观测

三次 producer 轨迹各包含 15 个 scenario/path 数据行

三次 SHA-256 均为 `458f3df2f6afb2933417efcc687b160c35a34a4cbee08fc7200865db4f8b9050`

| 场景 | 路径 | completed | 当前 B UID | 新增 effect | 操作数 |
| --- | --- | ---: | --- | ---: | ---: |
| normal | value-only | 1 | uid-B1 | 0 | 2 |
| normal | value-revision | 1 | uid-B1 | 0 | 3 |
| normal | incarnation-bound | 1 | uid-B1 | 0 | 3 |
| recreate-before-check | value-only | 1 | uid-B2 | 0 | 3 |
| recreate-before-check | value-revision | 1 | uid-B2 | 0 | 4 |
| recreate-before-check | incarnation-bound | 0 | uid-B2 | 0 | 4 |
| recreate-after-value-read | value-only | 1 | uid-B2 | 0 | 3 |
| recreate-after-value-read | value-revision | 1 | uid-B2 | 0 | 4 |
| recreate-after-value-read | incarnation-bound | 0 | uid-B2 | 0 | 4 |
| unrelated-metadata | value-only | 1 | uid-B1 | 0 | 3 |
| unrelated-metadata | value-revision | 1 | uid-B1 | 0 | 4 |
| unrelated-metadata | incarnation-bound | 1 | uid-B1 | 0 | 4 |
| completed-replay | value-only | 1 | uid-B1 | 0 | 1 |
| completed-replay | value-revision | 1 | uid-B1 | 0 | 1 |
| completed-replay | incarnation-bound | 1 | uid-B1 | 0 | 1 |

`recreate-before-check` 中 value-only 与 value-revision 都在当前目标已经是 B2 时保存 completion

这不是因为读取 stale, 两条弱路径读到的都是当前 B2, 问题是它们没有证明 B2 就是旧任务绑定的 B1

`recreate-after-value-read` 更强: value-revision 先观察旧 B1 的 local revision 1, 随后同名重建得到 B2 的 local revision 1, 最终 revision check 仍返回 fresh 并错误 completion

因此单纯 local revision equality 不能跨 incarnation 使用

incarnation-bound 在两种重建场景都观察到 UID 与任务 target identity 不一致, 返回 `SAFE_STOP|replan_required`, completed 保持 0, 没有对 B2 执行旧任务副作用

unrelated-metadata 中 incarnation-bound 正常 completed=1, 说明本轮强路径没有把无关 note 变化扩张成 target identity 变化

三次 producer 加独立 Python verifier 的进程级耗时分别约为 1719.570、1495.340 与 1491.453 毫秒, 只记录本轮环境开销, 不用于推断真实远端系统性能

## 独立验证

Python verifier 与 producer 为两个独立文件

verifier 不导入 producer, 不读取 producer 内部 success boolean 或保存的 expected result 作为真值

Python verifier 独立检查

- 15 个 scenario/path 组合完整且唯一
- normal 三条路径均 completed=1 且新增 effect=0
- completed-replay 三条路径重新进入 production entry 后新增 effect=0
- 两个重建场景中 value-only 与 value-revision 都在权威 B UID 已经是 `uid-B2` 时 completed=1, 因而形成 target identity 假完成
- incarnation-bound 在两个重建场景都 completed=0 并记录 `SAFE_STOP`
- unrelated-metadata 中 incarnation-bound completed=1 且没有 safe stop
- recreate-after-value-read 的 event order 明确是读取旧 target evidence 后发生 `RECREATE`, verifier 因而不把最终 UID 单点状态替代为事件顺序证据

三次 Python verifier 均返回 `PASS 15`

awk 第二验证返回 `AWK_PASS`

producer 与 verifier 均通过 `py_compile`

两个 verifier 仍共享 TSV 字段语义、event label 约定和同一运行环境

因此本轮不是对 Kubernetes UID、S3 version ID 或真实资源控制面的端到端验证

## 强反例

最强反例是 revision reuse

旧 B1 与新 B2 的逻辑名称、value 和 local revision 都完全相同, 只有不可混淆 incarnation identity 不同

value-revision 因而能够通过所有自己掌握的检查并错误保存 completion

这推翻了“只要 revision 一致就足以证明 current target 没变”的解释

反方向强反例是 unrelated-metadata

只有 note 改变时 incarnation-bound 不停止, 说明把 target UID 纳入 completion evidence 不要求使用 whole-object global revision 过度围栏

completed replay 三条路径全部表现安全, 再次说明已经持久化的 completion 不能替代真实 target replacement 窗口

## 路径比较

| 路径 | 正常 completion | 同名重建识别 | revision reuse 防护 | 无关 metadata 不过度围栏 | completed replay |
| --- | --- | --- | --- | --- | --- |
| value-only | 是 | 否 | 否 | 是 | 零新增 effect |
| value-revision | 是 | 否 | 否 | 是 | 零新增 effect |
| incarnation-bound | 是 | 是 | 是 | 是 | 零新增 effect |

value-only 操作最少, 但零写入并不代表结果正确, 它可以在目标实体已经变化后错误跳过必要的重新规划

value-revision 增加 revision 检查, 但 revision 只在 incarnation 内有意义时不能跨实体解释

incarnation-bound 操作数与 value-revision 相同或等价, 改进来自证据 identity 质量而不是更多操作

## 暂时结论

本轮支持 H3, 推翻 H1 与 H2

对绑定具体资源实体的 persistent-state completion contract, current completion evidence 不能只绑定逻辑名称、value 或可能跨 incarnation 重用的 local revision

至少需要把不可混淆 target incarnation identity 与 incarnation 内 freshness evidence 一起解释

当 target incarnation 已变化时, 旧任务应重新规划、重新授权或安全停止, 不能仅因为同名新实体当前值满足就继承旧 completion

该结论只适用于任务语义确实绑定具体 incarnation 的场景

如果任务合同本来就是“任何当前同名实体只要满足 value 即可”, 那么 UID 变化不一定构成错误, 必须由任务语义先定义 identity boundary

## 事实分层

### 已验证事实

- 受控模型中 B1 与 B2 可以具有相同逻辑名称、相同 `marked` value 和相同 local revision 1
- value-only 与 value-revision 在两个重建场景都 completed=1, 当前权威 B UID 为 `uid-B2`
- incarnation-bound 在两个重建场景都 completed=0 并安全停止, 没有对新实体执行旧任务副作用
- unrelated-metadata 不会使 incarnation-bound 失效
- completed replay 三条路径新增 effect 均为 0
- 三次 producer 轨迹 SHA-256 完全一致, Python verifier 3 次通过, awk 第二验证通过

### 基于证据的推断

- local revision equality 只有在 incarnation identity 已确定相同的前提下才能作为 freshness evidence
- current completion evidence 的 identity boundary 必须来自任务语义, 不能默认把逻辑名称等同于实体实例
- 对具体 incarnation 绑定任务, `target incarnation + revision` 比 `logical name + revision` 更能抵抗 delete/recreate alias

### 未验证事项

- 尚未验证真实 Kubernetes delete/recreate、S3 versioning 或其他控制面中的端到端恢复行为
- 尚未验证跨服务 target identity、UID 查询 freshness 或 identity store 自身发生 stale read 的组合故障
- 尚未证明所有 persistent-state task 都应绑定 immutable instance identity
- 尚未验证 target reincarnation 与 multi-resource fractured view、completion commit TOCTOU 的组合窗口
