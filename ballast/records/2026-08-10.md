# Ballast 日记录 2026-08-10

类型: 每日专题
主题: 后置条件读取竞态与验证代际绑定

## 研究问题

迟到任务因基准变化进入后置条件检查后, 如果目标在读取与完成判定之间再次变化, 单次目标读取、严格冲突停止和目标读取加代际复核三条路径中, 哪一种能避免把已失效观察误报为 `already_satisfied`

## 来源依据

查询日期为 2026-08-10

- [RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html) 发布于 2022-06, Section 13 要求状态变更前在接近实际执行动作的位置评估条件请求, `If-Match` 失败时不得执行原方法, 同时允许服务器在能够确认原变更已经实现时返回成功, 说明版本前置条件与目标已完成判断是两个不同问题
- [etcd API](https://etcd.io/docs/v3.6/learning/api/) 访问于 2026-08-10, etcd 为键和值附带 revision, 默认 Range 读取为线性一致, Transaction 将 compare 与 then or else 请求放在同一原子事务中, 可用 revision 或 value 比较保护并发更新
- [Kubernetes API Concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) 访问于 2026-08-10, 客户端使用过期 `resourceVersion` 更新时服务端返回 `409 Conflict`, 需要 lost update 检测的客户端应让更新依赖当前 `resourceVersion` 并在冲突后处理重试

RFC Editor, etcd 与 Kubernetes 来自不同标准或实现体系, 共同支持把状态判断绑定到当前版本或 revision, 但这些来源不证明一次正确读取可以保证状态在返回完成之后永远不再变化

## 可证伪假设

- H1: 基准变化后只读取一次当前目标, 只要读取值满足目标就可以直接返回 `already_satisfied`
- H2: 基准变化后统一返回 `generation_conflict` 最安全, 因为任何额外目标判断都可能引入竞态
- H3: 后置条件读取必须携带验证代际, 并在完成判定前确认权威 revision 未变化, 如果变化则返回 `verification_stale`, 只有同一代际上的目标满足才可返回 `already_satisfied`

如果单次目标读取在注入并发变化后仍能保证最终权威状态满足目标, H1 的风险解释被削弱

如果严格冲突停止能够识别没有竞态且目标已经由其他操作完成的基线, H2 的信息损失解释被削弱

如果代际复核在读取后状态变化时仍返回 `already_satisfied`, H3 被推翻

## 控制条件

- 当前权威状态初始为 revision 2, value 20, 代表较新操作已经满足旧任务目标
- 旧任务目标固定为 value 20
- 严格路径不读取后置条件, 直接返回 `generation_conflict`
- 松散路径读取一次 value 与 revision, 随后直接按读取结果分类
- 代际绑定路径先读取 value 与 revision, 再在分类前重新读取权威 revision, revision 不一致时返回 `verification_stale`
- 故障注入发生在第一次读取之后和完成分类之前, 把 value 从 20 改为 30 并推进 revision
- 强反例发生在代际绑定路径已经完成验证并返回之后, 再由独立操作把 value 改为 30, 用来检验本轮证据是否只能证明某个验证时点而不能证明未来不变
- 实验仅使用 Python 标准库和本轮运行时内存夹具, 没有使用外部依赖, 数据库, 缓存目录或持久实验脚本

## 实验设计

1. 对三条路径建立无竞态基线, 当前状态为 revision 2, value 20
2. 记录各路径的读取操作数量, 返回状态, 最终 revision, 最终 value 和写入计数
3. 对松散路径和代际绑定路径在第一次读取后注入并发写入 value 30, revision 推进到 3
4. 比较松散路径是否仍按旧观察返回 `already_satisfied`, 以及代际绑定路径是否识别观察已过时
5. 对三条验证路径使用同一输入连续重放两次, 检查验证路径自身是否产生新写入或改变权威状态
6. 构造强反例, 让代际绑定路径先在 revision 2, value 20 上成功返回, 再在返回后推进到 value 30
7. 独立验证不读取路径内部成功布尔值, 而是直接依据最终 value, revision 和写入计数检查路径声明是否与权威状态一致
8. 同一控制条件完整运行三次并比较观测摘要与验证后有效耗时

## 原始观测

三次完整运行得到一致观测摘要 `370849272fa34767eb08f78daf7cf76b63cfc9a365d07d50176c109db80230ec`

| 场景 | 路径 | 返回状态 | 读取操作 | 最终 revision | 最终 value |
| --- | --- | --- | ---: | ---: | ---: |
| 无竞态基线 | 严格冲突停止 | generation_conflict | 0 | 2 | 20 |
| 无竞态基线 | 单次目标读取 | already_satisfied | 1 | 2 | 20 |
| 无竞态基线 | 目标读取加代际复核 | already_satisfied | 2 | 2 | 20 |
| 读取后并发变化 | 严格冲突停止 | generation_conflict | 0 | 3 | 30 |
| 读取后并发变化 | 单次目标读取 | already_satisfied | 1 | 3 | 30 |
| 读取后并发变化 | 目标读取加代际复核 | verification_stale | 2 | 3 | 30 |

松散路径在 revision 2 读取到 value 20 后遭遇并发写入, 最终权威状态已经是 revision 3, value 30, 但仍返回 `already_satisfied`, 构成验证路径假成功

代际绑定路径在相同故障注入下检测到 revision 已变化并返回 `verification_stale`, 没有把旧观察当成当前完成证据

同输入连续重放两次时, 三条验证路径自身新增写入均为 0, 松散路径和代际绑定路径在无竞态条件下返回结果稳定

三次完整运行的验证后有效耗时分别为 0.028 毫秒, 0.016 毫秒和 0.014 毫秒, 仅用于记录本轮内存夹具成本, 不用于推断真实服务性能

## 独立验证

验证器直接从最终状态检查声明

- `already_satisfied` 若被解释为当前状态已满足, 则完成判定时对应的权威 value 必须仍为 20
- 故障注入后松散路径最终 value 为 30, 因此其 `already_satisfied` 与最终权威状态冲突
- 代际绑定路径看到 revision 从 2 变为 3 后返回 `verification_stale`, 与最终状态发生变化的事实一致
- 无竞态基线中, 代际绑定路径两次读取都对应 revision 2, value 20, 因而可以把完成证据明确限定为 revision 2
- 所有验证路径重放均没有增加写入计数

本轮独立验证与生产夹具共享同一 Python 运行时和对象模型, 但期望条件由最终权威状态直接推导, 没有复用各路径内部的成功判断

因此本轮验证在判断逻辑上独立, 但不是进程级或实现级独立

## 强反例

代际绑定仍不能证明目标在验证返回之后永远保持成立

强反例中, 代际绑定路径在 revision 2, value 20 上正确返回 `already_satisfied`, 随后独立操作把权威状态推进到 revision 3, value 30

这没有推翻代际绑定对读取窗口竞态的防护, 但限制了结论范围

`already_satisfied` 只能表示目标在被验证的 revision 上成立, 不能被扩展解释为未来状态永久成立

如果调用方需要更强语义, 必须让后续动作继续携带该 revision 或在同一原子事务中完成验证与受保护动作, 而不是丢弃验证代际后继续执行

## 路径比较

| 路径 | 无竞态目标识别 | 读取窗口竞态检测 | 新增写入 | 证据边界 |
| --- | --- | --- | ---: | --- |
| 严格冲突停止 | 否 | 通过停止规避 | 0 | 不判断目标是否已完成 |
| 单次目标读取 | 是 | 否 | 0 | 可能使用过时观察误报完成 |
| 目标读取加代际复核 | 是 | 是 | 0 | 完成只绑定到已验证 revision |

严格冲突停止操作最少且不会误写, 但在无竞态基线中丢失目标已经完成的信息

单次目标读取只增加一次读取, 但故障注入证明它可能在最终状态已经不满足时报告完成

代际绑定增加第二次权威读取, 操作数更多, 但把结果质量优先于少一次读取, 并把完成声明限制到可核验 revision

## 暂时结论

状态为观察

昨日的目标感知恢复仍需要增加一个边界条件: 后置条件本身必须与权威 revision 绑定, 否则读取目标与返回完成之间的状态变化可以制造 `already_satisfied` 假成功

严格冲突停止可以避免错误完成声明, 但它无法识别无竞态情况下已经由其他路径实现的目标

本轮更合适的暂时顺序是 `关闭旧写权限 -> 读取当前目标与 revision -> 在完成判定前复核 revision -> 返回绑定 revision 的完成或重新同步`

强反例说明即使该顺序通过, 完成证据也只是点时证据, 后续依赖动作如果需要同一事实仍应继续携带 revision 或放入原子边界

今天仍是单个受控研究单元, 三次同条件重复不计为三个独立实验, 不提升为候选或发现

## 事实分层

### 已验证事实

- 无竞态基线中, 单次目标读取和代际绑定路径都在 revision 2, value 20 上返回 `already_satisfied`
- 读取后注入并发变化时, 松散路径最终处于 revision 3, value 30 但仍返回 `already_satisfied`
- 同一故障注入下, 代际绑定路径返回 `verification_stale`, 没有报告完成
- 三条验证路径同输入连续重放两次时自身新增写入均为 0
- 强反例中, 代际绑定路径成功返回后仍可被后续独立写入推进到 revision 3, value 30
- 三次完整运行观测摘要一致

### 基于证据的推断

- 后置条件需要绑定版本身份, 单独验证业务值而不保留 revision 会把读取窗口中的状态漂移隐藏起来
- 完成证据应表达为某个权威 revision 上目标成立, 而不是无时间边界的永久完成
- 当下一步动作依赖该完成事实时, revision 应继续进入下一步前置条件或与动作合并进原子 compare and act 边界

### 未验证事项

- 真实 etcd Transaction, HTTP ETag 服务或 Kubernetes API 上的并发时序与返回语义
- 不同进程, 不同实现验证器和真实网络延迟下的独立性
- 多对象, 多字段与不可逆副作用下 revision 绑定是否足够
- 当前 PR head 对应完整工作树上的 `ballast/tools/check.py` 执行结果
