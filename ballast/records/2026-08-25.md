# Ballast 日记录 2026-08-25

类型: 每日专题
主题: 后置条件读取与 completion 提交之间的原子性窗口

## 研究问题

当 unknown outcome 恢复已经命中 exact historical receipt, current postcondition 也在最后一次读取时真实满足时, 如果 authoritative state 在该读取之后、completion commit 之前再次变化, 单次读取、完成前重读、global compare-and-complete 与 target compare-and-complete 四条路径能否区分有效完成与读取后失效

本轮改变故障位置: 不攻击 receipt identity、receipt freshness 或 postcondition read freshness, 而攻击 `fresh postcondition read -> completion commit` 之间的新 TOCTOU 窗口

关键窗口为 `historical effect + receipt -> completion missing -> fresh satisfied read -> authoritative reversal -> completion commit`

## 来源依据

查询日期为 2026-08-25

- [etcd API](https://etcd.io/docs/v3.6/learning/api/) 将 transaction 定义为原子的 If/Then/Else, compare 可以检查 key 的 value、version 或 modification revision, compare 与 success 或 failure 请求在一个原子块中执行. 适用边界是 etcd key-value transaction, 不直接证明任意远端 completion store 都能提供相同原子边界
- [PostgreSQL Transaction Isolation](https://www.postgresql.org/docs/17/transaction-iso.html) 说明 Serializable 并发成功提交的效果必须等价于某个串行执行顺序, 无法维持该性质时事务会以 serialization failure 中止并要求整个事务重试. 适用边界是 PostgreSQL transaction isolation, 不直接等价于跨服务 effect 与 completion 的原子提交

两个独立官方来源共同支持一个设计前提: 如果完成声明依赖某个状态读, 需要把状态条件与受保护提交绑定到同一可核验并发边界, 或在冲突时拒绝当前提交并重新判断

把这个边界用于 Ballast 的 current postcondition 与 completion commit 属于本轮待证伪假设

## 可证伪假设

- H1: 只要 current postcondition read 足够新鲜, 读取成功后就可以直接保存 completion
- H2: completion 前再重读一次 current postcondition 足以关闭读取到提交之间的竞态
- H3: 把 target-state revision compare 与 completion commit 放入同一原子边界, 可以拒绝最后一次读取后发生的 target reversal
- H4: whole-store global revision compare 也能阻止本轮 reversal, 但无关状态变化会产生额外冲突与恢复工作
- H5: completed replay 不能替代 `final read -> state change -> completion commit` 窗口测试

H1 的反证条件是最后一次读取真实返回 `marked`, 随后 target 被反转为 `clean`, 路径仍直接保存 completion

H2 的强反例是把 reversal 放到第二次读取之后, 如果 reread 路径仍完成则证明重读只是缩短窗口而不是关闭窗口

H3 的反证条件是 target revision 已改变而原子 compare 仍允许旧完成声明提交, 或冲突后恢复没有重新确认 current permission

H4 的限制反例是只改变无关 global state, target value 与 target revision 均不变, global compare 仍发生冲突而 target compare 不冲突

H5 的反证条件是 completed replay 能暴露上述 final-read-to-commit 竞态

## 控制条件

- task、normalized action、target incarnation 与 exact historical receipt identity 固定
- 历史 forward effect 已真实提交一次并写入 receipt, completion 初始缺失
- replay 时 task status、intent、ownership、valid_until、credential 与 approval binding 保持有效
- completion contract 固定要求 authoritative target value 当前为 `marked`
- target state 初始为 value `marked`, target revision 2, global revision 10
- target reversal 把 value 改为 `clean`, 同时推进 target revision 与 global revision
- unrelated change 只推进 global revision, 不改变 target value 或 target revision
- `single-read` 只读取一次 postcondition 后保存 completion
- `reread-before-complete` 在 completion 前执行第二次读取, 但读取和 completion commit 仍是两个分离步骤
- `global-compare-complete` 在最终读取后以 global revision compare 保护 completion commit
- `target-compare-complete` 在最终读取后以 target revision compare 保护 completion commit
- compare 失败后重新读取 current target, 如果仍不满足 completion contract, 每次真实 forward effect 前记录 `B:permission_valid`
- completed replay 必须重新进入同一 production entry 并通过 completion short circuit 返回
- 夹具只使用 Python 标准库和系统 awk, 不访问真实 etcd、PostgreSQL 或外部 effect sink

## 实验设计

1. 四条路径执行 normal-no-race, 验证没有状态变化时都从真实 receipt 与 satisfied postcondition 恢复 completion, 不增加 forward effect
2. 四条路径执行 reversal-before-final-check, 在第一次读取后推进 target state, 检查 reread 与 compare 路径能否发现变化
3. 四条路径执行 reversal-after-final-check, 把 target reversal 放在各路径最后一次普通读取之后、completion commit 或 atomic compare 之前, 直接攻击 H1 与 H2
4. 四条路径执行 unrelated-global-after-final-check, 只推进无关 global revision, 检查 whole-store compare 是否 over-fence
5. 四条路径执行 completed-replay, completion 已保存后重新进入 production entry
6. producer 输出 scenario、path、effect_count、completed、authoritative value、target revision、global revision、result、ops 与 event_order, 完整运行三次并比较 stdout TSV SHA-256
7. 独立 Python verifier 不导入 producer, 从 event_order 重建真实 forward effect 次数, 检查每个 B 侧 effect 前是否存在 current permission evidence, 并区分 reversal-before-completion 与 completed replay
8. awk 第二验证实现独立复核 reversal-after-final-check 与 unrelated global change 的决定性结果
9. producer 与 verifier 执行 `py_compile`

## 独立验证

Python verifier 与 producer 为两个独立文件

verifier 不导入 producer, 不读取 producer 内部成功布尔值或保存的期望对象

Python verifier 独立检查

- 20 个 scenario/path 组合完整且唯一
- event_order 中真实 forward effect commit 数与 effect_count 一致
- 每个 B 侧 effect commit 前都存在 `B:permission_valid`
- normal-no-race 四条路径均为 effect 1、completed 1、authoritative value `marked`
- completed-replay 四条路径均重新进入 production entry, 经过 `B:completed_short_circuit`, effect 总数保持 1
- reversal-after-final-check 的 single-read 与 reread-before-complete 均为 effect 1、completed 1、authoritative value `clean`
- reversal-after-final-check 的两条 compare-and-complete 路径均记录 compare conflict, 再恢复为 effect 2、completed 1、authoritative value `marked`
- reversal-before-final-check 的 reread-before-complete 能识别已经发生的 reversal 并恢复 `marked`, 说明第二次读取确实缩小部分竞态窗口
- unrelated-global-after-final-check 中 global compare 出现 compare conflict, target compare 不冲突, 两条路径都不增加 forward effect
- false-completion trace 中 reversal event 确实位于 completion commit 之前, verifier 因而能区分最终 completed 相同但历史不同的两条路径

三次 Python verifier 均返回 `PY_VERIFIER_PASS`

awk 第二验证实现返回 `AWK_PASS`

producer 与 verifier 均通过 `py_compile`

两个 verifier 仍共享 TSV 字段语义、event label 约定和同一系统运行环境

因此本轮不是对真实数据库 transaction、分布式 compare-and-swap 或跨服务 completion commit 的端到端验证

## 强反例

`reversal-before-final-check` 显示 reread-before-complete 有真实价值: 如果 state change 发生在第二次读取之前, 它能看到 `clean` 并触发必要恢复

但 `reversal-after-final-check` 把同一 reversal 移到第二次读取之后, reread 路径立即重新暴露假完成

因此 H2 被直接推翻: 增加第二次普通读取只能缩短 TOCTOU 窗口, 不能关闭最后一次读取到 completion commit 之间的竞态

`unrelated-global-after-final-check` 同时限制了 whole-store compare 的解释: global compare 可以安全拒绝本轮 target reversal, 但只发生无关 global change 时也会冲突, 比 target revision compare 多一次恢复读取

这不证明 target projection 在所有真实任务中都完整, 只证明本轮明确依赖字段只有 target value 与 target revision 时, global revision 的围栏范围更宽

completed replay 四条路径全部安全, 因为 completion 已存在时直接 short circuit, 因而再次不能替代 final-read-to-completion crash-window

## 路径比较

| 路径 | final read 后 target reversal | 无关 global change | completed replay | 主要边界 |
| --- | --- | --- | --- | --- |
| single-read | effect 1, clean 假完成 | 正常完成 | effect 1 | 读取与完成提交完全分离 |
| reread-before-complete | effect 1, clean 假完成 | 正常完成 | effect 1 | 缩短窗口但仍存在最后一次读取后的 TOCTOU |
| global-compare-complete | effect 2, marked | 多一次 compare conflict 与 recovery read | effect 1 | 安全但 whole-store revision 可能 over-fence |
| target-compare-complete | effect 2, marked | 无 compare conflict | effect 1 | 依赖 target revision 完整覆盖 completion semantics |

正常基线中 single-read 操作数最少, 但这一优势来自省略并发保护

target compare 与 global compare 正常基线操作数相同, unrelated global change 下 target compare 少一次恢复读取

本轮没有测量真实事务延迟、锁竞争、serialization retry 成本或跨服务协调开销, 因而不依据夹具操作数推断真实基础设施性能优劣

## 暂时结论

状态保持观察

本轮支持把 current completion evidence 的时间边界再收紧一步: `fresh read` 只证明读取线性化点上的事实, 如果 completion commit 仍依赖该事实, 普通 reread 不能关闭读取后的新 TOCTOU 窗口

在本轮受控模型中, 把 relevant target revision compare 与 completion commit 放进同一个原子 compare-and-act 边界可以拒绝 final read 后的 target reversal, 冲突后恢复器重新读取 current state 并在真实 effect 前重新确认 current permission

whole-store global compare 也能保证本轮正确性, 但无关 global change 会产生额外冲突, 因而相关状态围栏仍需要在完整性与精确性之间保守取舍

本轮没有改变现行 METHOD, 因为 `Current completion evidence 有效性` 已经明确要求 postcondition read 后仍依赖该事实时携带 revision 或把 compare 与受保护提交放入同一原子边界

## 事实分层

### 已验证事实

- reread-before-complete 在 reversal-before-final-check 中能发现变化并恢复 `marked`
- 相同路径在 reversal-after-final-check 中仍得到 effect 1、completed 1、authoritative value `clean`
- global-compare-complete 与 target-compare-complete 在 final read 后 target revision 变化时均拒绝旧 completion 提交并恢复 `marked`
- unrelated global change 中 global compare 发生额外冲突, target compare 不冲突
- completed replay 四条路径均 effect 1, 不能暴露本轮 TOCTOU
- 三次 producer 输出 SHA-256 完全一致, Python verifier 三次通过, awk 第二实现通过, producer 与 verifier 均通过语法编译

### 基于证据的推断

- current completion evidence 需要把被验证状态与 completion commit 绑定到可核验并发边界, 不应把最后一次普通读取当成永久事实
- reread 可以降低旧观察窗口, 但只要读取和受保护提交仍分离, 就仍存在新的判定后竞态
- relevant target revision compare 在依赖集合完整时可以减少 whole-store compare 的无关冲突

### 未验证事项

- 尚未验证真实 etcd 或 PostgreSQL 的端到端行为
- 尚未验证 target 与 completion 分属不同服务时的原子性方案
- 尚未验证多资源 postcondition、跨区域复制、真实 serialization failure、锁竞争与网络分区
- 尚未证明 target revision 在复杂任务中完整覆盖全部 completion semantics
