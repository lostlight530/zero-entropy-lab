# Ballast 日记录 2026-08-04

类型: 每日专题
主题: 批量部分成功中的逐项完成验证

## 研究问题

批量请求返回整体成功且结果条目数与输入相同时, 传输级验证能否证明每个意图已经生效, 整批重试与逐项对账恢复在重复副作用和最终质量上有何差异.

## 来源依据

查询日期为 2026-08-04.

- [Amazon SQS SendMessageBatch](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_SendMessageBatch.html) 当前 API 参考明确说明批量请求可以同时包含成功与失败动作, 即使 HTTP 状态为 200 也应检查批量错误, 响应把 Successful 与 Failed 分开报告.
- [Microsoft Graph JSON batching](https://learn.microsoft.com/en-us/graph/json-batching) 当前官方文档说明批量响应通常为 200 或 4xx, 批量响应头中的 200 不表示内部各请求成功, 每个响应使用自己的状态码.
- [Amazon SQS batch actions](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-batch-api-actions.html) 当前开发者指南把批量动作描述为把多个消息操作组合为一个调用, 支持降低连接与请求开销, 但没有把组合调用等同于单项事务.

AWS 与 Microsoft 文档来自独立产品体系, 共同支持把批量传输状态与单项执行状态分离. 它们不证明不同服务具有相同的重试、顺序、去重或事务语义.

## 可证伪假设

- H1: 批量 HTTP 状态为 200 且返回结果条目数等于输入条目数时, 可以把整个任务记为完成, 失败后整批重试即可恢复.
- H2: 整体状态和条目数量不能证明逐项完成. 恢复器需要关联每个唯一意图、单项结果与权威副作用, 只重试已确认失败或未生效的项目, 最终验证每个意图恰好出现一次且内容匹配.

如果传输级路径能拒绝部分成功, 整批重试不会重复 A 与 C, 或逐项恢复不能补齐 B 并保持完成后重放零副作用, H2 被推翻.

## 控制条件

- 输入清单固定为 A alpha、B bravo、C charlie, 标识在任务内唯一.
- 受控批量服务每次调用都返回 HTTP 200 并逐项报告结果.
- 首次调用固定让 A 与 C 成功并写入权威副作用日志, B 返回失败且不写入.
- 服务不提供隐式去重, 用于暴露整批重试的重复副作用.
- 独立验证器从输入清单与权威日志重新计算身份、数量和 SHA-256 内容摘要, 不读取生产器断言.
- 正式实验仅使用 Python 标准库与系统临时目录.

## 实验设计

1. 执行一次含 A、B、C 的批量调用, 注入 B 单项失败.
2. 使用只检查任务标识、HTTP 200 与结果条目数量的传输验证器判断首次响应.
3. 使用完整验证器回读输入清单、逐项状态和权威副作用日志.
4. 在独立服务状态中重放整个批次, 检查 A 与 C 是否产生重复写入.
5. 在另一独立服务状态中只重试失败项 B, 合并逐项结果并验证权威日志.
6. 对已经完整验证的状态重放同一任务, 先判断完成再决定是否调用服务.
7. 从最终状态重新执行完整验证并检查临时目录清理.

故障注入是首次批量调用中的 B 单项失败, 恢复点位于收到包含部分成功的整体 200 响应之后.

## 原始观测

| 路径 | 调用数 | 权威日志 | 验证结果 | 重复写入 |
| --- | ---: | --- | --- | ---: |
| 首次部分成功加传输验证 | 1 | A、C | 通过 | 0 |
| 首次部分成功加完整验证 | 1 | A、C | 拒绝 B 缺失与失败 | 0 |
| 整批重试 | 2 | A、C、A、B、C | 拒绝重复副作用 | 2 |
| 逐项对账后只重试 B | 2 | A、C、B | 通过 | 0 |
| 完成后同输入重放 | 0 个新增调用 | A、C、B | 通过 | 0 |

首次响应为 HTTP 200, 逐项结果数为 3, 与输入数相同. 传输验证退出 0, 完整验证退出 1, 原因为 missing_ids:B 与 failed_outcomes:B.

整批重试后完整验证退出 1, A 与 C 各出现两次. 逐项路径只重试 B, 完整验证退出 0. 四项机制断言全部为真, 独立验证进程 5 个, 正式实验验证后有效耗时 542.961 毫秒, 临时清理通过.

正式实验前的两次预运行因临时目录写权限失败而停止, 没有进入机制观测或结论计数.

## 独立验证

独立 Python 进程分别读取 UTF-8 输入清单与观测文件.

传输模式只检查任务标识、HTTP 状态和结果数量, 用于构造可通过的弱路径. 完整模式从输入载荷重新计算 SHA-256 摘要, 检查唯一身份、缺失身份、意外身份、内容、逐项状态和权威副作用计数.

验证器不导入批量服务实现, 不读取生产器的 effective_completion 或断言. 它仍与生产器共享 JSON 字段合同、Python 运行时和同一文件系统, 因而不是完全独立服务.

## 强反例

首次批量调用返回 HTTP 200, 结果数组包含 A、B、C 三个条目, 条目数与输入完全相同. 传输验证因此退出 0, 但 B 的单项状态为失败且权威日志只有 A、C.

结果条目存在只能证明服务报告了该意图, 不能证明对应副作用已完成. 整批重试也不能自动修复这一判断, 因为它补齐 B 的同时把已经生效的 A 与 C 各执行了一次.

## 路径比较

| 路径 | 识别单项失败 | 避免重复副作用 | 有效完成 | 结果质量 |
| --- | --- | --- | --- | --- |
| 只看整体状态与数量 | 否 | 不适用 | 否 | 假成功且缺少 B |
| 整批重试后完整验证 | 是 | 否 | 否 | B 补齐但 A、C 重复 |
| 逐项结果对账与选择性重试 | 是 | 是 | 是 | 每个意图恰好一次 |
| 完成后先验证再重放 | 是 | 是 | 是 | 零新增调用与写入 |

逐项路径与整批路径的服务调用数都为 2, 改进来自重试范围与最终验证, 不是减少调用数. 单机耗时不用于推断真实批量 API 性能.

## 暂时结论

状态为观察.

在本次受控实验中, 批量传输成功与结果条目齐全不能替代逐项完成证明. 恢复器先把每个结果关联到稳定意图和权威副作用, 再只重试失败或未生效项目, 能避免整批重试复制已经成功的副作用.

本次为 NOTES.md 的两个既有发现增加批量部分成功证据, 但逐项对账机制本身只出现一次, 不升级为新的候选或发现.

## 复验条件

在真实支持批量写入的 API 中注入限流、权限失败、响应丢失和乱序返回, 比较服务端去重、客户端逐项账本与整批重试.

改变失败项位置、同一标识不同载荷和权威副作用查询延迟, 检查逐项结果是否可能过期或与实际副作用分离. 对不可查询副作用验证安全停止边界.

## 事实分层

### 已验证事实

- HTTP 200 且结果数为 3 的弱路径通过, 完整验证发现 B 失败且权威日志缺少 B.
- 整批重试产生 A、C 两次重复写入, 完整验证拒绝.
- 逐项路径只重试 B 后日志包含 A、C、B 各一次, 内容摘要与输入清单匹配.
- 完成后同输入重放新增调用与写入均为 0.
- 四项机制断言为真, 五个独立验证进程完成, 正式实验临时清理通过.

### 基于证据的推断

- 批量任务的完成状态应按稳定单项意图聚合, 而不是按传输请求聚合.
- 批量优化减少网络调用的价值不能抵消逐项对账成本, 重试单元需要与可验证副作用单元对齐.

### 未验证事项

- 真实服务的逐项结果是否与副作用原子可见, 以及结果查询是否存在延迟或丢失.
- 服务端去重、顺序保证、限流提示和不可逆副作用是否允许安全选择性重试.
- 大批量、跨区域和并发恢复条件下的有效耗时与账本成本.

## 指标

- 有效完成: 逐项恢复路径为是, 传输级与整批重试路径为否.
- 重放一致与幂等通过: 逐项恢复完成后为是, 新增调用 0, 新增写入 0.
- 中断恢复: 在部分成功响应后的恢复点通过.
- 假成功: 传输级验证 1 次.
- 无效操作: 整批重试产生 2 次重复写入, 逐项路径为 0.
- 重试次数: 整批路径 1 次, 逐项路径 1 次.
- 人工介入: 正式机制实验为 0.
- 结果质量差异: 传输路径缺少 B, 整批路径重复 A 与 C, 逐项路径每项恰好一次.
- 验证后的有效耗时: 542.961 毫秒.
